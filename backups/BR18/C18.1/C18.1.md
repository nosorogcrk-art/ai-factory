### 📄 ПАСПОРТ КОНТЕЙНЕРА C18.1: LOG AGGREGATOR (АГРЕГАТОР ЛОГОВ)

**Ветка-родитель:** BR18 | **ID:** C18.1 | **Ответственный:** [назначить]

---

#### 1. ФУНКЦИОНАЛЬНОЕ ПРЕДНАЗНАЧЕНИЕ

Централизованный приём, агрегация и долговременное хранение логов от всех компонентов завода (ветки, контейнеры, агенты). Обеспечивает унифицированный интерфейс для записи логов, их индексацию и возможность последующего поиска и анализа (в том числе для C18.4 Traceability Index и BR19). Логи принимаются в структурированном формате (JSON) по HTTP, валидируются и сохраняются в распределённое хранилище с поддержкой ротации и сжатия.

---

#### 2. ТЕХНИЧЕСКАЯ ЛОГИКА (МЕХАНИКА)

- **Приём логов:**  
    – HTTP POST эндпоинт `/api/logs` принимает JSON-объект, соответствующий общей схеме логов (см. раздел 3).  
    – Поддерживается пакетная отправка (массив логов) для снижения накладных расходов.  
    – Валидация: проверка наличия обязательных полей (`timestamp`, `service`, `event_type`), при несоответствии возвращается 400.
    
- **Хранение:**  
    – Логи сохраняются в файловую систему с ротацией по дате (например, `/data/logs/YYYY-MM-DD.json`).  
    – Используется формат JSON Lines (каждая запись на отдельной строке) для удобства потоковой обработки.  
    – Автоматическая ротация: ежедневно создаётся новый файл; старые файлы могут сжиматься (gzip) после заданного периода (например, 7 дней) и удаляться через N дней (настраивается).  
    – Для повышения отказоустойчивости можно дублировать логи в secondary storage (опционально).
    
- **Индексация и поиск:**  
    – (Опционально) может использоваться встроенный полнотекстовый поиск (например, через `grep` или простой индекс по ключевым полям). Для сложного семантического поиска логи передаются в C18.4 (Traceability Index) и BR2.  
    – Предоставляется простой API для выборки логов по фильтрам (service, event_type, диапазон дат) – может быть реализован позже как отдельный патч.
    
- **Логирование собственных действий:**  
    – C18.1 логирует свои ошибки (например, недоступность диска) в собственный локальный журнал и, если возможно, отправляет алерт в C18.3.
    
- **API:**  
    – `POST /api/logs` – приём одного или нескольких логов.  
    – `GET /api/logs` – получение логов (с фильтрацией) – опционально, может быть добавлено позже.  
    – `GET /health` – проверка работоспособности.
    

---

#### 3. ВХОДЫ И ВЫХОДЫ (INTERFACES)

- **REST API (внутри Docker-сети, порт 8093):**  
    – Все запросы и ответы в формате JSON.  
    – Пример запроса (один лог):
    
    json
    
    {
      "timestamp": "2026-03-18T12:00:00Z",
      "service": "C7.2",
      "event_type": "handover_completed",
      "details": {
        "from_agent": "ГЕФЕСТ",
        "to_agent": "РЕВА",
        "task_id": "BR1-P01",
        "duration_ms": 3450,
        "status": "success"
      }
    }
    
    – Пример пакетной отправки:
    
    json
    
    [
      { "timestamp": "...", "service": "C7.2", ... },
      { "timestamp": "...", "service": "C6.1", ... }
    ]
    
    – Ответ: `202 Accepted` (если асинхронно) или `200 OK` с подтверждением.
    
- **Формат хранения:**  
    – Каждая строка в файле лога – JSON-объект (без разделителей, кроме символа новой строки).  
    – Имена файлов: `logs-YYYY-MM-DD.jsonl`.
    

---

#### 4. ИНТЕГРАЦИИ

- **Все ветки и контейнеры:** отправляют логи через HTTP POST.
    
- **C18.4 (Traceability Index):** получает логи для построения индекса (через API или прямой доступ к файлам).
    
- **C18.3 (Alert Manager):** может анализировать логи (через потоковую обработку) для выявления аномалий.
    
- **BR19 (Self-Learning):** использует логи для анализа и улучшения.
    

---

#### 5. СТЕК ТЕХНОЛОГИЙ

- Python + FastAPI (микросервис).
    
- Файловая система с ротацией (стандартные библиотеки `logging.handlers` или собственная реализация).
    
- Асинхронная обработка запросов для минимизации задержек.
    
- Docker (контейнер с монтируемым томом для логов).
