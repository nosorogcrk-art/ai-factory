### **C7.1: Identity Core (Ядро идентичности)** – ОБНОВЛЁННАЯ ВЕРСИЯ

**Ветка-родитель:** BR7 | **ID:** C7.1 | **Ответственный:** АРГУС

**1. ФУНКЦИОНАЛЬНОЕ ПРЕДНАЗНАЧЕНИЕ**  
Централизованное хранение, версионирование и раздача системных промптов и технических лимитов для всех 7 базовых ролей. Обеспечивает единый источник истины для настроек каждого агента. Интегрируется с CI/CD (BR20) для автоматического обновления файлов промптов и с мониторингом (BR18) для логирования событий.

**2. ТЕХНИЧЕСКАЯ ЛОГИКА (МЕХАНИКА)**

- **Хранилище промптов:**  
  – Каждая роль имеет отдельный файл в формате Markdown (например, `ARGUS.md`), содержащий паспорт роли и её системный промпт.  
  – Файлы хранятся в директории `00_КАНОН/ПРОМПТЫ/` и управляются BR20: обновление происходит только через CI/CD-пайплайн, который гарантирует прохождение тестов (C3.3, C19.4). Identity Core не имеет прямого доступа к Git, только к файловой системе.

- **Актуализация при чтении:**  
  – При запросе промпта для роли модуль проверяет время модификации файла (`mtime`). Если файл изменился, кэш сбрасывается и новое содержимое загружается.  
  – Допускается кэширование в памяти (с учётом mtime) для оптимизации частых запросов.

- **Контроль целостности:**  
  – При запуске агента автоматически вычисляется хеш его промпта и сверяется с эталоном, который может храниться либо в отдельном файле хешей (управляемом BR20), либо вычисляться на лету.  
  – При несоответствии – блокировка запуска и отправка события в BR18 (Alert Manager).

- **Лимиты:**  
  – В паспортах ролей фиксируются ограничения (токены, права доступа, разрешённые инструменты). При назначении задачи Аргус проверяет соответствие этим лимитам.

- **Логирование:**  
  – Все значимые события (обновление промпта, доступ, ошибки целостности) отправляются в Log Aggregator (C18.1) в формате, описанном в п.5.

**3. ВХОДЫ И ВЫХОДЫ (INTERFACES)**

- **Input:**  
  – Запросы от Аргуса на получение промпта для конкретной роли (с указанием роли).  
  – (Косвенно) обновления файлов от BR20 – через файловую систему.
- **Output:**  
  – Актуальный промпт в текстовом формате.  
  – Уведомления о несоответствии хеша (через BR18).  
  – Логи событий (в BR18).

**4. СТЕК ТЕХНОЛОГИЙ**

- Файловая система (Markdown-файлы в `00_КАНОН/ПРОМПТЫ/`).
- Git (версионирование и CI/CD) – управляется BR20, Identity Core не использует Git напрямую.
- Скрипты на Python для чтения файлов, проверки хешей, кэширования и отправки логов.
- HTTP-клиент для отправки логов в Log Aggregator (если BR18 предоставляет API).

**5. ФОРМАТ ЛОГА ДЛЯ BR18**  
Каждое событие отправляется в C18.1 в виде JSON:
```json
{
  "timestamp": "2026-03-18T10:00:00Z",
  "service": "C7.1",
  "event_type": "prompt_updated | prompt_accessed | hash_check_failed",
  "details": {
    "role": "АРГУС",
    "version": "v1.2.3",               // если версия известна (из Git-тега или метаданных файла)
    "file": "ARGUS.md",
    "hash_match": true,                 // только для hash_check_failed
    "error": "описание ошибки"           // при наличии
  }
}
```
Для событий доступа (`prompt_accessed`) можно дополнительно логировать идентификатор агента/пользователя, если он доступен.

**6. ИНТЕГРАЦИИ**

- **BR20 (CI/CD):** получает обновлённые файлы промптов через деплой. Identity Core не взаимодействует с BR20 напрямую, только читает файлы.
- **BR18 (Monitoring):** отправка логов и алертов о несоответствии хеша.
- **BR3 (Methodology):** через стандарты (каноны) задаются правила оформления промптов.
- **BR19 (Self-Learning):** логи используются для анализа эффективности промптов.

**7. СПИСОК ПАТЧЕЙ И ИХ ФУНКЦИИ**  
- **P7.1.1 (Структура промптов):** создание базовой структуры папок `00_КАНОН/ПРОМПТЫ/` и шаблонов для каждой роли.
- **P7.1.2 (prompt_builder.py):** скрипт, который по запросу возвращает актуальный промпт для заданной роли, с проверкой mtime и кэшированием.
- **P7.1.3 (Версионирование):** добавление поддержки проверки целостности (хеш-суммы) и логирования событий в BR18.
- **P7.1.4 (Интеграция с BR20):** (новый патч) доработка для работы в режиме «только чтение файлов»; удаление зависимостей от Git. Этот патч может быть выполнен после того, как BR20 обеспечит деплой файлов. Фактически он заменяет предыдущую логику работы с Git на пассивное ожидание изменений через mtime.
