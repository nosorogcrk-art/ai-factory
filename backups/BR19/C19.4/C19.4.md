
### 📄 ПАСПОРТ КОНТЕЙНЕРА C19.4: A/B TESTER (A/B ТЕСТЕР)

---

#### 1. ФУНКЦИОНАЛЬНОЕ ПРЕДНАЗНАЧЕНИЕ
Платформа для проведения экспериментов по сравнению двух версий промптов или навыков: текущей (контрольной) и экспериментальной. Обеспечивает разделение трафика, сбор метрик успешности, времени выполнения, затрат и статистический анализ результатов. При положительном результате (статистически значимое улучшение) автоматически инициирует внедрение новой версии через BR20 (CI/CD). Все эксперименты логируются в BR18 для последующего аудита.

---

#### 2. ТЕХНИЧЕСКАЯ ЛОГИКА (МЕХАНИКА)

- **Создание эксперимента:**  
  – Через API (или автоматически от C19.2) создаётся эксперимент с указанием:  
    * тип объекта (prompt / skill) и его идентификатор;  
    * контрольная версия (например, текущая);  
    * экспериментальная версия (кандидат);  
    * доля трафика для экспериментальной версии (например, 10%);  
    * целевая метрика (успешность, время, затраты);  
    * длительность или количество задач.  

- **Маршрутизация запросов:**  
  – Во время эксперимента все запросы, относящиеся к данному объекту, проходят через A/B Tester (или он управляет переключением через C7.4 / C17.5).  
  – Для каждого запроса случайным образом выбирается версия согласно заданной пропорции.  
  – Результаты выполнения (успех/неудача, метрики) привязываются к версии и сохраняются.  

- **Сбор и анализ данных:**  
  – По завершении эксперимента (или по накоплению достаточного количества данных) запускается статистический тест (например, t-тест, хи-квадрат, тест Манна‑Уитни).  
  – Определяется, является ли улучшение статистически значимым (p < 0.05).  

- **Принятие решения:**  
  – Если экспериментальная версия значимо лучше, инициируется её внедрение через BR20 (создание задачи на деплой).  
  – Если хуже или нет значимых различий – эксперимент закрывается с соответствующим отчётом.  
  – Результаты сохраняются в историю.  

- **API:**  
  – `POST /experiments` – создать эксперимент.  
  – `GET /experiments` – список экспериментов.  
  – `GET /experiments/{id}` – детали и результаты.  
  – `POST /experiments/{id}/stop` – досрочная остановка.  
  – `POST /experiments/{id}/deploy` – принудительное внедрение (для админа).  

- **Логирование:**  
  – Каждый шаг (создание, назначение версии, результат) отправляется в C18.1.

#### 3. ВХОДЫ И ВЫХОДЫ (INTERFACES)

- **REST API (внутри Docker-сети, порт 8104):**  
  – Пример создания эксперимента:  
    `POST /experiments`  
    ```json
    {
      "type": "prompt",
      "object_id": "prompt_argus_v1",
      "control_version": "v1.2.3",
      "treatment_version": "v1.2.4",
      "traffic_split": 0.1,
      "target_metric": "success_rate",
      "min_samples": 1000
    }
    ```  
    Ответ: `{ "experiment_id": "exp_12345", "status": "created" }`  

- **Выход:** после завершения возвращает отчёт с решением.

#### 4. ИНТЕГРАЦИИ

- **C19.2 (Prompt Optimizer):** получает кандидатов для тестирования.  
- **C7.4 (Skill Integrator) / C17.5 (Skill Publisher):** для маршрутизации запросов к нужной версии промпта/навыка.  
- **BR18 (Monitoring):** сбор метрик (через C18.2, C18.5).  
- **BR20 (CI/CD):** инициирование деплоя при положительном результате.  
- **BR3 (Methodology):** может предоставлять критерии для тестов.
