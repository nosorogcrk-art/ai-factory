## 1. Функциональное предназначение

Проектирование атомарных шагов реализации согласно методу САГА. Превращает описание задачи в набор атомарных патчей (L4) с чёткими границами, зависимостями и указанием необходимых навыков. Предоставляет REST API для внешнего вызова.

---

## 2. Техническая логика (механика)

### 2.1. Эндпоинты

- `POST /decompose` – принять описание задачи и вернуть список созданных патчей.
- `GET /health` – проверка работоспособности.

#### 2.1.1. Запрос `/decompose`

**Тело (JSON):**
```json
{
  "description": "текст описания задачи",
  "context": {
    "task_id": "DIALOG-xxx"
  }
}
```

**Ответ (JSON):**
```json
{
  "patches": ["IMP-20260324-001", "IMP-20260324-002"],
  "status": "ok"
}
```

**Коды ответа:**
- `200 OK` – успешно.
- `400 Bad Request` – неверный формат запроса.
- `500 Internal Server Error` – ошибка декомпозиции.

### 2.2. Алгоритм работы
1. Получить описание и контекст из запроса.
2. Вызвать внутренний модуль `decomposer` (оформленный как Python-библиотека, `import decomposer`). Вызов должен быть синхронным.
3. Полученные патчи сохранить в реестр задач (`task_registry.json`) в том же формате, что и при ручной декомпозиции (каждая запись патча содержит поля `id`, `title`, `description`, `status: NEW`, `type: improvement` и т.д.).
4. Вернуть список ID созданных патчей.

### 2.3. Логирование
- Каждый запрос логируется в локальный файл `01_ЦЕХ/01_ЖУРНАЛЫ/patch_architect.log`.
- При успехе или ошибке отправляется событие в BR18 (через `send_log_to_br18`).

### 2.4. Healthcheck
- Эндпоинт `GET /health` возвращает `{"status": "ok"}`.

## 3. Входы и выходы (Interfaces)

### 3.1. Input
- HTTP-запросы на `/decompose`.

### 3.2. Output

- Обновлённый реестр задач.
- Логи в BR18.
