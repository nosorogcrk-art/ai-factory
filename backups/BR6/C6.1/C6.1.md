### **C6.1: Chaos Monkey (Хаос-обезьяна)**

**Ветка-родитель:** BR6 | **ID:** C6.1 | **Ответственный:** РЕВА

**1. ФУНКЦИОНАЛЬНОЕ ПРЕДНАЗНАЧЕНИЕ**  
Автоматизированная проверка устойчивости инфраструктуры и системных компонентов завода к различным типам сбоев. Chaos Monkey имитирует отказы (остановка контейнеров, потеря сети, высокая нагрузка и т.п.) и оценивает способность системы к самовосстановлению. Результаты экспериментов логируются в BR18 и могут использоваться для анализа надёжности и улучшения архитектуры.

**2. ТЕХНИЧЕСКАЯ ЛОГИКА (МЕХАНИКА)**  

- **Типы сбоев (настраиваются в конфигурации):**  
  – Остановка контейнера (`docker stop`) с последующим автоматическим восстановлением (ожидается, что BR0 перезапустит контейнер).  
  – Удаление контейнера (`docker rm`) – проверка пересоздания оркестратором.  
  – Потеря сети – изоляция контейнера (отключение от внутренней сети).  
  – Искусственные задержки – добавление латентности через `tc` (traffic control).  
  – Высокая нагрузка CPU/памяти – запуск стресс-теста внутри контейнера (например, с помощью `stress`).  
  – Потеря тома – временное отключение монтируемого тома (имитация сбоя диска).  

- **Запуск экспериментов:**  
  – **По расписанию:** планировщик (например, `apscheduler` или cron внутри контейнера) запускает эксперименты в случайные моменты времени в пределах заданного интервала (например, каждый час ± 10 минут).  
  – **По запросу:** через REST API (POST `/experiment`) можно инициировать конкретный тип сбоя для целевого контейнера. API интегрируется с C4.3 (Command Console).  

- **Выбор цели:**  
  – Целевые контейнеры определяются из реестра BR0 (C0.4) или из Docker API.  
  – В конфигурации можно указать список контейнеров-кандидатов, исключая критические (например, сам BR6).  

- **Ход эксперимента:**  
  1. Получение списка доступных контейнеров (через Docker API или BR0).  
  2. Выбор случайного контейнера и типа сбоя согласно вероятностям (настраивается).  
  3. Применение воздействия (остановка, удаление, сетевая задержка и т.д.).  
  4. Ожидание восстановления (таймаут, например, 120 секунд).  
  5. Проверка:  
     – Появился ли контейнер снова (через Docker API или опрос healthcheck).  
     – Целостность данных (опционально, запрос к C0.2 Reality Observer).  
     – Отсутствие влияния на другие контейнеры (проверка доступности критических сервисов).  
  6. Фиксация результата (успех/неудача, время восстановления) и логирование.  

- **Логирование:**  
  – Каждый эксперимент формирует событие, отправляемое в **BR18 (C18.1 Log Aggregator)** в формате JSON (см. раздел 3).  

**3. ВХОДЫ И ВЫХОДЫ (INTERFACES)**  

- **REST API (внутри Docker-сети):**  
  – `POST /experiment` – запуск эксперимента вручную. Тело запроса (JSON):  
    ```json
    {
      "container": "br1_cognitive_engine",   // опционально, если не указан – выбирается случайно
      "type": "container_stop",               // тип сбоя
      "duration_sec": 30                       // длительность воздействия (для нагрузочных тестов)
    }
    ```  
    Ответ: `202 Accepted` с ID эксперимента.  

  – `GET /experiment/{id}` – получение статуса и результата эксперимента.  

  – `GET /config` – просмотр текущей конфигурации (вероятности, расписание).  

  – `PUT /config` – изменение конфигурации (только для администратора).  

- **Формат лога (в BR18):**  
  ```json
  {
    "timestamp": "2026-03-18T12:00:00Z",
    "service": "C6.1",
    "event_type": "chaos_experiment",
    "details": {
      "container": "br1_cognitive_engine",
      "experiment_type": "container_stop",
      "duration_sec": 30,
      "recovered": true,
      "recovery_time_ms": 2500,
      "error": null
    }
  }
  ```  

**4. ИНТЕГРАЦИИ**  

- **BR0 (Infrastructure):**  
  – **Docker API** – для управления контейнерами (остановка, удаление, инспекция).  
  – **C0.4 Registry Manager** – для получения информации о контейнерах (опционально).  
- **BR18 (Monitoring):**  
  – **C18.1 Log Aggregator** – отправка логов экспериментов.  
- **BR4 (Interface):**  
  – **C4.3 Command Console** – приём команд ручного запуска через API.  
- **BR6 (Immunitet):**  
  – **C6.2 Semantic Auditor** – (косвенно) через логи; данные Chaos Monkey могут использоваться для оценки последствий.  

**5. СТЕК ТЕХНОЛОГИЙ**  

- Python + FastAPI (микросервис).  
- Docker SDK for Python (`docker-py`).  
- Планировщик: `APScheduler` или просто cron (запуск скрипта).  
- Для сетевых задержек: утилита `tc` (требуется привилегированный режим контейнера).  
- Для нагрузки CPU/памяти: `stress` или `stress-ng` (устанавливаются в контейнер).  
- Логирование: отправка HTTP POST в BR18.  
- Контейнер должен запускаться с привилегиями (`privileged: true`) и доступом к Docker-сокету (монтирование `/var/run/docker.sock`).
