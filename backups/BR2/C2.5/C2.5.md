### **C2.5: Source Quality Filter (Фильтр качества источников)**

**Ветка-родитель:** BR2 | **ID:** C2.5 | **Ответственный:** МНЕМОСИНА

**1. ФУНКЦИОНАЛЬНОЕ ПРЕДНАЗНАЧЕНИЕ**  
Оценка качества внешних источников знаний (GitHub-репозиториев, статей arXiv, технических блогов) перед их индексацией в векторную память. Фильтр применяет набор критериев (звёзды, свежесть коммитов, наличие тестов, лицензия, дата публикации, доверенные домены) и выдаёт вердикт: допускать источник к индексации или отбрасывать. Все проверки логируются в BR18 для последующего аудита и настройки порогов.

**2. ТЕХНИЧЕСКАЯ ЛОГИКА (МЕХАНИКА)**  

- **Конфигурация:**  
  – Пороговые значения и правила хранятся в файле `source_quality_config.json`, расположенном в томе контейнера (монтируется из BR0).  
  – Пример структуры конфига:  
    ```json
    {
      "github": {
        "min_stars": 100,
        "max_last_commit_days": 365,
        "require_tests": true,
        "allowed_licenses": ["MIT", "Apache-2.0", "BSD-3-Clause", "BSD-2-Clause", "ISC"]
      },
      "arxiv": {
        "max_age_years": 2,
        "allowed_categories": ["cs.AI", "cs.LG", "cs.CL", "stat.ML"]
      },
      "blog": {
        "max_age_days": 365,
        "trusted_domains": ["medium.com", "dev.to", "habr.com", "opensource.com"]
      }
    }
    ```  
  – При старте сервиса конфиг загружается и кэшируется; изменения в файле применяются без перезапуска (периодическая проверка mtime или хот-релоад).

- **Оценка источника:**  
  – Модуль получает на вход JSON с данными об источнике (см. раздел 3).  
  – В зависимости от поля `type` применяются соответствующие правила.  
  – Если хотя бы одно условие нарушено, источник считается некачественным, возвращается `"allowed": false` с указанием причины.  
  – Если все проверки пройдены — `"allowed": true`.

- **Интеграция с C2.4:**  
  – C2.4 (External Knowledge Collector) при обнаружении нового источника отправляет синхронный HTTP POST-запрос в C2.5 на эндпоинт `/check`.  
  – В ответе получает решение и действует соответственно (индексирует или отбрасывает).

- **Логирование:**  
  – Каждый вызов `/check` генерирует лог-событие, которое отправляется в **BR18 (Log Aggregator)**.  
  – Логируются как успешные прохождения, так и отказы с причинами.

**3. ВХОДЫ И ВЫХОДЫ (INTERFACES)**  

- **REST API:**  
  – **POST /check**  
    * **Тело запроса** (JSON):  
      ```json
      {
        "source_url": "https://github.com/owner/repo",
        "type": "github",
        "stars": 150,
        "last_commit": "2025-01-15T00:00:00Z",
        "has_tests": true,
        "license": "MIT",
        "published_date": "2025-01-01",
        "category": "cs.AI",
        "domain": "medium.com"
      }
      ```  
      (поля, не относящиеся к типу, игнорируются).  
    * **Ответ** (JSON):  
      ```json
      {
        "allowed": true,
        "reason": null
      }
      ```  
      или  
      ```json
      {
        "allowed": false,
        "reason": "stars below threshold (45 < 100)"
      }
      ```

- **Коды ответа:**  
  – `200 OK` – успешная проверка.  
  – `400 Bad Request` – неверный формат входных данных, отсутствие обязательных полей.  
  – `500 Internal Server Error` – внутренняя ошибка сервиса.

**4. ИНТЕГРАЦИИ**  

- **C2.4 (External Knowledge Collector):** вызывает C2.5 перед индексацией нового источника.  
- **BR18 (Monitoring):** отправка логов в C18.1 (Log Aggregator).  
- **BR0 (Infrastructure):** через общий том получает доступ к конфигурационному файлу.

**5. СТЕК ТЕХНОЛОГИЙ**  

- Python + FastAPI (микросервис).  
- Pydantic для валидации входных данных.  
- Uvicorn (ASGI-сервер).  
- HTTP-клиент (`httpx`) для отправки логов (опционально, если логирование реализуется отдельной библиотекой).  
- Docker (контейнер добавляется в `docker-compose.yml` ветки BR2).
