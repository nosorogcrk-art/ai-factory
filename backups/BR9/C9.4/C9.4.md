## 1. Функциональное предназначение

Управление диалогом с пользователем, использование LLM (DeepSeek) для генерации уточняющих вопросов и накопления информации. После завершения диалога создаёт задачу в handover, **автоматически вызывает декомпозитор (C1.2) через HTTP, а затем интегратор (C10.1)**.

---

## 2. Техническая логика (механика)

### 2.1. Существующая логика
- Приём сообщений через `POST /api/dialog`.
- Взаимодействие с DeepSeek.
- Сохранение диалога в C2.6.
- Создание задачи в handover (через `handover.py`).

### 2.2. Новая логика (автоматическая обработка)

#### 2.2.1. Вызов декомпозитора (C1.2)
- После успешного создания задачи в handover (получен `task_id`) запускается асинхронная фоновая задача.
- В фоновой задаче отправляется `POST /decompose` на адрес `DECOMPOSER_URL` с телом:
  ```json
  {
    "description": "описание задачи",
    "context": { "task_id": "DIALOG-xxx" }
  }
  ```
- Ответ C1.2 содержит список созданных патчей (например, `{"patches": ["IMP-...", ...]}`).
- Если декомпозиция успешна:
  - статус исходной задачи в реестре обновляется на `IN_PROGRESS`.
  - в `history` добавляется запись о декомпозиции.
- **Если декомпозитор вернул пустой список (`patches: []`)**:
  - статус задачи не изменяется (остаётся `NEW`).
  - в `history` добавляется запись: `decomposition returned no patches`.
  - интегратор не вызывается.

#### 2.2.2. Вызов интегратора (C10.1)
- После получения списка патчей (не пустого) отправляется `POST /build` на `INTEGRATOR_URL` с телом:
  ```json
  {
    "patch_ids": ["IMP-...", ...],
    "check_skills": true,
    "run_tests": true
  }
  ```
- Результат (успех/неудача) логируется и отправляется в BR18.

#### 2.2.3. Обработка ошибок
- Если вызов C1.2 или C10.1 не удался:
  - ошибка фиксируется в логе и отправляется в BR18.
  - статус задачи **не изменяется** (остаётся `NEW`), в `history` добавляется запись об ошибке.
- Основной ответ пользователю возвращается немедленно, не дожидаясь завершения фоновой задачи.

### 2.3. Логирование
- Все вызовы и их результаты записываются в локальный лог (`01_ЦЕХ/01_ЖУРНАЛЫ/dialogue_manager.log`) и отправляются в BR18 с типами:
  - `decomposition_started`
  - `decomposition_completed` (с количеством патчей)
  - `decomposition_failed`
  - `integration_triggered`
  - `integration_failed`

---

## 3. Входы и выходы (Interfaces)

### 3.1. Input
- HTTP-запросы на `/api/dialog`.
- Ответы от DeepSeek.
- Ответы от C1.2 (декомпозитор) и C10.1 (интегратор).

### 3.2. Output
- HTTP-ответы пользователю.
- Запросы к handover (`take`).
- HTTP-запросы к C1.2 (`/decompose`) и C10.1 (`/build`).
- Логи в BR18.

## 4. Интеграции

| Сервис | Использование |
|--------|---------------|
| **BR7 (handover)** | Создание задачи |
| **C1.2 (Patch Architect)** | Вызов декомпозитора (HTTP) |
| **C10.1 (Integrator)** | Вызов сборки (HTTP) |
| **BR18 (Monitoring)** | Отправка логов |
| **C2.6 (Project Memory)** | Сохранение диалогов |

## 5. Переменные окружения

| Переменная | Значение по умолчанию | Назначение |
|------------|-----------------------|------------|
| `DECOMPOSER_URL` | `http://patch-architect:8085` | Адрес сервиса C1.2 |
| `INTEGRATOR_URL` | `http://integrator:8096` | Адрес C10.1 |

---

## 6. Стек технологий

- Python 3.12 + FastAPI
- `httpx` для асинхронных HTTP-вызовов
- `asyncio.create_task` для фоновых задач
- Логирование через `logging` + отправка в BR18
