### 📄 СПЕЦИФИКАЦИЯ ПАТЧА P2.3.4 (LEVEL 5)

**ID:** P2.3.4  
**Контейнер:** C2.3 (Semantic Search)  
**Название:** Доработка API семантического поиска: расширенные метаданные, фильтры и логирование в BR18

---

#### 1. ЗАМЫСЕЛ ПАТЧА
Доработать существующий модуль `semantic_search.py` (реализованный в P2.1.3) для поддержки:
- расширенных метаданных в результатах поиска (поля `source_type`, `source`, `timestamp`, `title`, `related_entities`);
- дополнительных фильтров запроса (`source_type`, `source`, `date_from`, `date_to`, `related_to`);
- отправки логов в центральный агрегатор BR18 (C18.1) при каждом поисковом запросе.

Это обеспечит соответствие требованиям паспорта C2.3 и интеграцию с Citations Agent (BR3), графом навыков (BR17) и системой самообучения (BR19).

---

#### 2. ТЕХНИЧЕСКИЕ ПАРАМЕТРЫ

- **Зависимости:** P2.1.3 (базовый семантический поиск), C18.1 (Log Aggregator) – предполагается, что BR18 уже реализован или его API доступен на момент выполнения патча.
- **Модифицируемый файл:** `agents/tools/semantic_search.py` (или эквивалентный).
- **Добавляемые возможности:**

  **2.1. Расширенные метаданные результатов**
  Каждый возвращаемый документ должен содержать поля:
  - `id` – идентификатор документа (путь).
  - `source` – строка, идентифицирующая происхождение (например, `"internal"`, `"github:owner/repo"`, `"arxiv:XXXX.XXXXX"`, `"blog:domain.com"`, `"skill:skill_id"`).
  - `source_type` – `"internal"` или `"external"`.
  - `timestamp` – время последнего изменения документа (Unix timestamp или ISO-строка).
  - `title` – первая строка документа (обрезается до 100 символов).
  - `related_entities` – массив строк с идентификаторами связанных объектов (например, `["SKILL-001", "P1.2.3", "[[ID_Замысел]]"]`), извлечённых из содержимого документа при индексации.
  - `score` – оценка релевантности (0..1).
  - `snippet` – фрагмент текста, содержащий ключевые слова запроса.

  **2.2. Дополнительные фильтры запроса**
  Входной JSON должен принимать опциональный объект `filters` со следующими полями:
  - `source_type` – может быть `"internal"`, `"external"` или `null` (все).
  - `source` – конкретное имя источника (например, `"github:microsoft/autogen"`).
  - `date_from`, `date_to` – фильтр по временной метке (формат ISO 8601 или Unix timestamp).
  - `related_to` – поиск документов, связанных с конкретным навыком или патчем (фильтр по полю `related_entities`).

  Фильтры должны применяться при запросе к векторному хранилищу (через параметр `where` Chroma или пост-фильтрацию).

  **2.3. Логирование в BR18**
  Каждый успешный запрос должен асинхронно отправлять лог-событие в Log Aggregator (C18.1) по адресу, заданному в переменной окружения `BR18_URL` (по умолчанию `http://br18:8080/api/logs`). Формат лога:

  ```json
  {
    "timestamp": "ISO 8601 UTC",
    "service": "C2.3",
    "event_type": "semantic_search",
    "details": {
      "query": "текст запроса",
      "user": "идентификатор_агента_или_пользователя",
      "result_count": 10,
      "response_time_ms": 150,
      "filters_applied": { "source_type": "internal", ... },
      "status": "success" // или "error"
    }
  }
  ```

  При ошибках также отправлять лог с `event_type: "error"`.

- **Кэширование:** улучшить существующий LRU-кэш, чтобы ключ включал применённые фильтры.
- **Совместимость:** старый формат ответа (без метаданных) может быть сохранён для обратной совместимости через опциональный параметр `include_metadata` (по умолчанию `true` в новой версии). Но в рамках патча можно сразу перейти к новому формату, если все потребители обновлены.

#### 3. РЕАЛИЗАЦИЯ (L6 — КОД) – ОПИСАНИЕ
- Дополнить функцию `search(query, k=10, filters=None, include_metadata=True)`.
- При получении фильтров преобразовывать их в синтаксис, понятный Chroma (например, для `source_type` можно добавить условие `{"source_type": {"$eq": value}}`, если это поле есть в метаданных).
- После выполнения запроса к Chroma обогащать каждый результат метаданными из `metadatas`, вычислять `score` на основе расстояния (например, `1 / (1 + distance)`).
- Для получения `related_entities` использовать поле метаданных, которое должно заполняться индексатором (C2.2) при обработке документов. Если поле отсутствует – возвращать пустой массив.
- Логирование реализовать через фоновую задачу FastAPI (или через `asyncio.create_task`), чтобы не задерживать ответ.
- Обновить файл конфигурации (если есть) для настройки порогов и параметров кэша.

---

#### 4. КРИТЕРИЙ ПРИЕМКИ (DoD)
- При запросе с фильтрами возвращаются только документы, удовлетворяющие условиям.
- Каждый результат содержит все обязательные поля метаданных.
- Логи отправляются в BR18 (можно проверить, временно заменив URL на локальный сервер).
- Кэширование работает с учётом фильтров.
- Старый функционал (без фильтров) продолжает работать корректно.
- Документация к модулю обновлена.
