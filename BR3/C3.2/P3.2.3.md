
### 📄 СПЕЦИФИКАЦИЯ ПАТЧА P3.2.3 (LEVEL 5)

**ID:** P3.2.3  
**Контейнер:** C3.2 (Pipeline Configurator)  
**Название:** Генератор модели переходов

**Зависимости:** P3.2.2 (обновлённый `pipeline_config.json`)

---

#### 1. ЗАМЫСЕЛ ПАТЧА  
Создать скрипт `generate_task_model.py`, который на основе конфигурации конвейера (`pipeline_config.json`) автоматически генерирует или обновляет файл `task_model.json` (используемый в BR7 для SAD Logic). Скрипт преобразует последовательность этапов в набор статусов и допустимых переходов, включая новые этапы, добавленные в P3.2.2. Это обеспечит синхронизацию между методологией и фактическим управлением задачами.

---

#### 2. ТЕХНИЧЕСКИЕ ПАРАМЕТРЫ  

- **Входной файл:** `00_КАНОН/Методология/pipeline_config.json`.  
- **Выходной файл:** `00_КАНОН/ПРОЦЕССЫ/task_model.json` (если не существует, создаётся).  
- **Логика генерации:**  
  - Статусы соответствуют `id` этапов (плюс добавляются служебные статусы `BLOCKED`, `REWORK`, если их нет).  
  - Для каждого этапа создаётся статус.  
  - Для последовательности этапов генерируются переходы: из предыдущего этапа в следующий, с указанием `allowed_roles`, взятых из поля `allowed_roles` этапа (или из целевого этапа – нужно определиться). Обычно переход разрешён ролям, которые могут выполнять следующий этап.  
  - Для новых этапов также добавляются переходы с учётом их места в конвейере (по умолчанию после `ARCHIVE` или между соответствующими этапами).  
  - Также добавляются стандартные переходы:  
    - Из любого статуса в `BLOCKED` (роль `*` или `АРГУС`).  
    - Из `BLOCKED` в исходный статус (или в `NEW`).  
    - Для этапов, подразумевающих доработку (например, `REWORK`), добавляются обратные переходы.  
- **Параметры переходов:**  
  - `from` – исходный статус.  
  - `to` – целевой статус.  
  - `allowed_roles` – список ролей, которым разрешён этот переход.  
- **Скрипт должен быть идемпотентным:** при повторном запуске не создавать дубликаты переходов.  

**Пример генерируемого перехода:**  
```json
{
  "from": "L6_CODE",
  "to": "SKILL_VALIDATION",
  "allowed_roles": ["АРХИ", "ДЕДАЛ"]
}
```

- **Логирование:** скрипт записывает свои действия в `01_ЦЕХ/01_ЖУРНАЛЫ/generate_task_model.log`.

---

#### 3. РЕАЛИЗАЦИЯ (L6 — КОД) – ОПИСАНИЕ  

- Создать файл `generate_task_model.py` в `agents/tools/`.  
- Функция `load_pipeline()` читает JSON.  
- Функция `generate_model(pipeline_data)` строит новый объект модели.  
- Функция `merge_with_existing(new_model, existing_model)` обновляет существующую модель, добавляя новые статусы и переходы, но не удаляя старые (для обратной совместимости).  
- Сохранить результат в `task_model.json`.  
- Добавить логирование.  

**Пример кода (упрощённо):**  
```python
def generate_model(pipeline):
    stages = pipeline["stages"]
    statuses = [stage["id"] for stage in stages] + ["BLOCKED", "REWORK"]
    transitions = []
    for i in range(len(stages)-1):
        transitions.append({
            "from": stages[i]["id"],
            "to": stages[i+1]["id"],
            "allowed_roles": stages[i+1].get("allowed_roles", [])
        })
    # добавить другие переходы
    return {"statuses": statuses, "transitions": transitions}
```

- При запуске скрипт должен принимать опциональные аргументы (например, `--force` для перезаписи).

#### 4. КРИТЕРИЙ ПРИЕМКИ (DoD)  

- Скрипт `generate_task_model.py` создан и запускается без ошибок.  
- При первом запуске создаётся или обновляется `task_model.json`, включающий новые статусы (`SKILL_VALIDATION`, `SKILL_TESTING`, `AB_TESTING`, `CICD_INTEGRATION`).  
- Переходы между этапами корректно отражают порядок из конвейера.  
- Существующие вручную добавленные переходы сохраняются (при слиянии).  
- Логирование работает.
