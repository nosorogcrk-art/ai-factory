
### 📄 СПЕЦИФИКАЦИЯ ПАТЧА P20.3.3 (LEVEL 5)

**ID:** P20.3.3  
**Контейнер:** C20.3 (Rollback Manager)  
**Название:** Интеграция с C20.1 и применение  

**Зависимости:** P20.3.2

---

#### 1. ЗАМЫСЕЛ ПАТЧА  
Реализовать фоновый процесс, который выполняет реальный откат для задач, находящихся в статусе `pending`. Процесс получает файлы целевой версии из C20.1 (GitOps Core) и применяет их к целевому окружению через Environment Manager (C20.5). После успеха создаётся новый коммит в C20.1 с пометкой о откате.

---

#### 2. ТЕХНИЧЕСКИЕ ПАРАМЕТРЫ  

- **Фоновая задача:** планировщик (APScheduler) периодически проверяет задачи со статусом `pending` и запускает для каждой процесс отката.  
- **Процесс отката для одной задачи:**  
  1. Получить из задачи `deploy_id` или `environment` + `target_version`.  
  2. Если есть `deploy_id`, найти в `deploy_history` соответствующий деплой, извлечь `repo`, `commit`. Иначе использовать переданные `environment` и `target_version`.  
  3. Получить файлы целевой версии из C20.1:  
     – Использовать `GET /repos/{repo}/files?ref={commit}` (или последовательные запросы).  
  4. Запросить параметры окружения у C20.5 (`GET /environments/{env}`).  
  5. Для каждого файла, в зависимости от репозитория, отправить его в соответствующий целевой сервис (как в деплое).  
  6. После успешного применения всех файлов создать коммит в C20.1 с сообщением, например: `Rollback to {target_version}`. Для этого использовать `POST /repos/{repo}/commits`.  
  7. Обновить статус задачи на `completed`, сохранить результат.  
- **Обработка ошибок:** при ошибке на любом шаге статус задачи устанавливается в `failed`, детали сохраняются.  
- **Адреса сервисов:** задаются переменными окружения: `GITOPS_CORE_URL` (C20.1), `ENV_MANAGER_URL` (C20.5), а также целевых сервисов (C7.1, C17.5).  

---

#### 3. РЕАЛИЗАЦИЯ (L6 — КОД) – ОПИСАНИЕ  

- Добавить планировщик при старте.  
- В функции обработки задачи:  
  – Получить задачу из БД.  
  – Выполнить шаги, описанные выше.  
  – Обновить статус.  
- Использовать `httpx` для асинхронных запросов к сервисам.  

---

#### 4. КРИТЕРИЙ ПРИЕМКИ (DoD)  

- При наличии задачи `pending` она обрабатывается фоновым процессом.  
- При успешном откате в репозитории появляется новый коммит.  
- Целевые сервисы получают обновлённые конфигурации.  
- Статус задачи становится `completed`.  
- При ошибке статус `failed`, детали в логе.
