### 📄 СПЕЦИФИКАЦИЯ ПАТЧА P4.2.5 (LEVEL 5)

**ID:** P4.2.5  
**Контейнер:** C4.2 (Graph Visualizer)  
**Название:** Фронтенд (React + Cytoscape)  

**Зависимости:** P4.2.4 (API с поддержкой разных типов графов)

---

#### 1. ЗАМЫСЕЛ ПАТЧА  
Создать одностраничное приложение (SPA) на React, которое будет визуализировать графы, получаемые от бэкенда. Приложение должно поддерживать переключение между типами графов (семантический, навыков, патчей), интерактивное взаимодействие с узлами (всплывающие подсказки, клик для просмотра деталей) и удобную навигацию. Для отрисовки графа используется библиотека Cytoscape.js.

---

#### 2. ТЕХНИЧЕСКИЕ ПАРАМЕТРЫ  

- **Структура фронтенда:**  
  - Проект создаётся с помощью Vite + React (или Create React App).  
  - Основной компонент `GraphViewer` отвечает за загрузку данных и рендеринг графа.  
  - Компонент `GraphTypeSelector` предоставляет переключатель типов (semantic, skills, patches).  
  - Компонент `NodeDetails` отображает информацию об узле в модальном окне.  
- **Взаимодействие с бэкендом:**  
  - Используется API, разработанное в P4.2.2–P4.2.4. Эндпоинт `/api/graph?type={type}` возвращает данные графа.  
  - Для получения деталей узла (если не встроены в граф) можно использовать `/api/node/{id}` (предполагается, что он будет реализован в одном из патчей). Если нет – показывать только ID.  
- **Визуализация:**  
  - Cytoscape.js конфигурируется с force-directed layout (например, `cose`).  
  - Узлы раскрашиваются по типу (документ, навык, патч).  
  - При наведении показывается всплывающая подсказка с ID и названием.  
  - Клик по узлу открывает модальное окно с деталями (пока просто ID).  
- **Маршрутизация:** приложение располагается по корневому маршруту `/graph` (или `/`). Бэкенд должен обслуживать статические файлы.  
- **Стилизация:** используется CSS-in-JS (например, styled-components) или простой CSS с Bootstrap для минимальной стилизации.  

---

#### 3. РЕАЛИЗАЦИЯ (L6 — КОД) – ОПИСАНИЕ  

- Создать React-приложение в папке `frontend`.  
- Настроить прокси для разработки (чтобы запросы на `/api` направлялись на бэкенд).  
- Реализовать основные компоненты.  
- После сборки (`npm run build`) скопировать статические файлы в папку, обслуживаемую бэкендом (например, `static/graph`), и настроить бэкенд для отдачи `index.html` по маршруту `/graph`.  

---

#### 4. КРИТЕРИЙ ПРИЕМКИ (DoD)  

- При переходе по адресу `/graph` загружается React-приложение.  
- По умолчанию отображается семантический граф.  
- Переключатель типов меняет запрос к API и обновляет отображение.  
- Узлы разного типа имеют разные цвета.  
- При наведении показывается всплывающая подсказка.  
- Клик по узлу открывает модальное окно с ID узла.  
- Граф отрисовывается без ошибок в консоли браузера.

### 📄 СПЕЦИФИКАЦИЯ ПАТЧА P4.2.6 (LEVEL 5)

**ID:** P4.2.6  
**Контейнер:** C4.2 (Graph Visualizer)  
**Название:** Поиск и фильтрация  

**Зависимости:** P4.2.5  

---

#### 1. ЗАМЫСЕЛ ПАТЧА  
Расширить фронтенд возможностью поиска узлов по названию или ID и фильтрации по типу (документ, навык, патч). Это позволит пользователю быстро находить нужные элементы в больших графах.

---

#### 2. ТЕХНИЧЕСКИЕ ПАРАМЕТРЫ  

- **Поиск:**  
  - Добавить поле ввода над графом. При вводе текста узлы, чей `label` или `id` содержит подстроку, подсвечиваются (или остаются видимыми, остальные становятся полупрозрачными).  
  - Поиск выполняется на клиентской стороне (по уже загруженным данным).  
- **Фильтрация по типу:**  
  - Добавить набор чекбоксов или выпадающий список для выбора типов узлов (doc, skill, patch).  
  - При изменении фильтра отображаются только узлы выбранных типов.  
- **Сброс:** кнопка для сброса фильтров и поиска.  
- **Интеграция с API:** поиск на стороне сервера не требуется, так как все данные уже загружены в граф.  

---

#### 3. РЕАЛИЗАЦИЯ (L6 — КОД) – ОПИСАНИЕ  

- Добавить в `GraphViewer` состояние для хранения текста поиска и выбранных типов.  
- Применить фильтры к массиву узлов перед отрисовкой.  
- Для подсветки можно изменять прозрачность или добавлять обводку.  
- Использовать debounce для поиска (опционально).  

---

#### 4. КРИТЕРИЙ ПРИЕМКИ (DoD)  

- Поле поиска работает: при вводе текста неподходящие узлы становятся полупрозрачными.  
- Чекбоксы фильтрации скрывают узлы других типов.  
- Кнопка сброса возвращает исходное состояние.  
- Фильтры применяются без перезагрузки страницы.

### 📄 СПЕЦИФИКАЦИЯ ПАТЧА P4.2.7 (LEVEL 5)

**ID:** P4.2.7  
**Контейнер:** C4.2 (Graph Visualizer)  
**Название:** Логирование в BR18  

**Зависимости:** P4.2.6  

---

#### 1. ЗАМЫСЕЛ ПАТЧА  
Добавить в бэкенд Graph Visualizer middleware для логирования всех обращений к API в центральный лог-агрегатор BR18 (C18.1). Это обеспечит наблюдаемость использования визуализатора и поможет в отладке.

---

#### 2. ТЕХНИЧЕСКИЕ ПАРАМЕТРЫ  

- **Механизм:**  
  - В FastAPI-приложении добавить middleware, который перехватывает каждый запрос, замеряет время выполнения и отправляет лог в BR18.  
  - Лог должен содержать: метод, путь, статус код, время выполнения, IP клиента (если доступно).  
- **Формат лога:**  
  ```json
  {
    "timestamp": "ISO 8601",
    "service": "C4.2",
    "event_type": "api_call",
    "details": {
      "method": "GET",
      "path": "/api/graph",
      "query": "type=semantic",
      "status_code": 200,
      "response_time_ms": 120,
      "client_ip": "192.168.1.100"
    }
  }
  ```  
- **Асинхронность:** отправка логов выполняется в фоновой задаче (через `asyncio.create_task` или `BackgroundTasks`), чтобы не задерживать ответ.  
- **Адрес BR18:** задаётся переменной окружения `BR18_URL` (по умолчанию `http://br18:8080/api/logs`).  

---

#### 3. РЕАЛИЗАЦИЯ (L6 — КОД) – ОПИСАНИЕ  

- В файле `graph_api.py` добавить функцию `send_log` для отправки POST-запроса в BR18.  
- Создать middleware, используя `@app.middleware("http")` или `BaseHTTPMiddleware`.  
- В middleware получить время начала, выполнить запрос, затем отправить лог.  
- Обрабатывать возможные ошибки отправки (не должны влиять на основной ответ).  

---

#### 4. КРИТЕРИЙ ПРИЕМКИ (DoD)  

- При каждом запросе к API Graph Visualizer (кроме `/health`, возможно) в BR18 отправляется лог.  
- Логи содержат все указанные поля.  
- Отправка не замедляет ответ клиента.  
- При недоступности BR18 ошибки логируются локально, но не ломают API.
