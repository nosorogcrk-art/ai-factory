
### 📄 СПЕЦИФИКАЦИЯ ПАТЧА P7.2.4 (LEVEL 5)

**ID:** P7.2.4  
**Контейнер:** C7.2 (SAD Logic)  
**Название:** Отправка логов handover в BR18 (заглушка)

**Зависимости:** (ждёт BR18) — патч должен быть выполнен после того, как станет доступен хотя бы API BR18 (или его заглушка). В рамках Фазы 1 мы реализуем заглушку, которая просто пишет в локальный файл, но с имитацией отправки в BR18.

---

#### 1. ЗАМЫСЕЛ ПАТЧА
Модифицировать модуль `handover.py` (P7.2.2) таким образом, чтобы при каждом изменении статуса задачи (команды take, complete, delegate, block, unblock) отправлялось лог-событие в центральный агрегатор BR18 (C18.1). На данном этапе, пока BR18 не реализован, создаётся заглушка: логи пишутся локально в специальный файл, но с тем же форматом, что ожидается BR18. Это позволит позже легко заменить заглушку на реальный HTTP-вызов.

---

#### 2. ТЕХНИЧЕСКИЕ ПАРАМЕТРЫ

- **Целевой файл:** `agents/tools/handover.py`.
- **Новый модуль:** добавить функцию `send_log_to_br18(event_type, details)`.
- **Формат лога:** строго соответствует спецификации C7.2 (см. паспорт). Поля: `timestamp`, `service`, `event_type`, `details`.
- **Временное хранение:** заглушка должна записывать каждое событие в файл `01_ЦЕХ/01_ЖУРНАЛЫ/handover_br18.log` в формате JSON Lines (каждая строка — JSON-объект). Это позволит потом легко перенаправить в настоящий BR18.
- **Интеграция с handover:** в функции `handle_command` после успешного обновления реестра и перед возвратом результата вызывать `send_log_to_br18` с соответствующим `event_type` и деталями.
- **События для логирования:** все типы, перечисленные в паспорте C7.2: `handover_initiated`, `handover_accepted`, `handover_rejected`, `handover_completed`, `handover_timeout`, `handover_failed`, `task_cancelled`. В текущей реализации `handover.py` поддерживаются команды `take`, `complete`, `delegate`, `block`, `unblock`. Нужно сопоставить их с типами событий. Например:
  - `take` → `handover_initiated` (или `handover_accepted`, если задача уже была в очереди, но у нас простая модель). Лучше создать событие `task_taken` или использовать `handover_initiated`.
  - `complete` → `handover_completed`.
  - `delegate` → отдельное событие `task_delegated`? Но по паспорту есть `handover_rejected`, `handover_accepted` — они не совсем подходят. Предлагаем добавить новый тип `task_delegated` в детали. Но в спецификации C7.2 разрешены только указанные типы. Можно использовать `handover_initiated` с указанием цели в деталях. Уточним: для делегирования мы не меняем статус задачи, только исполнителя. Это можно логировать как `handover_delegated` (нестандартный тип) или включить в детали события `handover_initiated`. Проще всего создать отдельный тип `task_delegated`, но так как формат должен соответствовать паспорту, возможно, потребуется расширить список. На данном этапе можно договориться, что заглушка может иметь расширенный набор, а при реальной интеграции приведём к стандарту. В DoD укажем, что формат соответствует спецификации, а для делегирования используем `handover_initiated` с дополнительным полем `target` в деталях.
  - `block` → `task_blocked` (аналог `handover_failed`? Лучше `task_blocked`). Можно использовать `handover_failed` с причиной.
  - `unblock` → `task_unblocked` (можно `handover_completed`? Не подходит). Лучше добавить отдельный тип. Для заглушки допустимо.

Так как это заглушка, можно временно использовать любые типы, но лучше приблизиться к стандарту. В DoD укажем, что событие включает все необходимые поля, а типы событий приведены в соответствие с паспортом, где это возможно.

- **Пример лога:**
```json
{
  "timestamp": "2026-03-18T12:00:00Z",
  "service": "C7.2",
  "event_type": "handover_completed",
  "details": {
    "from_agent": "ГЕФЕСТ",
    "to_agent": "РЕВА",
    "task_id": "BR1-P01",
    "duration_ms": 3450,
    "status": "success"
  }
}
```
Для команды `take`:
```json
{
  "timestamp": "...",
  "service": "C7.2",
  "event_type": "handover_initiated",
  "details": {
    "to_agent": "ГЕФЕСТ",
    "task_id": "BR1-P01",
    "status": "NEW"
  }
}
```
Для `delegate`:
```json
{
  "timestamp": "...",
  "service": "C7.2",
  "event_type": "handover_initiated",
  "details": {
    "from_agent": "ГЕФЕСТ",
    "to_agent": "АРХИ",
    "task_id": "BR1-P01",
    "reason": "delegated"
  }
}
```

- **Файл лога:** `01_ЦЕХ/01_ЖУРНАЛЫ/handover_br18.log`. Строки дописываются в конец.

#### 3. РЕАЛИЗАЦИЯ (L6 — КОД) – ОПИСАНИЕ

- Добавить в `handover.py` функцию `_log_to_br18(event_type, details)`.
- Внутри функции:
  - Создать словарь лога с текущим временем (`datetime.utcnow().isoformat() + "Z"`), `service="C7.2"`, `event_type`, `details`.
  - Открыть файл `handover_br18.log` в режиме добавления (`"a"`) и записать JSON-строку с новой строкой.
- В функции `handle_command` после успешного выполнения (после сохранения реестра) вызывать `_log_to_br18` с соответствующими аргументами.
- Сопоставление команд и типов событий:
  - `take` → `event_type = "handover_initiated"`, details: `{"to_agent": actor, "task_id": task_id, "old_status": old_status}`
  - `complete` → `event_type = "handover_completed"`, details: `{"from_agent": task["assigned_to"], "task_id": task_id, "duration_ms": ...}` (duration можно не вычислять, опустить).
  - `delegate` → `event_type = "handover_delegated"` (или `"handover_initiated"` с полем `"target": target`), details: `{"from_agent": actor, "to_agent": target, "task_id": task_id}`
  - `block` → `event_type = "handover_failed"`, details: `{"task_id": task_id, "reason": comment or "blocked"}`
  - `unblock` → `event_type = "task_unblocked"`, details: `{"task_id": task_id}`

Можно использовать единый формат с полем `action` для нестандартных случаев. Главное, чтобы логи были структурированы.

- Обработка ошибок: при записи в файл не должно быть исключений, влияющих на основной процесс. Использовать `try...except` с локальным логированием ошибок (можно в `stderr` или другой лог).

---

#### 4. КРИТЕРИЙ ПРИЕМКИ (DoD)

- При каждом выполнении команды `handover.py` (take, complete, delegate, block, unblock) в файл `handover_br18.log` добавляется одна строка JSON.
- Формат строки содержит поля `timestamp`, `service`, `event_type`, `details`.
- Для команды `take` событие содержит информацию о задаче и исполнителе.
- Для `complete` – событие завершения.
- Для `delegate` – событие с указанием исходного и целевого агента.
- Для `block` – событие с причиной.
- Для `unblock` – событие разблокировки.
- При ошибках записи в файл основной процесс не прерывается (ошибка логируется в консоль или отдельный лог).
- Заглушка готова к замене на реальный HTTP-вызов в будущем.
