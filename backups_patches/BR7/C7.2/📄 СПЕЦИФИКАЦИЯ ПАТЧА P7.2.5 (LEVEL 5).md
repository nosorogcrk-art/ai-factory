### 📄 СПЕЦИФИКАЦИЯ ПАТЧА P7.2.5 (LEVEL 5)

**ID:** P7.2.5  
**Контейнер:** C7.2 (SAD Logic)  
**Название:** Заменить заглушку логирования на реальную отправку в BR18  

**Зависимости:** P18.1.1 (Log Aggregator), P7.2.4 (заглушка логирования handover)

---

#### 1. ЗАМЫСЕЛ ПАТЧА  
В предыдущем патче P7.2.4 была создана заглушка, которая записывала логи handover в локальный файл. Теперь необходимо заменить её на реальную отправку логов в центральный лог-агрегатор BR18 (C18.1). При каждом событии handover (handover_initiated, handover_completed и т.д.) модуль `handover.py` должен асинхронно отправлять POST-запрос на эндпоинт BR18 с соответствующим JSON-объектом. Это обеспечит централизованный мониторинг всех передач ответственности.

---

#### 2. ТЕХНИЧЕСКИЕ ПАРАМЕТРЫ  

- **Модифицируемый файл:** `agents/tools/handover.py` (или эквивалентный).  
- **Адрес BR18:** переменная окружения `BR18_URL` (по умолчанию `http://br18:8080/api/logs`).  
- **Формат лога** должен строго соответствовать спецификации C7.2 (см. паспорт контейнера).  
  ```json
  {
    "timestamp": "ISO 8601 UTC",
    "service": "C7.2",
    "event_type": "handover_initiated | handover_accepted | handover_rejected | handover_completed | handover_timeout | handover_failed | task_cancelled",
    "details": {
      "from_agent": "ГЕФЕСТ",
      "to_agent": "РЕВА",
      "task_id": "BR1-P01",
      "reason": "...",          // для отказов и ошибок
      "duration_ms": 3450,       // для завершённых
      "status": "success/failure"
    }
  }
  ```  
- **Механизм отправки:**  
  – Использовать асинхронный HTTP-клиент (`httpx`) в фоновой задаче FastAPI (`BackgroundTasks` или `asyncio.create_task`), чтобы не блокировать основной процесс обработки handover.  
  – При каждом вызове функции `handle_command` (или аналогичной) после успешного обновления реестра и перед возвратом результата вызывать функцию отправки лога.  
  – Для событий, которые могут происходить не только в результате команд (например, тайм-ауты), добавить вызовы в соответствующих местах.  
- **Обработка ошибок:**  
  – Если BR18 недоступен или возвращает ошибку, это не должно влиять на выполнение handover. Ошибка логируется локально в файл `handover.log` (уже существующий).  
  – Предусмотреть повторные попытки? На данном этапе достаточно однократной отправки без retry.  
- **Удаление заглушки:**  
  – Убрать запись в локальный файл `handover_br18.log` (или оставить как дополнительное логирование для отладки – опционально). Основной канал – BR18.  
- **Логирование:** все действия по отправке (успех/неудача) фиксируются в локальном лог-файле `handover.log`.  

---

#### 3. РЕАЛИЗАЦИЯ (L6 — КОД) – ОПИСАНИЕ  

- В `handover.py` добавить импорт `httpx` и `asyncio`.  
- Создать функцию `_send_log_to_br18(event_type, details, background_tasks)` (или использовать `BackgroundTasks` из FastAPI, если handover вызывается через API). Поскольку handover может вызываться не только из API, удобнее использовать `asyncio.create_task`.  
- В функциях, где ранее была заглушка, заменить вызов на `asyncio.create_task(_send_log_to_br18(...))`.  
- Убедиться, что все необходимые события логируются (см. список в спецификации).  
- Добавить обработку исключений внутри `_send_log_to_br18`.  

---

#### 4. КРИТЕРИЙ ПРИЕМКИ (DoD)  

- При выполнении любой команды handover (take, complete, delegate, block, unblock) отправляется соответствующий лог в BR18.  
- Лог содержит все обязательные поля и корректные данные.  
- При недоступности BR18 ошибка не влияет на выполнение handover, но фиксируется в локальном логе.  
- Заглушка удалена (или оставлена как опция).  
- Тестирование: можно временно поднять заглушку BR18 и проверить приходящие логи.
