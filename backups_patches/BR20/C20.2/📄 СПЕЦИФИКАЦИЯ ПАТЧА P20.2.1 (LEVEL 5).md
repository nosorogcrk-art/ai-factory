### 📄 СПЕЦИФИКАЦИЯ ПАТЧА P20.2.1 (LEVEL 5)

**ID:** P20.2.1  
**Контейнер:** C20.2 (Auto Deployer)  
**Название:** Базовая структура и опрос репозитория  

**Зависимости:** отсутствуют

---

#### 1. ЗАМЫСЕЛ ПАТЧА  
Создать FastAPI-приложение для автоматического деплоя. Реализовать базовую структуру и фоновый процесс, который периодически опрашивает Git-репозитории (через C20.1) на наличие новых коммитов в отслеживаемой ветке. При обнаружении изменений запускается pipeline (пока заглушка). Предоставить API для ручного запуска деплоя.

---

#### 2. ТЕХНИЧЕСКИЕ ПАРАМЕТРЫ  

- **Стек:** Python + FastAPI, Uvicorn, APScheduler (или asyncio).  
- **Порт:** 8106 (настраивается через переменную окружения `PORT`).  
- **Конфигурация:** файл `deployer_config.json` (или переменные окружения) содержит:  
  - Список отслеживаемых репозиториев и веток (например, `{"skills": {"branch": "main"}, "prompts": {"branch": "main"}}`).  
  - Интервал опроса `poll_interval_seconds` (по умолчанию 60).  
- **Фоновый процесс:** планировщик (APScheduler) каждые `poll_interval_seconds` вызывает функцию `check_for_updates()`, которая для каждого репозитория:  
  1. Запрашивает у C20.1 последний коммит в отслеживаемой ветке (`GET /repos/{repo}/commits?branch=...&limit=1`).  
  2. Сравнивает с сохранённым в локальной БД последним обработанным коммитом.  
  3. Если есть новый коммит, запускает процесс деплоя (пока просто логирует и создаёт задачу в БД).  
- **Хранение состояния:** SQLite (таблица `deploy_state` с полями `repo`, `last_commit`, `last_deploy_id`, `status`).  
- **API эндпоинты:**  
  - `POST /deploy` – ручной запуск деплоя для указанного репозитория и ветки (пока заглушка, возвращает `deploy_id`).  
  - `GET /status` – возвращает статус последних деплоев (из БД).  
- **Локальное логирование:** файл `01_ЦЕХ/01_ЖУРНАЛЫ/auto_deployer.log`.  
- **Эндпоинт /health** – возвращает `{"status": "ok"}`.  

---

#### 3. РЕАЛИЗАЦИЯ (L6 — КОД) – ОПИСАНИЕ  

- Создать файл `auto_deployer.py` с FastAPI-приложением.  
- При старте инициализировать SQLite (таблица `deploy_state`), загрузить конфигурацию, запустить планировщик.  
- Реализовать функцию `check_for_updates()`, которая опрашивает C20.1, сравнивает коммиты и при обнаружении нового создаёт запись в таблице `deploy_state` со статусом `pending`.  
- Эндпоинт `POST /deploy` пока просто генерирует `deploy_id`, создаёт запись в БД со статусом `manual` и возвращает ID.  
- Эндпоинт `GET /status` возвращает список последних деплоев из БД.  

---

#### 4. КРИТЕРИЙ ПРИЕМКИ (DoD)  

- Приложение запускается на порту 8106.  
- Планировщик запускается и выполняет опрос с заданным интервалом.  
- При наличии нового коммита в репозитории создаётся запись в БД.  
- Ручной запуск деплоя работает.  
- Эндпоинт `/status` возвращает данные.  
- Логирование работает.
