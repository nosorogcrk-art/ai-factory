
### 📄 СПЕЦИФИКАЦИЯ ПАТЧА P10.2.3 (LEVEL 5)

**ID:** P10.2.3  
**Контейнер:** C10.2 (Стенд Приемки)  
**Название:** Интеграция с реестром задач (обновление статуса)

**Зависимости:** P10.2.2

---

#### 1. ЗАМЫСЕЛ ПАТЧА  
После завершения тестирования необходимо обновить статус соответствующей задачи в реестре. Если тесты пройдены успешно, задача переводится в статус `ON_RELEASE`; при наличии ошибок – возвращается на доработку (статус `REWORK` с комментарием). Патч добавляет новый скрипт `update_task_status.py`, который интегрируется с системой управления задачами (BR7) и обновляет реестр.

---

#### 2. ТЕХНИЧЕСКИЕ ПАРАМЕТРЫ  

- **Новый файл:** `agents/tools/update_task_status.py`.  
- **Входные данные:** JSON-объект, содержащий:  
  - `task_id` – идентификатор задачи.  
  - `success` – булев флаг, успешны ли тесты.  
  - `report_path` – путь к файлу отчёта о тестировании (опционально).  
- **Выходные данные:** JSON-объект с полем `status` (обновлённый статус) или ошибкой.  
- **Алгоритм:**  
  1. Загружает реестр задач из `01_ЦЕХ/ТЕКУЩИЕ_ЗАДАЧИ/task_registry.json`.  
  2. Находит задачу по `task_id`.  
  3. Определяет новый статус: `ON_RELEASE` если `success == True`, иначе `REWORK`.  
  4. Обновляет поля `status`, `updated_at`, добавляет запись в `history` с комментарием о результате тестирования и ссылкой на отчёт.  
  5. Сохраняет реестр.  
- **Логирование:** действия записываются в `01_ЦЕХ/01_ЖУРНАЛЫ/update_task_status.log`.  

---

#### 3. РЕАЛИЗАЦИЯ (L6 — КОД)  

(Код аналогичен приведённому в файле `P10.2.2 Интеграция с реестром задач.md` из предоставленных материалов, но с корректировкой ID патча.)  

**Файл: `update_task_status.py`**  

```python
#!/usr/bin/env python3
# -*- coding: utf-8 -*-

"""
update_task_status.py – обновление статуса задачи по результатам тестирования.
"""

import json
import sys
import logging
from pathlib import Path
from datetime import datetime

TASK_REGISTRY_PATH = Path("01_ЦЕХ/ТЕКУЩИЕ_ЗАДАЧИ/task_registry.json")
LOG_FILE = Path("01_ЦЕХ/01_ЖУРНАЛЫ/update_task_status.log")
LOG_FILE.parent.mkdir(parents=True, exist_ok=True)

logging.basicConfig(
    filename=LOG_FILE,
    level=logging.INFO,
    format='%(asctime)s - %(levelname)s - %(message)s'
)

def load_registry():
    if not TASK_REGISTRY_PATH.exists():
        return []
    with open(TASK_REGISTRY_PATH, "r", encoding="utf-8") as f:
        return json.load(f)

def save_registry(registry):
    with open(TASK_REGISTRY_PATH, "w", encoding="utf-8") as f:
        json.dump(registry, f, indent=2, ensure_ascii=False)

def update_task(registry, task_id, success, report_path):
    for task in registry:
        if task["id"] == task_id:
            old_status = task["status"]
            new_status = "ON_RELEASE" if success else "REWORK"
            task["status"] = new_status
            task["updated_at"] = datetime.now().isoformat()
            if "history" not in task:
                task["history"] = []
            task["history"].append({
                "timestamp": datetime.now().isoformat(),
                "from": old_status,
                "to": new_status,
                "actor": "test_stand",
                "comment": f"Tests {'passed' if success else 'failed'}. Report: {report_path}"
            })
            logging.info(f"Task {task_id} status updated to {new_status}")
            return True
    logging.error(f"Task {task_id} not found")
    return False

def main():
    data = json.load(sys.stdin)
    task_id = data.get("task_id")
    success = data.get("success", False)
    report_path = data.get("report_path", "")

    if not task_id:
        logging.error("Missing task_id")
        sys.exit(1)

    registry = load_registry()
    if update_task(registry, task_id, success, report_path):
        save_registry(registry)
        print(json.dumps({"status": "ok", "task_id": task_id}))
    else:
        sys.exit(1)

if __name__ == "__main__":
    main()
```

#### 4. КРИТЕРИЙ ПРИЕМКИ (DoD)  

- Скрипт создан и может быть вызван после выполнения тестов.  
- При передаче корректных данных обновляет статус задачи в реестре.  
- В историю задачи добавляется запись с результатом тестирования.  
- При отсутствии задачи в реестре скрипт завершается с ошибкой и логирует проблему.  
- Логирование ведётся.

### 📄 СПЕЦИФИКАЦИЯ ПАТЧА P10.2.4 (LEVEL 5)

**ID:** P10.2.4  
**Контейнер:** C10.2 (Стенд Приемки)  
**Название:** Тестирование использования навыков (реальная интеграция)

**Зависимости:** P10.2.3, BR17 (C17.4 Skill Tester)

---

#### 1. ЗАМЫСЕЛ ПАТЧА  
Заменить заглушку проверки навыков (P10.2.2) на реальную интеграцию с **C17.4 (Skill Tester)**. Теперь перед запуском тестов продукта стенд будет запрашивать у BR17 выполнение тестов для каждого навыка, указанного в метаданных продукта. Результаты тестирования навыков влияют на общий вердикт: если хотя бы один навык не проходит тесты, продукт считается неготовым к релизу, и задача переводится в статус `REWORK` с соответствующим комментарием. Все результаты логируются в BR18.

---

#### 2. ТЕХНИЧЕСКИЕ ПАРАМЕТРЫ  

- **Модифицируемый файл:** `agents/tools/test_stand.py`.  
- **Заменяемая функция:** `_check_skills_stub` заменяется на `_check_skills_real(skills)`.  
- **API BR17 (C17.4):**  
  - Предполагается эндпоинт `POST /tester/run` для запуска тестов одного навыка (или пакетного запуска). Формат запроса:  
    ```json
    {
      "skill_id": "SKILL-042",
      "version": "1.2.3"  // опционально
    }
    ```  
  - Ответ: `{"success": true, "details": {...}}` или `{"success": false, "error": "..."}`.  
  - Адрес сервиса задаётся переменной окружения `BR17_SKILL_TESTER_URL` (по умолчанию `http://c17.4:8080`).  
- **Логика проверки:**  
  1. Для каждого навыка из метаданных вызывается C17.4.  
  2. Если любой вызов возвращает `success: false`, общая проверка считается проваленной.  
  3. Результаты (успех/неудача, детали) логируются в BR18 и локально.  
- **Влияние на общий процесс:**  
  - Если проверка навыков провалена, тесты продукта могут быть не запущены (или запущены, но итоговый статус задачи всё равно будет `REWORK`). Выбор стратегии: либо сразу прерывать процесс с ошибкой, либо запускать тесты, но потом всё равно ставить `REWORK`. Для простоты можно прерывать и не запускать тесты продукта, если проверка навыков не пройдена.  
  - Отчёт о проверке навыков добавляется в общий отчёт тестирования.  
- **Логирование в BR18:**  
  - Событие `skill_test_run` с деталями по каждому навыку.

#### 3. РЕАЛИЗАЦИЯ (L6 — КОД) – ОПИСАНИЕ  

- В `test_stand.py` добавить функцию `_check_skills_real(skills)`, которая для каждого навыка выполняет HTTP POST к C17.4. Использовать `httpx` с таймаутом.  
- Собирать результаты в список. Если хотя бы один `success == False`, возвращать `False`.  
- В основной функции `run_tests` после загрузки метаданных вызвать `_check_skills_real`. Если она вернула `False`, завершить скрипт с кодом 1, предварительно записав ошибку в лог и, возможно, обновив статус задачи через P10.2.3 (но это будет сделано отдельно).  
- Добавить конфигурационную опцию `SKIP_SKILL_TESTS` для возможности пропуска проверки (например, при отладке).

#### 4. КРИТЕРИЙ ПРИЕМКИ (DoD)  

- При наличии метаданных о навыках стенд выполняет реальные запросы к C17.4.  
- Если все навыки проходят тесты, процесс продолжается (запускаются тесты продукта).  
- Если хотя бы один навык не проходит, стенд завершается с ошибкой, логирует детали.

- В BR18 отправляются логи о результатах проверки навыков.
