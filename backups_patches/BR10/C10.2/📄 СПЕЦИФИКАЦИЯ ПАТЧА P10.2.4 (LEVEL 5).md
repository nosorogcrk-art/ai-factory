
### 📄 СПЕЦИФИКАЦИЯ ПАТЧА P10.2.4 (LEVEL 5)

**ID:** P10.2.4  
**Контейнер:** C10.2 (Стенд Приёмки)  
**Название:** Реальная интеграция тестов навыков с BR17  

**Зависимости:** P17.4.5 (C17.4 – логирование в BR18, но требуется доступность API C17.4)

---

#### 1. ЗАМЫСЕЛ ПАТЧА  
В стенде приёмки ранее была реализована заглушка для проверки использования навыков (P10.2.2). Теперь необходимо заменить её на реальные вызовы к C17.4 (Skill Tester) для запуска тестов навыков и получения результатов. Перед запуском тестов продукта стенд запрашивает метаданные о навыках (из C10.3 или непосредственно из спецификаций) и для каждого навыка, используемого в продукте, инициирует тестирование через C17.4. Результаты тестирования навыков влияют на общий вердикт: если хотя бы один навык не проходит тесты, продукт считается неготовым к релизу, задача переводится в статус `REWORK`. Все действия логируются в BR18.

---

#### 2. ТЕХНИЧЕСКИЕ ПАРАМЕТРЫ  

- **Модифицируемый файл:** `agents/tools/test_stand.py` (или аналогичный).  
- **Адрес C17.4:** переменная окружения `SKILL_TESTER_URL` (по умолчанию `http://c17.4:8091`).  
- **Источник списка навыков:**  
  – Метаданные о навыках могут быть получены из файла `metadata.json`, созданного упаковщиком (C10.3), или напрямую из спецификаций патчей. В данном патче будем использовать информацию, переданную в конфигурации тестирования (например, поле `skills` в запросе).  
- **Логика тестирования навыков:**  
  1. Перед запуском функциональных тестов продукта стенд проверяет, есть ли список навыков для тестирования.  
  2. Для каждого навыка из списка выполняется POST-запрос к C17.4 на эндпоинт `/test/{skill_id}` (или `/test`, если требуется пакетный запуск).  
  3. Так как тестирование может занимать время, используется асинхронный вызов с последующим опросом статуса (или сразу получение `test_run_id`).  
  4. Необходимо дождаться завершения всех тестов навыков (с таймаутом).  
  5. Если хотя бы один тест вернул `overall: false` (или статус `failed`), общий результат тестирования продукта считается неудачным.  
  6. Результаты тестирования навыков добавляются в отчёт стенда (поле `skill_tests`).  
  7. В BR18 отправляются логи о каждом тесте навыка (используя механизм логирования, аналогичный P10.2.4?).  
- **Интеграция с реестром задач:** после завершения всех тестов (и продукта, и навыков) вызывается обновление статуса задачи (как в P10.2.3) с учётом результатов проверки навыков.  
- **Обработка ошибок:**  
  – При недоступности C17.4 можно либо блокировать релиз, либо игнорировать проверку навыков (настраивается).  
  – Таймауты обрабатывать как ошибки.  

---

#### 3. РЕАЛИЗАЦИЯ (L6 — КОД) – ОПИСАНИЕ  

- В функции `run_tests` после загрузки конфигурации извлечь список навыков (если есть).  
- Для каждого навыка асинхронно отправить запрос в C17.4 на запуск теста.  
- Получить `test_run_id` и запустить цикл опроса до получения результата (или использовать вебхуки, если поддерживается).  
- После получения результатов агрегировать их и добавить в общий отчёт.  
- Если какой-либо тест навыка не пройден, установить флаг `skill_tests_passed = False`.  
- После выполнения всех тестов продукта и навыков вызвать `update_task_status` с учётом этого флага.  

---

#### 4. КРИТЕРИЙ ПРИЕМКИ (DoD)  

- При наличии в конфигурации списка навыков для каждого из них выполняется запрос к C17.4.  
- Результаты тестирования навыков корректно отражаются в отчёте.  
- Если все тесты навыков пройдены, продукт тестируется дальше.  
- Если какой-то тест навыка не пройден, общий результат считается неудачным, задача переводится в `REWORK`.  
- Логи в BR18 отправляются.  
- При недоступности C17.4 работа продолжается в соответствии с настройкой (блокировка/пропуск).
