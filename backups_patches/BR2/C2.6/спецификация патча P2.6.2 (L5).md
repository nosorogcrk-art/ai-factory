## 🔧 Исправленная спецификация патча P2.6.2 (L5) – с учётом аудита

**ID:** P2.6.2  
**Контейнер:** C2.6 Project Memory  
**Название:** Хранение сообщений и артефактов  

---

### 1. Цель  
Добавить возможность сохранять историю диалогов (сообщения) и артефакты (патчи, спецификации, код) для каждого проекта. **Единый источник истины для сообщений – SQLite**, файл `dialogues.jsonl` не используется (будет генерироваться при экспорте проекта в будущем). Артефакты хранятся в файловой системе с UUID-именами, метаданные – в SQLite. Обеспечивается транзакционная целостность между БД и файлами.

---

### 2. Технические параметры

#### 2.1. Структура SQLite (добавляется к существующей таблице `projects`)

```sql
-- Таблица сообщений (единственный источник)
CREATE TABLE IF NOT EXISTS project_messages (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    project_id TEXT NOT NULL,
    role TEXT NOT NULL,               -- 'user' или 'assistant'
    content TEXT NOT NULL,
    timestamp TEXT NOT NULL,
    message_type TEXT DEFAULT 'text', -- 'text', 'command', 'decision'
    FOREIGN KEY (project_id) REFERENCES projects(id) ON DELETE CASCADE
);
CREATE INDEX IF NOT EXISTS idx_project_messages_project_id ON project_messages(project_id);
CREATE INDEX IF NOT EXISTS idx_project_messages_timestamp ON project_messages(timestamp);

-- Таблица артефактов (метаданные)
CREATE TABLE IF NOT EXISTS project_artifacts (
    id TEXT PRIMARY KEY,               -- генерируется как 'art_{uuid.hex[:8]}'
    project_id TEXT NOT NULL,
    artifact_type TEXT NOT NULL,       -- 'patch', 'specification', 'code', 'test'
    name TEXT NOT NULL,                -- человеко-читаемое имя
    filename TEXT NOT NULL,            -- имя файла на диске (генерируется из id)
    version TEXT,                      -- версия, если применимо
    created_at TEXT NOT NULL,
    metadata TEXT,                     -- JSON (опционально)
    FOREIGN KEY (project_id) REFERENCES projects(id) ON DELETE CASCADE
);
CREATE INDEX IF NOT EXISTS idx_project_artifacts_project_id ON project_artifacts(project_id);
CREATE INDEX IF NOT EXISTS idx_project_artifacts_type ON project_artifacts(artifact_type);
```

#### 2.2. Файловая структура
- `01_ЦЕХ/ПРОЕКТЫ/{project_id}/artifacts/` – папка для файлов артефактов.  
- Имя файла = `{artifact_id}.md` (для текстовых) или `{artifact_id}.bin` (для бинарных). Тип определяется по расширению, но для простоты все артефакты сохраняются как `.txt` с возможностью указать `Content-Type` в будущем.  
- **Файл `dialogues.jsonl` не используется** (будет генерироваться по требованию при экспорте).

#### 2.3. API эндпоинты

##### Сообщения
- **`POST /projects/{id}/messages`**  
  Тело: `{ "role": "user|assistant", "content": "...", "message_type": "text" }`  
  – Проверка существования проекта и папки.  
  – Вставка записи в БД (транзакция).  
  – Возвращает `{ "id": ..., "timestamp": ... }`.  
  – Ошибки: 400 (неверный role), 404 (проект не найден), 500.

- **`GET /projects/{id}/messages`**  
  Параметры: `limit` (100), `offset` (0), `since` (ISO timestamp, опционально).  
  – Возвращает массив сообщений из БД, отсортированных по `timestamp` ASC.  
  – Пагинация на уровне SQL.

##### Артефакты
- **`POST /projects/{id}/artifacts`**  
  Тело: `{ "artifact_type": "patch|specification|code|test", "name": "...", "content": "...", "version": "..." }`  
  – Проверка существования проекта.  
  – Генерация `artifact_id = f"art_{uuid.uuid4().hex[:8]}"`.  
  – Имя файла = `{artifact_id}.txt`.  
  – **Порядок операций (транзакция):**  
    1. Вставка записи в таблицу `project_artifacts`.  
    2. Создание файла в `artifacts/` с содержимым.  
    3. Если файл не удалось создать – удалить запись из БД (ROLLBACK).  
  – Возвращает `{ "id": artifact_id, "name": ..., "path": ..., "created_at": ... }`.  
  – Ошибки: 400 (неверный тип, отсутствует name/content), 404 (проект не найден), 409 (артефакт с таким именем уже существует – опционально), 500.

- **`GET /projects/{id}/artifacts`**  
  Параметры: `type` (опционально), `limit`, `offset`.  
  – Возвращает список артефактов (метаданные, без содержимого).

- **`GET /projects/{id}/artifacts/{artifact_id}`**  
  – Возвращает метаданные артефакта (JSON).

- **`GET /projects/{id}/artifacts/{artifact_id}/content`**  
  – Возвращает содержимое файла с `Content-Type: text/plain`.  
  – Если файл не найден – 404.

- **`DELETE /projects/{id}/artifacts/{artifact_id}`**  
  – Удаляет запись из БД и файл.  
  – Возвращает 204 No Content.

#### 2.4. Валидация и защита
- **Path traversal**: имя файла формируется из `artifact_id`, а не из `name`.  
- **Размер содержимого**: ограничить 10 МБ (можно настроить через переменную окружения). При превышении возвращать 413 Payload Too Large.  
- **Уникальность имени**: опционально (по желанию).  
- **Проверка существования папки проекта**: при добавлении сообщения или артефакта, если папка отсутствует – вернуть 500 с логированием (нарушение целостности). Восстанавливать не пытаемся, так как это говорит о сбое.

#### 2.5. Логирование
- Каждая операция добавления сообщения/артефакта логируется локально и асинхронно отправляется в BR18.  
- Формат лога: `{ "service": "C2.6", "event_type": "message_added|artifact_added|artifact_deleted", "details": {...} }`.

#### 2.6. Миграция
- При старте приложения проверять существование таблиц `project_messages` и `project_artifacts`. Если нет – создать.  
- Индексы создаются после таблиц.

### 4. Рекомендации по реализации (для разработчика)

- Использовать `sqlite3` с явными транзакциями (`BEGIN`, `COMMIT`, `ROLLBACK`).  
- При создании артефакта: сначала вставить запись в БД (получить `artifact_id`), затем попытаться создать файл. Если файл не создался – выполнить `ROLLBACK`.  
- Для проверки размера содержимого: перед обработкой запроса проверить длину `content` (если передаётся в JSON). Для больших файлов в будущем – использовать `multipart`.  
- В `GET /projects/{id}/messages` при наличии `since` добавить условие `WHERE timestamp >= ?`.  
- В эндпоинтах проверять существование проекта через `SELECT id FROM projects WHERE id = ?` (учитывая `status` – активные).
