### 📄 СПЕЦИФИКАЦИЯ ПАТЧА P17.4.1 (LEVEL 5)

**ID:** P17.4.1  
**Контейнер:** C17.4 (Skill Tester)  
**Название:** Базовая структура и API (заглушка)  

**Зависимости:** отсутствуют

---

#### 1. ЗАМЫСЕЛ ПАТЧА  
Создать каркас микросервиса для тестирования навыков: FastAPI-приложение с заглушечными эндпоинтами для запуска тестов и получения статуса. На данном этапе не требуется реальное выполнение тестов; эндпоинты возвращают фиктивные ответы, чтобы можно было проверить работоспособность API и подготовить интеграцию с другими компонентами.

---

#### 2. ТЕХНИЧЕСКИЕ ПАРАМЕТРЫ  

- **Стек:** Python + FastAPI, Uvicorn.  
- **Порт:** 8091 (настраивается через переменную окружения `PORT`).  
- **Эндпоинты-заглушки:**  
  - `POST /test/{skill_id}` – принимает ID навыка и опциональные параметры, возвращает `{"test_run_id": "tr_12345", "status": "in_progress"}`.  
  - `GET /results/{skill_id}` – возвращает фиктивный результат:  
    ```json
    {
      "skill_id": "SKILL-042",
      "last_test": "2026-03-18T12:00:00Z",
      "overall": "passed",
      "tests": [{"name": "stub", "passed": true, "duration_ms": 100}]
    }
    ```  
  - `POST /test/all` – заглушка, возвращает `{"status": "not_implemented"}`.  
  - `GET /status` – возвращает `{"status": "ok"}`.  
- **Логирование:** все запросы записываются в локальный лог-файл `01_ЦЕХ/01_ЖУРНАЛЫ/skill_tester.log`.  

---

#### 3. РЕАЛИЗАЦИЯ (L6 — КОД) – ОПИСАНИЕ  

- Создать файл `skill_tester.py` с FastAPI-приложением.  
- Определить Pydantic-модели для ответов (хотя бы минимальные).  
- Реализовать эндпоинты как простые функции, возвращающие фиксированные JSON-объекты.  
- Настроить логирование через `logging`.  

---

#### 4. КРИТЕРИЙ ПРИЕМКИ (DoD)  

- Приложение запускается на указанном порту.  
- При `POST /test/SKILL-042` возвращается корректный JSON с `test_run_id`.  
- При `GET /results/SKILL-042` возвращается фиктивный результат.  
- Эндпоинт `/status` возвращает `{"status": "ok"}`.  
- Логи запросов пишутся в указанный файл.

### 📄 СПЕЦИФИКАЦИЯ ПАТЧА P17.4.2 (LEVEL 5)

**ID:** P17.4.2  
**Контейнер:** C17.4 (Skill Tester)  
**Название:** Интеграция с C17.1 (получение навыка)  

**Зависимости:** P17.4.1

---

#### 1. ЗАМЫСЕЛ ПАТЧА  
Заменить заглушку на реальное получение данных навыка из реестра C17.1. При запуске теста сервис запрашивает метаданные навыка (инструкцию, зависимости) через API C17.1. Это позволяет в дальнейшем использовать реальные данные для тестирования. На данном этапе само тестирование ещё не реализовано, но данные сохраняются или логируются.

---

#### 2. ТЕХНИЧЕСКИЕ ПАРАМЕТРЫ  

- **Адрес C17.1:** переменная окружения `SKILL_REGISTRY_URL` (по умолчанию `http://c17.1:8088`).  
- **Взаимодействие:**  
  - При вызове `POST /test/{skill_id}` выполняется GET-запрос к `/skills/{skill_id}` для получения полной записи навыка.  
  - Если навык не найден или статус `deleted`, возвращается ошибка 404.  
  - Полученные данные сохраняются во временном хранилище (например, в памяти) для последующего использования.  
- **Обновление статуса навыка (опционально):** после тестирования (в будущем) можно будет обновлять статус через PATCH `/skills/{id}`. Пока не реализуется.  
- **Логирование:** логируются запросы к C17.1 и ошибки.  

---

#### 3. РЕАЛИЗАЦИЯ (L6 — КОД) – ОПИСАНИЕ  

- Добавить HTTP-клиент (например, `httpx`) в зависимости.  
- В эндпоинте `POST /test/{skill_id}` перед возвратом заглушки выполнить запрос к C17.1.  
- При успешном получении данных сохранить их в глобальном словаре `test_sessions` по `test_run_id`.  
- При ошибке вернуть 404 или 500 с описанием.  

---

#### 4. КРИТЕРИЙ ПРИЕМКИ (DoD)  

- При вызове `POST /test/SKILL-042` с существующим навыком сервис обращается к C17.1 и сохраняет данные.  
- Если навык не существует, возвращается 404.  
- В логах видны запросы к C17.1.  
- При недоступности C17.1 возвращается 500.

### 📄 СПЕЦИФИКАЦИЯ ПАТЧА P17.4.3 (LEVEL 5)

**ID:** P17.4.3  
**Контейнер:** C17.4 (Skill Tester)  
**Название:** Изолированное выполнение тестов (Docker)  

**Зависимости:** P17.4.2

---

#### 1. ЗАМЫСЕЛ ПАТЧА  
Реализовать запуск тестов для навыка в изолированной среде (Docker-контейнер). Для каждого тестового запуска создаётся временный контейнер, в котором выполняется инструкция навыка с заданными входными данными, и собирается результат. Это ядро функциональности тестировщика.

---

#### 2. ТЕХНИЧЕСКИЕ ПАРАМЕТРЫ  

- **Инфраструктура:** контейнер должен иметь доступ к Docker-сокету (`/var/run/docker.sock`) для запуска дочерних контейнеров.  
- **Тестовый образ:** используется базовый образ (например, `python:3.11-slim`), в который монтируются инструкции навыка и тестовые данные.  
- **Процесс тестирования:**  
  1. Для каждого навыка, по которому поступил запрос, создаётся временная директория, куда копируются:  
     - скрипт с инструкцией (можно сгенерировать из поля `instruction` навыка);  
     - тестовые данные (из библиотеки тестов, см. P17.4.4).  
  2. Запускается Docker-контейнер с этой директорией, выполняющий команду `python script.py`.  
  3. Собирается stdout/stderr, время выполнения.  
  4. Результат сравнивается с ожидаемым.  
- **Параметры теста:** могут передаваться в теле запроса (например, конкретный тест-кейс).  
- **Результат:** возвращается статус теста (passed/failed), детали ошибок, время выполнения.  

---

#### 3. РЕАЛИЗАЦИЯ (L6 — КОД) – ОПИСАНИЕ  

- Добавить библиотеку `docker` для Python.  
- В функции обработки теста после получения данных навыка создать временную папку, записать скрипт, запустить контейнер через `docker run --rm`.  
- Дождаться завершения, проанализировать код возврата и вывод.  
- Сохранить результат в сессии теста.  
- Удалить временные файлы.  

---

#### 4. КРИТЕРИЙ ПРИЕМКИ (DoD)  

- При запуске теста для навыка создаётся Docker-контейнер, выполняющий инструкцию.  
- Результат (успех/неудача) возвращается в ответе.  
- Временные файлы удаляются после завершения.  
- При ошибках Docker (например, образ не найден) возвращается понятное сообщение.  

---

### 📄 СПЕЦИФИКАЦИЯ ПАТЧА P17.4.4 (LEVEL 5)

**ID:** P17.4.4  
**Контейнер:** C17.4 (Skill Tester)  
**Название:** Библиотека тестов и метрики  

**Зависимости:** P17.4.3

---

#### 1. ЗАМЫСЕЛ ПАТЧА  
Добавить возможность использовать заранее подготовленные тестовые кейсы из внешней библиотеки. Тестовые кейсы содержат входные данные, ожидаемые результаты и критерии оценки. Также внедрить сбор метрик (время выполнения, точность) и их сохранение для последующего анализа.

---

#### 2. ТЕХНИЧЕСКИЕ ПАРАМЕТРЫ  

- **Хранение тестовых кейсов:** в директории `00_КАНОН/Методология/Тесты_навыков/` в формате JSON. Каждый файл соответствует одному навыку (по ID) или общий для всех. Структура кейса:  
  ```json
  {
    "skill_id": "SKILL-042",
    "tests": [
      {
        "name": "basic_case",
        "input": {"code": "def foo(): return 42"},
        "expected_output": {"result": 42},
        "timeout_sec": 10
      }
    ]
  }
  ```  
- **Загрузка кейсов:** при запуске теста для навыка сервис ищет файл с соответствующим ID. Если найден, использует эти тесты; иначе выполняет только один тест с заглушкой.  
- **Метрики:** для каждого теста фиксируются:  
  - `passed` (bool)  
  - `duration_ms`  
  - `error` (если есть)  
  - `actual_output` (для отладки)  
- **Сохранение результатов:** результаты тестирования сохраняются в локальной БД (SQLite) для последующего получения через API.  

---

#### 3. РЕАЛИЗАЦИЯ (L6 — КОД) – ОПИСАНИЕ  

- Создать функцию `load_test_cases(skill_id)`, которая читает файл из `Тесты_навыков`.  
- Модифицировать процесс тестирования: для каждого тест-кейса запускать контейнер отдельно (или в одном контейнере с разными входными данными).  
- Собирать метрики и сохранять их в БД.  
- Добавить эндпоинт `GET /results/{skill_id}` для получения последних результатов (включая детали по тестам).  

---

#### 4. КРИТЕРИЙ ПРИЕМКИ (DoD)  

- При наличии файла тестов для навыка выполняются все описанные тесты.  
- Результаты содержат метрики по каждому тесту.  
- При отсутствии файла выполняется один базовый тест (заглушка).  
- Результаты сохраняются и доступны через API.

### 📄 СПЕЦИФИКАЦИЯ ПАТЧА P17.4.5 (LEVEL 5)

**ID:** P17.4.5  
**Контейнер:** C17.4 (Skill Tester)  
**Название:** Логирование в BR18  

**Зависимости:** P17.4.4

---

#### 1. ЗАМЫСЕЛ ПАТЧА  
Добавить отправку результатов тестирования и ошибок в центральный лог-агрегатор BR18 (C18.1). Это обеспечит централизованный мониторинг качества навыков и возможность анализа в BR19.

---

#### 2. ТЕХНИЧЕСКИЕ ПАРАМЕТРЫ  

- **Адрес BR18:** переменная окружения `BR18_URL` (по умолчанию `http://br18:8080/api/logs`).  
- **Формат лога:**  
  ```json
  {
    "timestamp": "ISO 8601 UTC",
    "service": "C17.4",
    "event_type": "skill_test",
    "details": {
      "skill_id": "SKILL-042",
      "test_case": "basic_case",
      "passed": true,
      "duration_ms": 1500,
      "error": null
    }
  }
  ```  
- **События для логирования:**  
  - Каждый завершённый тест (успешный или нет).  
  - Критические ошибки (например, недоступность Docker).  
- **Асинхронность:** отправка выполняется в фоновом режиме, не задерживая ответ клиента.  

---

#### 3. РЕАЛИЗАЦИЯ (L6 — КОД) – ОПИСАНИЕ  

- Добавить функцию `send_log(details, background_tasks)`.  
- В процессе выполнения тестов после каждого теста вызывать эту функцию.  
- При ошибках в самом сервисе также отправлять лог с типом `error`.  
- Обрабатывать ошибки отправки (логировать локально).  

---

#### 4. КРИТЕРИЙ ПРИЕМКИ (DoD)  

- При каждом тесте отправляется лог в BR18.  
- Лог содержит все обязательные поля.  
- При недоступности BR18 ошибка не влияет на выполнение теста, но логируется локально.  
- Отправка не блокирует основной поток.
