
### 📄 СПЕЦИФИКАЦИЯ ПАТЧА P1.3.6 (LEVEL 5)

**ID:** P1.3.6  
**Контейнер:** C1.3 (Self-Audit)  
**Название:** Интеграция с C19.4 (A/B Tester)  

**Зависимости:** P19.4.5 (API A/B Tester с логированием)

---

#### 1. ЗАМЫСЕЛ ПАТЧА  
Самоаудит (Self-Audit) должен иметь возможность инициировать A/B-тесты для сравнения текущих и улучшенных версий промптов, а также получать результаты этих тестов для принятия решения о внедрении улучшений. Ранее эта функциональность была заглушкой. Теперь, после реализации A/B Tester (C19.4) и его API, необходимо заменить заглушку на реальные вызовы. Это позволит автоматически проводить эксперименты и на основе их результатов обновлять промпты.

---

#### 2. ТЕХНИЧЕСКИЕ ПАРАМЕТРЫ  

- **Модифицируемый файл:** `agents/tools/improvement_initiator.py` (или модуль, отвечающий за создание задач на улучшение).  
- **Интеграция с C19.4 (A/B Tester):**  
  – Адрес C19.4 задаётся переменной окружения `AB_TESTER_URL` (по умолчанию `http://c19.4:8104`).  
  – Используются эндпоинты:  
    * `POST /experiments` – создание нового эксперимента. Тело запроса содержит:  
      ```json
      {
        "type": "prompt",
        "object_id": "prompt_argus_v1",
        "control_version": "v1.2.3",
        "treatment_version": "v1.2.4",
        "traffic_split": 0.1,
        "target_metric": "success_rate",
        "min_samples": 1000
      }
      ```  
      Ответ: `{ "experiment_id": "exp_12345", "status": "created" }`.  
    * `GET /experiments/{id}` – получение статуса и результатов эксперимента.  
    * (Опционально) `POST /experiments/{id}/stop` – досрочная остановка.  
- **Логика работы:**  
  1. Когда анализатор промптов (P1.3.2) и инициатор улучшений (P1.3.3) определяют, что для конкретного промпта есть кандидат на улучшение, они могут инициировать A/B-тест вместо немедленного создания задачи.  
  2. Для этого вызывается функция `create_ab_test(control_version, treatment_version, ...)`, которая отправляет запрос в C19.4 и сохраняет `experiment_id` в контексте.  
  3. Затем необходимо периодически проверять статус эксперимента (например, раз в час) через фоновую задачу или при следующем запуске инициатора.  
  4. Если эксперимент завершён и результат положительный (p-value < 0.05 и improvement > 0), создаётся задача на внедрение улучшения (через BR7).  
- **Хранение состояния:** в локальной БД или в памяти нужно хранить соответствие между experiment_id и задачей.  
- **Асинхронность:** все вызовы асинхронные, не блокируют основной процесс.  
- **Обработка ошибок:** при недоступности C19.4 логировать ошибку и использовать старую логику (без A/B-теста).  

---

#### 3. РЕАЛИЗАЦИЯ (L6 — КОД) – ОПИСАНИЕ  

- В `improvement_initiator.py` добавить функцию `_start_ab_test(control, treatment, role)`, которая отправляет POST-запрос в C19.4 и возвращает experiment_id.  
- В основном цикле проверки улучшений: если включена опция `ab_test_enabled`, то вместо создания задачи вызывать `_start_ab_test` и сохранять experiment_id в отдельной таблице `pending_ab_tests`.  
- Добавить фоновую задачу (или при каждом запуске) проверять все незавершённые эксперименты, запрашивая их статус через C19.4. Если эксперимент завершён, обрабатывать результат.  
- При положительном результате создавать задачу на обновление промпта.  

---

#### 4. КРИТЕРИЙ ПРИЕМКИ (DoD)  

- При наличии кандидата на улучшение и включённой опции A/B-тестов отправляется запрос в C19.4, возвращается experiment_id.  
- Эксперимент корректно создаётся в A/B Tester (можно проверить через его API).  
- Фоновая задача периодически опрашивает статус эксперимента.  
- При завершении эксперимента с положительным результатом создаётся задача в реестре.  
- При отрицательном результате задача не создаётся.  
- Все ошибки логируются, при недоступности C19.4 система работает в обычном режиме (без A/B-тестов).
