## 6. АУДИТ КОДА И РЕАЛИЗАЦИИ (L6)

### 6.1. Структура и стиль
- [ ] Код на Python 3.12.
- [ ] Соответствие PEP 8 (длина строки ≤100).
- [ ] Аннотации типов для всех функций, методов, публичных переменных.
- [ ] Структура файлов соответствует шаблону (main, models, services, repositories, utils, tests).
- [ ] Отсутствуют закомментированные блоки кода (если только не объяснены).
- [ ] Отсутствуют `print()` (использовать `logging`).

### 6.2. Логирование
- [ ] Используется модуль `logging`.
- [ ] Логи пишутся в файл `01_ЦЕХ/01_ЖУРНАЛЫ/{container_name}.log`.
- [ ] Критические действия (создание, обновление, удаление) – INFO.
- [ ] Ошибки – ERROR.
- [ ] Вызовы внешних сервисов логируются (факт, статус).
- [ ] Логи отправляются в BR18 (Log Aggregator) – хотя бы заглушка.

### 6.3. Обработка ошибок
- [ ] Пользовательские ошибки → HTTP 4xx с пояснением в `detail`.
- [ ] Внутренние ошибки → 500, логирование ERROR, без раскрытия деталей.
- [ ] Ошибки зависимых сервисов → 503 (если критично) или логирование и продолжение.

### 6.4. REST API
- [ ] Все ответы – JSON.
- [ ] Успешные операции: 200/201 с телом или заголовком Location.
- [ ] Ошибки: `{"detail": "Пояснение"}`.
- [ ] Эндпоинт `/health` возвращает `{"status":"ok"}` (и, возможно, проверки зависимостей).
- [ ] Документация API (docstring, OpenAPI) присутствует.

### 6.5. Тесты
- [ ] **Юнит-тесты:**
  - [ ] Каждая функция бизнес-логики покрыта.
  - [ ] Проверены успешные сценарии и краевые случаи.
- [ ] **Интеграционные тесты:**
  - [ ] Для каждого нового эндпоинта.
  - [ ] Используется тестовая БД (SQLite :memory:) или моки.
- [ ] **E2E-тесты с LLM-судьёй (если требуется):**
  - [ ] Сценарий описан, критерии для судьи заданы.
  - [ ] Порог успеха ≥ 0.8.
  - [ ] Тест запускается в CI/CD отдельно.

### 6.6. Статический анализ и качество
- [ ] `mypy --ignore-missing-imports` – без ошибок.
- [ ] `ruff check . --fix` – без ошибок (включая C901).
- [ ] Цикломатическая сложность каждой функции ≤ 10.
- [ ] Количество строк в каждом файле ≤ 300.

### 6.7. Индексация и финальные шаги
- [ ] Обновлён паспорт контейнера:
  - [ ] `status: implemented`
  - [ ] `has_tests: true`
  - [ ] `healthcheck: true`
  - [ ] `version: 1.x` (инкремент)
  - [ ] `memory_indexed: false` (станет true после индексации)
  - [ ] `requires_e2e_llm_tests: true` (если применимо)
- [ ] Добавлен healthcheck в `docker-compose.yml`.
- [ ] Перегенерирована карта: `curl -X GET "http://localhost:8101/map?refresh=true"`.
- [ ] Выполнена индексация всех новых/изменённых файлов (паспорт, код, спецификации) через `POST /index` C2.6.
- [ ] **После индексации – обязательно перегенерировать карту и проверить, что все контейнеры отображаются с корректными портами.**

## 12. ПРИЛОЖЕНИЕ: КОМАНДЫ ДЛЯ ПРОВЕРОК

# Проверка mypy
mypy --ignore-missing-imports <container_path>

ruff check <container_path> --fix

# Цикломатическая сложность
ruff check <container_path> --select C901

# Количество строк
wc -l <file>

# Валидация JSON
jq . <file.json>

# Индексация файла
curl -X POST "http://localhost:8108/api/index" \
  -H "Content-Type: application/json" \
  -d '{"documents": ["<path>"]}'

# Перегенерация карты
curl -X GET "http://localhost:8101/map?refresh=true"

# Проверка healthcheck
curl -f http://localhost:<port>/health

# Запуск тестов
pytest -v <container_path>/tests/
```
