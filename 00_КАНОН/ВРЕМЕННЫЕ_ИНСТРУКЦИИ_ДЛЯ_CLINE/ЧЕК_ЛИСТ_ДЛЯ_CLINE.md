## 1. Анализ задачи и планирование
- [ ] Прочитана и понята постановка задачи
- [ ] Проанализированы связанные файлы (паспорта, код, документация)
- [ ] Определён объём работ и необходимые изменения
- [ ] Проверена совместимость с существующей архитектурой

## 2. Кодирование и структура
- [ ] Код соответствует PEP 8 (длина строк ≤ 100 символов)
- [ ] Все функции, методы, публичные переменные имеют аннотации типов
- [ ] Цикломатическая сложность каждой функции ≤ 10
- [ ] Количество строк в каждом файле ≤ 300
- [ ] Код разделён на слои (models, services, repositories, main)
- [ ] Используется Python 3.12

## 3. Обработка ошибок и валидация
- [ ] Входные данные валидируются через Pydantic
- [ ] Пользовательские ошибки возвращают HTTP 4xx с пояснением в `detail`
- [ ] Внутренние ошибки логируются ERROR, возвращают 500 без деталей клиенту
- [ ] Ошибки зависимых сервисов обрабатываются (503 если критично)

## 4. Логирование
- [ ] Используется стандартный модуль `logging`
- [ ] Локальный лог-файл: `01_ЦЕХ/01_ЖУРНАЛЫ/{container_name}.log`
- [ ] Критические действия логируются с уровнем INFO
- [ ] Ошибки логируются с уровнем ERROR
- [ ] Добавлена функция `send_log_to_br18` (см. инструкцию по логированию)
- [ ] Переменные окружения: `ENABLE_BR18=false`, `BR18_URL=http://log-aggregator:8093/api/logs`

## 5. Тестирование
- [ ] Написаны юнит-тесты (минимум 3 сценария на функцию)
- [ ] Написаны интеграционные тесты для каждого нового эндпоинта
- [ ] Если есть недетерминированные сценарии – написаны E2E-тесты с LLM-судьёй
- [ ] Все тесты проходят (`pytest -v`)
- [ ] В тестах замокана отправка логов в BR18

## 6. Документация
- [ ] Обновлён `README.md` (описание, переменные окружения, запуск)
- [ ] Эндпоинты имеют docstring с описанием, параметрами, статусами
- [ ] API-документация доступна по `/docs` (FastAPI Swagger)

## 7. Docker и развёртывание
- [ ] Создан/обновлён `Dockerfile`
- [ ] Создан/обновлён `requirements.txt`
- [ ] Сервис добавлен в `docker-compose.yml` с healthcheck
- [ ] Healthcheck настроен: `test: ["CMD", "curl", "-f", "http://localhost:ПОРТ/health"]`
- [ ] Порт не конфликтует с существующими сервисами

## 8. Проверка чистоты файловой системы (НОВОЕ)
- [ ] **Перед любым деплоем или индексацией:** выполнить проверку через C0.2:
  ```bash
  curl -X POST http://localhost:8192/scan -H "Content-Type: application/json" -d '{"type":"deep"}'
  ```
- [ ] Убедиться, что сканирование не обнаружило незарегистрированных файлов
- [ ] Если обнаружены мусорные файлы – они перемещены в карантин через C0.2
- [ ] Не удалять файлы вручную – только через API C0.2

## 9. Обновление паспортов
- [ ] Обновлён паспорт контейнера (статус: `implemented`, `has_tests: true`, `healthcheck: true`)
- [ ] Обновлён паспорт ветки (если контейнер новый)
- [ ] Версия контейнера указана (например, `version: 1.0`)
- [ ] Поле `memory_indexed: false` (станет true после индексации)

## 10. Индексация в векторную память

  ```bash

    -H "Content-Type: application/json" \

  ```
- [ ] Проверено, что индексация прошла успешно

## 11. Финальные проверки
- [ ] Перегенерирована карта системы:
  ```bash
  curl -X GET "http://localhost:8101/map?refresh=true"
  ```
- [ ] Проверено, что карта показывает корректные поля (`status: implemented`, `has_tests: true`, `healthcheck: true`)
- [ ] Контейнер запускается без ошибок
- [ ] Healthcheck проходит успешно
- [ ] Основные эндпоинты работают

## 12. A/B-тестирование (если применимо)

- [ ] Логирование не обязательно (но желательно)

**Для простых прокси/утилит:**

- [ ] Healthcheck обязателен
- [ ] Логирование по желанию

- [ ] E2E-тесты с LLM-судьёй обязательны и проходят
- [ ] В паспорте установлен `requires_e2e_llm_tests: true`
