## 📄 Методология проектирования: от идеи до архитектуры

**Документ:** ПРОЕКТИРОВАНИЕ_СИСТЕМЫ.md  
**Версия:** 1.0  
**Статус:** Утверждён  
**Область действия:** Этап проектирования (BR9 – Аналитический цех, BR3 – Методология)

---

### 1. Цель документа
Определить единый процесс извлечения смыслов из идеи пользователя и превращения их в иерархическую структуру: **ветки → контейнеры → патчи**. Обеспечить гибкость, позволяющую добавлять новые функции в будущем без перестройки ядра.

---

### 2. Два этапа проектирования

| Этап | Что делаем | Результат |
|------|------------|-----------|
| **1. Сбор требований (L1–L2)** | Опрос пользователя, выявление целей, ограничений, неявных ожиданий, возможных расширений. | Документ **«Замысел проекта»** (L1) и **«Паспорт системы»** (L2) – общее описание, границы, ключевые сущности. |
| **2. Архитектурное проектирование (L3–L4)** | Разбиение системы на ветки (BR), контейнеры (C), определение зависимостей, создание списка патчей. | Паспорта веток (L2), паспорта контейнеров (L3), список патчей с зависимостями (L4). |

---

## 3. Этап 1: Сбор требований – как опрашивать пользователя

### 3.1. Чек-лист опроса (вопросы, которые нужно задать)

| Категория | Вопросы | Примеры ответов |
|-----------|---------|-----------------|
| **Цель и задачи** | 1. Какую основную задачу должно решать приложение?<br>2. Кто будет им пользоваться?<br>3. Какой результат должен получить пользователь в конце? | 1. Создание Telegram-бота для продаж.<br>2. Владельцы малого бизнеса.<br>3. Бот, который продаёт услуги, собирает заявки, ведёт статистику. |
| **Функциональность** | 4. Какие ключевые функции должны быть реализованы?<br>5. Какие функции могут быть добавлены в будущем (но не обязательны сейчас)?<br>6. Есть ли примеры похожих решений? | 4. Регистрация, каталог, оплата, личный кабинет.<br>5. Интеграция с CRM, рассылки.<br>6. Бот «X», сервис «Y». |
| **Ограничения** | 7. Есть ли технические ограничения (платформа, бюджет, время)?<br>8. Требования к безопасности, масштабируемости?<br>9. Должна ли система работать автономно или взаимодействовать с внешними API? | 7. Telegram, Python, бюджет 0$, срок 1 месяц.<br>8. Безопасность: базовая, масштабируемость: 1000 пользователей.<br>9. Только Telegram API. |
| **Данные и хранение** | 10. Какие данные нужно хранить?<br>11. Требуется ли история действий, логи?<br>12. Какой объём данных ожидается? | 10. Пользователи, заказы, товары.<br>11. Да, логи всех действий.<br>12. Несколько тысяч записей. |
| **Расширяемость** | 13. Какие функции планируется добавить позже?<br>14. Нужна ли модульность, чтобы подключать новые модули без переписывания ядра? | 13. Партнёрская программа, веб-панель.<br>14. Да, нужно разделить на независимые модули. |

### 3.2. Принципы опроса
- **Не задавать вопросы, которые можно вывести из контекста** – сначала попросить пользователя описать идею свободно, потом уточнять.
- **Фиксировать не только явные требования, но и неявные** – например, если пользователь говорит «хочу бота», уточнить: «должен ли бот работать 24/7? нужна ли админ-панель?».
- **Выявлять возможные расширения** – спрашивать: «что вы могли бы добавить через полгода?».
- **Создавать диаграммы / списки сущностей** – после опроса нарисовать простую схему: пользователь → бот → база данных → внешние сервисы.

### 3.3. Результат этапа 1 – документ «Замысел проекта» (L1/L2)
- **Название проекта**.
- **Цель и основные функции**.
- **Список ключевых сущностей** (пользователь, заказ, товар, сообщение).
- **Границы** (что система не делает).
- **Потенциальные расширения** (список функций, которые могут быть добавлены позже).
- **Технические ограничения**.

## 4. Этап 2: Архитектурное проектирование – разбиение на ветки

### 4.1. Принцип «ядро + модули»
Система должна быть спроектирована так, чтобы **ядро** (базовые сущности и логика) было стабильным, а новые функции добавлялись как отдельные ветки (модули), которые могут быть подключены без изменения ядра.

**Пример для Telegram-бота:**
- **Ядро (BR1 – Базовые функции)** – регистрация, авторизация, обработка сообщений, хранение пользователей.
- **Ветка BR2 – Каталог** – управление товарами, категориями.
- **Ветка BR3 – Заказы** – оформление, оплата, история.
- **Ветка BR4 – Админ-панель** – веб-интерфейс для управления.
- **Ветка BR5 – Партнёрская программа** (потенциальное расширение).

### 4.2. Алгоритм выделения веток

1. **Выделить ключевые сущности** из замысла.
2. **Сгруппировать функции вокруг сущностей** – каждая группа может стать отдельной веткой.
3. **Определить зависимости** – какие ветки нужны для работы других.
4. **Оценить возможность независимого развития** – может ли ветка быть разработана отдельно, без переписывания ядра.

**Чек-лист для ветки:**
- [ ] Ветка решает одну чёткую задачу (например, «управление каталогом»).
- [ ] Ветка имеет свой паспорт (L2) с описанием ответственности.
- [ ] Ветка использует API ядра (BR1) для доступа к общим данным.
- [ ] Ветка может быть отключена без влияния на другие (если не требуется).

### 4.3. Детализация до контейнеров и патчей

Для каждой ветки:
- **Разбить на контейнеры (C)** – микросервисы или модули, отвечающие за конкретные подзадачи.
- **Для каждого контейнера – список патчей (L4)** – атомарные задачи по реализации.

**Пример для ветки «Каталог»:**
- **C2.1 – Управление товарами** (CRUD, категории).
- **C2.2 – Поиск товаров** (поиск, фильтрация).
- **C2.3 – Интеграция с внешним API** (если товары подгружаются извне).

**Патчи для C2.1:**
- P2.1.1 – Модель товара в БД.
- P2.1.2 – Эндпоинты создания/чтения/обновления товаров.
- P2.1.3 – Валидация данных товара.
- P2.1.4 – Тесты.

### 4.4. Учёт возможных расширений
- **Закладывать интерфейсы (API) для будущих веток** – даже если сейчас модуль не нужен, продумать, как он будет подключаться.
- **Использовать плагинную архитектуру** – например, регистрация хендлеров через декораторы, а не жёсткие вызовы.
- **Документировать расширения** – в паспорте ветки указать, какие точки расширения предусмотрены.

## 5. Итеративность и обратная связь

Проектирование не бывает линейным. В процессе разработки могут появляться новые идеи или обнаруживаться пробелы. Нужно предусмотреть **цикл обратной связи**:

1. **Начальное проектирование** – создание L1–L4.
2. **Разработка первого патча** – тестирование гипотез на практике.
3. **Рефакторинг архитектуры** – если выяснилось, что первоначальное деление на ветки неудобно, можно перераспределить ответственность, но стараться сохранить интерфейсы.
4. **Добавление новых веток** – новые функции оформляются как отдельные ветки, которые подключаются к ядру.

**Чек-лист для проверки архитектуры перед началом разработки:**
- [ ] Каждая ветка имеет чёткую ответственность.
- [ ] Зависимости между ветками минимальны и направлены только от модулей к ядру (не наоборот).
- [ ] Ядро не зависит от модулей.
- [ ] Для каждой ветки определены потенциальные расширения.
- [ ] Существующие патчи не мешают добавлению новых (нет жёстких связей).

## 6. Инструменты и артефакты

| Артефакт | Где хранится | Кто создаёт |
|----------|--------------|-------------|
| **Замысел проекта (L1)** | `01_ЦЕХ/ПРОЕКТЫ/{project_id}/ЗАМЫСЕЛ.md` | Аналитик (Архи) |
| **Паспорт системы (L2)** | `01_ЦЕХ/ПРОЕКТЫ/{project_id}/ПАСПОРТ_СИСТЕМЫ.md` | Архи |
| **Паспорта веток (L2)** | `02_КОНТЕЙНЕРЫ/BR{номер}.md` | Архи |
| **Паспорта контейнеров (L3)** | `02_КОНТЕЙНЕРЫ/BR{номер}_C{номер}.md` | Архи |
| **Список патчей (L4)** | `03_ПАТЧИ/BR{номер}_C{номер}_ПАТЧИ.md` | Архи + Дедал |
| **Спецификации патчей (L5)** | `04_СПЕКИ/` (создаются перед разработкой) | Дедал |

## 7. Рекомендации для ассистентов (промпт)

**Когда ассистент получает задание «спроектировать систему по идее пользователя», он должен:**

1. **Провести опрос по чек-листу** (задавать вопросы из раздела 3.1), фиксируя ответы в документе «Замысел проекта».
2. **На основе ответов выделить сущности и возможные расширения**.
3. **Сформировать список веток (BR)** – каждую ветку описать в паспорте (L2).
4. **Для каждой ветки выделить контейнеры (C)** и описать их в паспортах (L3).
5. **Для каждого контейнера разбить задачи на патчи (L4)** с учётом зависимостей.
6. **Создать спецификации патчей (L5)** только для тех, которые будут разрабатываться в ближайшее время. Остальные оставить как план.
7. **Передать результат на аудит** (пользователю или другому ассистенту).

## 8. Пример использования (краткий)

**Идея:** Сделать Telegram-бота для записи к врачу.

**Опрос:**
- Пользователи: пациенты, врачи.
- Функции: запись на приём, отмена, уведомления, личный кабинет врача (статистика).
- Расширения: онлайн-консультации, интеграция с календарём.

**Выделение веток:**
- **BR1 – Ядро** (пользователи, авторизация, роли).
- **BR2 – Расписание** (слоты, запись, отмена).
- **BR3 – Уведомления** (напоминания).
- **BR4 – Кабинет врача** (статистика, настройки).
- **BR5 – Интеграция с календарём** (потенциальное расширение).

**Контейнеры в BR2:**
- C2.1 – Управление слотами.
- C2.2 – Запись на приём.
- C2.3 – Отмена записи.

**Патчи C2.1:**
- P2.1.1 – Модель слота (БД).
- P2.1.2 – API создания/обновления слотов.
- P2.1.3 – Валидация даты.
- P2.1.4 – Тесты.

## 9. Заключение

Данная методология позволяет **системно подходить к проектированию**, избегая хаотичного добавления функций и переписывания кода. Ключевые принципы:
- **Разделяй ядро и модули.**
- **Проектируй с учётом будущих расширений.**
- **Используй итеративный подход** – корректируй архитектуру по мере появления новых требований.
- **Документируй всё на уровнях L1–L4**, чтобы любой ассистент мог понять структуру.
