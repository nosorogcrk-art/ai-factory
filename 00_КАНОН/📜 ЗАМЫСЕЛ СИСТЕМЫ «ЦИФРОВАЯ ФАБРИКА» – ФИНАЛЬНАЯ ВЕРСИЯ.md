## 1. ГЛОБАЛЬНАЯ ЦЕЛЬ

Создать **автономную платформу**, которая позволяет любому человеку (не программисту) разрабатывать программные продукты, просто описывая свою идею естественным языком (текст, голос, файлы). Платформа сама проектирует, пишет код, тестирует, упаковывает, развёртывает и **непрерывно улучшает себя** на основе обратной связи, анализа собственной работы и **обучения на открытых источниках знаний** (GitHub, техническая документация, статьи, научные публикации, форумы).

**Долгосрочная бизнес-цель** – стать мировым стандартом для создания программного обеспечения, где качество, прослеживаемость и надёжность гарантируются не людьми, а встроенными механизмами контроля (Аргус, Рева, Золотой стандарт).

## 2. КЛЮЧЕВЫЕ ПРИНЦИПЫ

| Принцип | Смысл |
|---------|-------|
| **Автономность** | Система работает без участия профессиональных программистов. Человек только ставит цели, утверждает стратегические изменения и наблюдает за прогрессом через визуальный пульт управления. |
| **Сквозная связность («пуповина»)** | Каждая единица работы (патч, контейнер, строка кода, документ) имеет неразрывную ссылку на первоначальный замысел пользователя. Ни один артефакт не существует без «родителя». |
| **Самообучение и самоулучшение** | Система анализирует свои ошибки и успехи (через логи, метрики, результаты тестов, обратную связь от пользователей) и автоматически улучшает свои промпты, навыки, архитектуру и маркетинговые стратегии. **Дополнительно** – обучается на открытых источниках знаний (GitHub, технические блоги, документация, научные статьи, форумы). |
| **Золотой стандарт** | Все создаваемые системой артефакты (код, документация, тесты, паспорта) должны соответствовать единым высоким стандартам качества: наличие тестов (pytest), статического анализа (mypy, ruff), healthcheck, машиночитаемых паспортов с YAML-шапкой, логирования, обработки ошибок. |
| **Безопасность и изоляция** | Система работает в изолированной Docker-среде, с минимальными привилегиями (запрет `sudo`), с контролем доступа на уровне ролей и обязательным аудитом всех действий агентов. |
| **Модульность и расширяемость** | Система состоит из независимых микросервисов (контейнеров). Каждый контейнер выполняет строго определённую роль и имеет чётко описанный API. Добавление новых функций не требует переписывания ядра. |
| **Пользователь – не программист** | Весь интерфейс (чат, голос, карта, кнопки) должен быть интуитивно понятным человеку, который никогда не работал в терминале. Код, тесты, Dockerfile генерируются системой автоматически и скрыты от пользователя. |
| **Продвижение и самопрезентация** | Система самостоятельно ведёт свои аккаунты в социальных сетях (включая профессиональные сообщества программистов: GitHub, Habr, профильные форумы), генерирует контент (посты, статьи, видео-уроки), анализирует вовлечённость, улучшает маркетинговые стратегии и привлекает новых пользователей, партнёров и сотрудников. |
| **Экономика токенов и стоимость фич** | Система считает затраты (токены, время) на каждую задачу и предоставляет прозрачную отчётность о «цене» каждой фичи. Бизнес-метрики (деньги и время выполнения задач) доступны для анализа. |
| **Продажа доверия, а не кода** | Основной продукт – гарантия качества и прослеживаемости (Continuous Compliance). Система предоставляет аудит, сертификаты соответствия и метрики, которые могут быть предъявлены совету директоров или инвесторам. |
| **Глобальная память и внешнее обучение** | Система не ограничивается своим опытом. Она непрерывно поглощает знания из открытых источников (GitHub, технические блоги, документация, научные статьи, форумы). Этот внешний опыт используется для улучшения навыков, промптов, архитектуры и даже для генерации новых идей. |

## 3. РОЛЕВАЯ МОДЕЛЬ (6 АГЕНТОВ)

Система управляется шестью агентами с чёткими ролями, которые взаимодействуют через API и общий реестр задач.

| Агент | Полномочия | Границы |
|-------|------------|---------|
| **АРГУС** | Обладает правом вето, контролирует соблюдение канонов, назначает задачи, управляет ролями. | Не участвует в написании кода, но может блокировать некорректные действия. |
| **АРХИ** | Проектирует архитектуру, создаёт ТЗ, следит за соответствием стандартам. | Не пишет код, но может предлагать улучшения. |
| **ГЕФЕСТ** | Реализует код строго по ТЗ, обязан писать тесты. | Не проектирует архитектуру, но может предлагать улучшения. |
| **РЕВА** | Проверяет код на соответствие стандартам, возвращает на доработку при нарушениях. | Не пишет код, но может комментировать и требовать исправлений. |
| **ГЕРМЕС** | Обеспечивает инфраструктуру, контролирует порты и безопасность среды. | Не занимается кодом продуктов, но отвечает за Docker и CI/CD. |
| **МНЕМОСИНА** | Ведёт память, индексирует смыслы, анализирует противоречия, обучается на внешних источниках. | Не участвует в разработке, но обеспечивает поиск и аналитику. |

## 4. ПРОТОКОЛ ОПРОСА (ДЕШИФРОВКА ЗАМЫСЛА)

Система не начинает работу, пока не убедится, что полностью поняла задачу. Протокол обязателен для всех новых идей.

### 4.1. Четыре ключевых вопроса (обязательны)

1. **ЗАЧЕМ?** – Какую глобальную проблему решает задача?
2. **ДЛЯ ЧЕГО?** – Какую конкретную пользу получит система после её выполнения?
3. **ЗАМЫСЕЛ?** – Каким видит идеальный результат сам пользователь?
4. **ЛОГИКА?** – Как именно это должно работать «под капотом»?

### 4.2. Документирование «пуповины»

Каждый шаг опроса фиксируется в виде отдельного документа со сквозными ссылками:

1. **Распоряжение** (транскрипт голоса/текст/файл).
2. **Вопросник** (спрос ассистента).
3. **Ответы** (пользователь).
4. **Выводы и замысел** (итоговое понимание задачи).

### 4.3. Песочница (публичное заявление о начале работы)

Перед началом любой работы агент **обязан** в общем чате (или файле `SANDBOX.md`) объявить:

- Какую задачу берёт.
- Какие файлы будет менять.
- Ссылку на замысел.

Это предотвращает конфликты и накапливает опыт для других агентов.

## 5. СИСТЕМА ЗАЩИТЫ (QUADRUPLE GATE)

Четыре обязательных фильтра, через которые проходит каждый патч перед принятием.

| Фильтр | Что проверяет | Кто исполняет |
|--------|---------------|---------------|
| **Reality Check** | Все ли файлы имеют запись в реестре? Нет ли «мусорных» файлов? | C0.2 Reality Observer |
| **Traceability Gate** | Имеет ли каждый патч ссылку на замысел (пуповину)? | C3.4 Citations Agent |
| **Skill Validation Gate** | Используют ли агенты актуальные и протестированные навыки? | C17.4 + C7.4 |
| **Cost/Meaning Counter** | Не превышают ли затраты (токены, время) установленный лимит? | C18.5 Cost Tracker |

## 6. ОСНОВНЫЕ ПРОЦЕССЫ

### 6.1. Приём и дешифровка замысла пользователя

- Пользователь общается через веб-интерфейс (C4.4 Dialogue Console), который поддерживает: текст, голос (Whisper), загрузку файлов, ссылки на GitHub/GitLab.
- Система (C9.4 Dialogue Manager) запускает протокол опроса (п.4).
- Фиксирует цепочку «пуповины».
- Ни одна задача не переходит в стадию проектирования, пока цепочка ссылок не будет замкнута.

### 6.2. Проектирование (превращение замысла в архитектуру)

- Архитектор (Архи) разбивает итоговый замысел на ветки (BR) → контейнеры (C) → патчи (P).
- Результат сохраняется в машиночитаемых паспортах (YAML-шапка + Markdown) и отображается на едином пульте управления (карта).

### 6.3. Реализация (автоматическое написание кода)

- На основе спецификаций L5 система запускает **генератор кода** (C21.1 Code Generator), который пишет код без внешних инструментов.
- Генератор создаёт все файлы контейнера, логирование, обработку ошибок, тесты, Dockerfile, README.
- После генерации код автоматически проверяется на соответствие Золотому стандарту (pytest, mypy, ruff, healthcheck).

### 6.4. Тестирование и упаковка

- Контейнеры передаются в C17.4 Skill Tester и C10.2 Test Stand для полного тестирования.
- При успехе C10.3 Packager упаковывает готовое приложение в дистрибутив (Docker-образы, документация, метаданные о навыках, release notes).

### 6.5. Развёртывание и эксплуатация

- BR20 (CI/CD) автоматически деплоит готовое приложение в целевую среду (локально, на сервере, в облаке).
- После деплоя система мониторит состояние через healthcheck, собирает логи (BR18) и метрики.

### 6.6. Самообновление системы (самообучение)

- BR18 передаёт данные в C19.1 Log Analyzer.
- Log Analyzer выявляет кластеры ошибок, часто встречающиеся проблемы.
- C19.2 Prompt Optimizer и C19.3 Skill Updater генерируют улучшения.
- C19.4 A/B Tester запускает эксперимент (разделение трафика, сбор метрик).
- Если улучшение статистически значимо (p-value < 0.05) и положительно – C20.2 Config Versioning и C20.3 Deployment Executor автоматически деплоят новую версию системы.

### 6.7. Продвижение, маркетинг и самопрезентация

Система самостоятельно занимается своим продвижением, включая работу с **профессиональными сообществами программистов** (GitHub, Habr, профильные форумы), где она может привлекать сторонников, клиентов и сотрудников.

| Функция | Как реализовано |
|---------|------------------|
| **Генерация контента** (C21.4) | Анализирует свои успехи (новые контейнеры, завершённые проекты, успешные тесты) и превращает их в посты, статьи, видео-сценарии. |
| **Публикация в соцсети** (C21.5) | Отправляет посты в Telegram, Twitter, VK, а также в GitHub (README, pinned repos, discussions) и на Habr (публикации статей). |
| **Анализ вовлечённости** (C21.6) | Собирает лайки, репосты, комментарии, переходы по ссылкам, звёзды на GitHub, форки, issues. |
| **Самообучение маркетингу** (C21.7) | На основе аналитики корректирует стиль, темы, частоту постов. |
| **Создание обучающих курсов** (C21.8) | Генерирует уроки, видео-туториалы, FAQ на основе документации и успешных кейсов. |
| **Ведение блога** (C21.9) | Пишет статьи про архитектуру, новые функции, кейсы пользователей. |
| **Привлечение контрибьюторов** | Создаёт issues с меткой `good first issue`, отвечает на вопросы новичков, ревьюит pull request'ы от внешних участников. |

### 6.8. Непрерывное обучение на внешних источниках (глобальная память)

- **C2.4 External Knowledge Collector** регулярно сканирует настроенные источники: GitHub (репозитории по тегам, звёздам, лицензиям), технические блоги (Habr, Medium, Dev.to), официальную документацию, научные статьи (arXiv), форумы (Stack Overflow, Reddit).
- **C2.5 Source Quality Filter** оценивает качество источника (звёзды, рейтинг, авторитетность, свежесть) и решает, добавлять ли данные в память.
- **C2.7 Global Knowledge Updater** (новый контейнер):
  - Периодически забирает новые данные от C2.4.
  - Генерирует эмбеддинги и добавляет их в векторную базу (C2.1).
  - Анализирует, какие новые паттерны, подходы, библиотеки появляются в мире.
  - Передаёт эту информацию в BR19 (самообучение) для генерации улучшений промптов и навыков.
- **Мнемосина** отвечает за балансировку: система не «забывает» старые знания при добавлении новых.

## 8. ЖИВУЧЕСТЬ И ВОССТАНОВЛЕНИЕ (RESILIENCE)

- **Контейнеризация** – каждый сервис в Docker, изоляция сбоев.
- **«Золотой образ» на GitHub** – код на сервере всегда соответствует репозиторию; локальные правки теряются при перезапуске.
- **План «Красная кнопка»** – скрипт `restore_factory.sh`, который за минуту восстанавливает систему из Git.
- **Резервное копирование** – дампы БД каждые 6 часов, синхронизация Obsidian с облаком.
- **Healthcheck и авто-реанимация** – Аргус каждые 5 минут пингует порты; после 3 неудачных попыток – уведомление пользователя.

## 9. ГЛАВНЫЕ МЕТРИКИ УСПЕХА

- **Время от идеи до работающего приложения** – менее 1 часа для 90% типовых задач.
- **Доля успешно прошедших тесты патчей** – не менее 95% (без ручного вмешательства).
- **Процент самообновлений системы** – 100% для некритических улучшений.
- **Количество активных пользователей (непрограммистов)** – целевая аудитория: миллионы.
- **Эффективность маркетинга** – не менее 1000 новых пользователей в месяц без внешнего финансирования на рекламу, за счёт органического роста через профессиональные сообщества.
- **Объём внешних знаний, усвоенных системой** – количество статей, репозиториев, документаций, обработанных за месяц.
- **Прирост качества навыков после обучения на внешних источниках** – измеряется через A/B-тесты.

## 10. НЕПРИКОСНОВЕННЫЕ ПРАВИЛА (ЗАПРЕТЫ)

1. **Никакого кода без спецификации (L5).**
2. **Каждый контейнер должен иметь тесты, healthcheck и паспорт с YAML-шапкой.**
3. **Любое изменение в системе должно быть прослеживаемо до первоначального замысла (пуповина).**
4. **Система не может выполнять команды с привилегиями root (запрет sudo).**
5. **Пользователь не обязан знать языки программирования или работать в терминале.**
6. **Все улучшения системы проходят A/B-тестирование перед деплоем.**
7. **Система не может полагаться на внешние инструменты, которые не являются её частью** (Cline, ручное редактирование кода в VS Code – недопустимы).

### 11.2. Привлечение сообщества через профессиональные соцсети

- **GitHub** – основной канал для программистов: публикация кода, issues, discussions, звёзды, форки. Система сама ведёт репозиторий, отвечает на вопросы, ревьюит pull request'ы.
- **Habr / Dev.to** – публикация статей о внутреннем устройстве системы, успешных кейсах, сравнении с альтернативами.
- **Telegram-канал** – новости, обсуждения, быстрая обратная связь.

Через эти каналы система привлекает:
- **Сторонников** – звёзды, форки, распространение информации.
- **Клиентов** – компании, которым нужна автоматизированная разработка.
