## 📜 Золотой стандарт разработки (ЦИФРОВАЯ ФАБРИКА) – ВЕРСИЯ 5.0 (ПЕРЕРАБОТАННАЯ)

**Статус:** Утверждён  
**Область действия:** Все ветки, контейнеры, патчи (разработка L6 и доработка существующих контейнеров)  
**Версия:** 5.0 (с учётом LLM-судьи, контроля сложности, индексации, E2E-тестов и агентного CI/CD)

---

### 0. Общие принципы (добавлены и усилены)

- **Индексация в векторную память:** каждый артефакт (код, паспорт, спецификация) после создания или изменения **обязательно** индексируется через API C2.6 (`POST /index`). Без индексации артефакт не считается завершённым.
- **LLM-судья для недетерминированных сценариев:** если функциональность контейнера включает неоднозначные или генеративные задачи (выделение ключевых слов, оценка релевантности, ответы LLM), то **обязательны** E2E-тесты с LLM-судьёй.
- **Контроль здоровья кода:**
  - Цикломатическая сложность каждой функции ≤ 10 (проверяется `ruff` или `radon`).
  - Количество строк в одном файле ≤ 300 (проверяется `wc -l`).
- **Агентный CI/CD:** после деплоя изменений, затрагивающих промпты, навыки или критическую логику, запускается A/B-тест (C19.4). При ухудшении метрик – автоматический откат.
- **Единый стандарт для всех контейнеров** (независимо от того, реализован ли агент или используется Cline).

## 1. Кодирование (обязательно)

### 1.1. Язык и стиль
- **Язык:** Python 3.12.
- **Стиль:** PEP 8 (допустима длина строки до 100 символов).
- **Типизация:** все функции, методы, публичные переменные должны иметь аннотации типов.

### 1.2. Структура файлов (для бэкенд-контейнеров) – обязательно

```
container/
├── main.py               # FastAPI приложение, эндпоинты
├── models.py             # Pydantic-модели запросов/ответов
├── services.py           # Бизнес-логика
├── repositories.py       # Работа с БД / файлами
├── utils.py              # Вспомогательные функции
├── tests/
│   ├── test_services.py  # Юнит-тесты (pytest)
│   ├── test_api.py       # Интеграционные тесты (TestClient)
│   └── test_e2e_llm.py   # **E2E-тесты с LLM-судьёй (обязательно для недетерминированных сценариев)**
├── requirements.txt
├── Dockerfile
└── README.md
```

**Исключение:** для статических фронтенд-контейнеров (HTML/JS) структура может быть упрощена, но тесты (Jest) и healthcheck обязательны.

### 1.3. Логирование (обязательно)
- Использовать стандартный модуль `logging`.
- Для каждого контейнера свой лог-файл: `01_ЦЕХ/01_ЖУРНАЛЫ/{container_name}.log`.
- Критические действия (создание, обновление, удаление) логировать с уровнем INFO.
- Ошибки – ERROR.
- При вызове внешних сервисов логировать факт вызова и ответ (хотя бы статус).
- **Логи также отправляются в BR18 (Log Aggregator)** по инструкции `ИНСТРУКЦИЯ_ПО_ЛОГИРОВАНИЮ.md` (см. отдельный документ).

### 1.4. Обработка ошибок (обязательно)
- **Пользовательские ошибки** (неверный ввод, отсутствие ресурса) – возвращать HTTP 4xx с пояснением в поле `detail`.
- **Внутренние ошибки** (БД недоступна, файл не пишется) – логировать ERROR, возвращать 500, не раскрывая детали клиенту.
- **Ошибки зависимых сервисов** – если сервис критичен, возвращать 503; если нет – логировать и продолжать работу.

### 1.5. Контроль здоровья кода (НОВОЕ, ОБЯЗАТЕЛЬНОЕ)
- **Цикломатическая сложность** каждой функции ≤ 10 (измеряется `radon cc -a` или `ruff check --select C901`).
- **Количество строк в одном файле** ≤ 300 (проверяется `wc -l < файл`).
- Проверка выполняется автоматически в CI/CD (BR20) и при локальном запуске `ruff check . --fix`. Если превышает – код должен быть разбит на меньшие функции/модули.

## 2. REST API (обязательно)

### 2.1. Формат ответов
- Все ответы – JSON.
- Успешные операции:
  - `200 OK` – с телом ответа.
  - `201 Created` – с телом созданного ресурса и заголовком `Location`.
- Ошибки: `{ "detail": "Пояснение" }`.

### 2.2. Статусы (обязательно)
- `200` – успех (GET, PATCH, DELETE).
- `201` – создано (POST).
- `400` – ошибка валидации (неверный формат, отсутствие обязательного поля).
- `404` – ресурс не найден.
- `409` – конфликт (например, дубликат имени).
- `500` – внутренняя ошибка сервера.
- `503` – внешний сервис недоступен.

### 2.3. Документация API (рекомендовано)
- Каждый эндпоинт должен содержать docstring с описанием, параметрами, возможными статусами.
- Использовать встроенную документацию FastAPI (OpenAPI).

## 3. Тестирование (обязательно)

### 3.1. Юнит-тесты
- Использовать `pytest`.
- Каждая функция бизнес-логики (`services.py`) должна быть покрыта тестами.
- Тесты должны проверять успешные сценарии и краевые случаи (отсутствие данных, неверный ввод).

### 3.2. Интеграционные тесты
- Для каждого нового эндпоинта написать тест через `TestClient` (FastAPI) или `requests`.
- Проверять статусы, структуру ответа, заголовки.
- Использовать тестовую БД (SQLite :memory:) для изоляции.

### 3.3. E2E-тесты с LLM-судьёй (НОВОЕ, ОБЯЗАТЕЛЬНО ДЛЯ НЕДЕТЕРМИНИРОВАННЫХ СЦЕНАРИЕВ)
- **Когда обязательны:** если функциональность контейнера включает недетерминированные сценарии, например:
  - Выделение ключевых слов в тексте (разные варианты форматирования).
  - Генерация ответа LLM (разные формулировки).
  - Проверка релевантности (поиск в памяти).
  - Кластеризация или классификация с нечётким результатом.
- **Как писать:** в папке `tests/test_e2e_llm.py` создать тесты, которые:
  - Вызывают реальный API контейнера (или функцию) с тестовыми данными.
  - Получают ответ.
  - Передают запрос и ответ LLM-судье (например, через вызов C19.2 Prompt Optimizer или прямого LLM API) с заданными критериями оценки.
  - Судья возвращает `{"score": 0-1, "comment": "...", "passed": true/false}`.
  - Тест считается пройденным, если `score >= 0.8` (порог может быть изменён в спецификации патча).
- **Пример критериев для судьи:** «Правильно ли выделено ключевое слово жирным?», «Соответствует ли ответ ожидаемому формату?», «Содержит ли ответ хотя бы одно ключевое слово?».
- **Интеграция:** тесты с LLM-судьёй запускаются в CI/CD отдельно (могут быть медленнее) и не должны блокировать быструю итерацию, но **обязательны перед финальным релизом контейнера**.

### 3.4. Запуск тестов (обязательно)
- Перед сдачей патча запустить `pytest -v`. Все тесты должны проходить (юнит, интеграционные, E2E-LLM).
- Для фронтенд-контейнеров – запустить `npm test` (Jest).

## 5. Процесс разработки патча (L5) – обязательные критерии приёмки (DoD)

Перед сдачей патча **все пункты должны быть выполнены**. Если хотя бы один обязательный пункт не выполнен – патч не принимается, возвращается на доработку.

- [ ] **Код разделён на слои** (models, repositories, services, main) – для бэкенда.
- [ ] **Написаны юнит-тесты** (минимум 3 сценария).
- [ ] **Написаны интеграционные тесты** для каждого нового эндпоинта.
- [ ] **Если есть недетерминированные сценарии – написаны E2E-тесты с LLM-судьёй** (раздел 3.3) и они проходят.
- [ ] **Все ошибки обработаны** и возвращают корректный HTTP-статус.
- [ ] **Входные данные валидируются** через Pydantic (где применимо).
- [ ] **Логирование** всех критических операций (INFO/ERROR).
- [ ] **Код проверен `mypy`** без ошибок.
- [ ] **Код проверен `ruff`** без ошибок (включая проверку цикломатической сложности `C901`).
- [ ] **Цикломатическая сложность каждой функции ≤ 10** (проверяется `ruff` или `radon`).
- [ ] **Количество строк в каждом файле ≤ 300** (проверяется `wc -l`).
- [ ] **Тесты проходят** (`pytest -v`, включая E2E-LLM).
- [ ] **README.md** обновлён (если контейнер новый или изменился API).
- [ ] **Healthcheck** настроен в `docker-compose.yml` (для всех HTTP-сервисов).
- [ ] **Индексация:** после завершения патча вызван API `POST /index` у C2.6 Project Memory для всех новых или изменённых файлов (паспорт, код, спецификации). Команда для индексации приведена в разделе 6.
- [ ] **Если контейнер имеет флаг `requires_e2e_llm_tests: true` в паспорте, E2E-тесты с LLM-судьёй обязательны и должны проходить.**

**Исключения:** для фронтенда допускается отсутствие `mypy`/`ruff`, но обязательны тесты (Jest) и разделение на файлы (HTML, CSS, JS).

## 6. Финальный шаг после завершения кода и тестов (ОБЯЗАТЕЛЬНО)

После того как код написан, тесты прошли, статический анализ выполнен, **ты обязан выполнить следующие действия**. Без них контейнер НЕ СЧИТАЕТСЯ ГОТОВЫМ.

### 6.1. Обновить паспорт контейнера
В файле паспорта контейнера (`/data/projects/{project_id}/containers/C-*.md` или в заводской папке `BR*/C*/*.md`) в YAML-шапке проставить:

```yaml
status: implemented
has_tests: true
healthcheck: true
version: 1.0
memory_indexed: false   # станет true после индексации
# Если контейнер требует LLM-судью:
requires_e2e_llm_tests: true   # если паспорт ветки или контейнера требует
```

### 6.2. Добавить сервис в `docker-compose.yml` с healthcheck (если ещё не добавлен)
```yaml
healthcheck:
  test: ["CMD", "curl", "-f", "http://localhost:ПОРТ/health"]
  interval: 30s
  timeout: 5s
  retries: 3
```

### 6.3. Перегенерировать карту системы
```bash
curl -X GET "http://localhost:8101/map?refresh=true"
```

### 6.4. Проверить, что карта показывает корректные поля
```json
{
  "status": "implemented",
  "has_tests": true,
  "healthcheck": true
}
```

### 6.5. Выполнить индексацию в векторную память (НОВОЕ, ОБЯЗАТЕЛЬНОЕ)
Для проекта (если контейнер относится к проекту):
```bash
curl -X POST "http://localhost:8108/api/project/{project_id}/index" \
  -H "Content-Type: application/json" \
  -d '{"documents": ["/data/projects/{project_id}/containers/C-*.md", "/data/projects/{project_id}/specs/P-*.md"]}'
```
Если контейнер часть завода (BR0–BR20), используйте путь к паспорту:
```bash
curl -X POST "http://localhost:8108/api/index" \
  -H "Content-Type: application/json" \
  -d '{"documents": ["/Users/a1/Dev/ЗАВОД_АГЕНТОВ/ai-factory/BR1/C1.2/C1.2.md"]}'
```

### 6.6. Запустить A/B-тестирование (если применимо)
- Если изменения затрагивают промпты, навыки, критическую логику или алгоритмы, после деплоя **обязательно** запустить A/B-тест через C19.4 (по отдельному заданию).
- Для этого использовать API `POST /experiment` на C19.4 A/B Tester (см. документацию BR19).

**Если хотя бы один из этих пунктов не выполнен – контейнер не принимается, работа не считается завершённой.**

## 7. Политика чистоты (НОВОЕ, ОБЯЗАТЕЛЬНОЕ)

Для поддержания чистоты файловой системы завода и предотвращения включения мусорных файлов в продукты и индексы:

### 7.1. Обязательная проверка перед сборкой и индексацией
- Перед сборкой продукта (C10.3 Packager) или индексацией артефактов **обязательно** запустить `deep_scan` через C0.2 Reality Observer.
- Цель: убедиться, что в файловой системе нет незарегистрированных файлов.

### 7.2. Обработка обнаруженного мусора
- Если обнаружены незарегистрированные файлы – они должны быть автоматически перемещены в карантин (`01_ЦЕХ/05_КАРАНТИН/`).
- Мусорные файлы **не должны** включаться в продукт или индекс.
- Записи о карантинированных файлах добавляются в `SYSTEM_REGISTRY.json` с меткой `quarantined: true`.

### 7.3. Правила для разработчиков
- Разработчик (Cline, Гефест) не должен вручную удалять файлы – только через API C0.2.
- Перед любым деплоем или индексацией необходимо выполнить проверку:
  ```bash
  curl -X POST http://localhost:8192/scan -H "Content-Type: application/json" -d '{"type":"deep"}'
  ```
- Убедиться, что сканирование не обнаружило незарегистрированных файлов, или что они были перемещены в карантин.

### 7.4. Автоматическая очистка карантина
- Файлы в карантине автоматически удаляются через 7 дней.
- Очистка выполняется фоновой задачей C0.2 (раз в сутки).
- Вручную очистку можно запустить через API:
  ```bash
  curl -X DELETE http://localhost:8192/quarantine/clean -H "Content-Type: application/json" -d '{"days":7}'
  ```

## 8. Агентный CI/CD (дополнительно, но рекомендовано для критичных изменений)

После успешного деплоя контейнера (или набора патчей) через BR20, система (или вы вручную, пока агенты не реализованы) должна:

1. **Запустить smoke-тесты** (быстрая проверка healthcheck и основных эндпоинтов).
2. **Если есть изменения в промптах, навыках или критической логике** – запустить A/B-тест (C19.4) на части трафика (например, 10% пользователей).
3. **Собрать метрики** через BR18 (логи, ошибки, задержки) в течение заданного времени (например, 1 час).
4. **Если улучшение статистически значимо (p-value < 0.05)** – развернуть на 100% трафика и заархивировать старую версию.
5. **Если ухудшение** – автоматически откатить до предыдущей версии (через C20.3 Deployment Executor) и уведомить администратора (Аргуса).

Этот процесс описан в отдельном протоколе CI/CD, но каждый разработчик (Cline, будущий Гефест) должен быть готов к тому, что его изменения могут пройти A/B-тест.

## 8. Заключение

Данный стандарт обязателен для всех контейнеров и патчей, создаваемых или дорабатываемых в системе «Цифровая Фабрика». Патчи, не соответствующие обязательным требованиям, подлежат отклонению.

**Ключевые нововведения версии 5.0:**
- E2E-тесты с LLM-судьёй для недетерминированных сценариев.
- Контроль цикломатической сложности (≤10) и максимального числа строк (≤300).
- Обязательная индексация всех артефактов в векторную память (C2.6).
- Агентный CI/CD с A/B-тестированием для критичных изменений.
