## 1. Введение

### 1.1. Цель документа

Данный документ описывает **второй этап** проектирования системы: превращение формализованного замысла (L2) в **ветки (BR)**. Ветки — это крупные функциональные блоки, которые определяют архитектуру системы на стратегическом уровне.

Этот протокол является прямым продолжением **«Технологии опроса» (L1 → L2)**. Если замысел ещё не сформирован, система должна сначала пройти этап опроса пользователя.

### 1.2. Место в общем процессе проектирования

| Уровень | Что делаем | Результат | Кто выполняет |
|---------|-----------|-----------|---------------|
| **L1** | Сбор требований, опрос пользователя | `ЗАМЫСЕЛ.md` | C9.4 |
| **L2** | Формализация в паспорт системы | `ПАСПОРТ_СИСТЕМЫ.md` | C9.4 + C1.2 |
| **L3** | Выделение веток (BR) | Паспорта веток | **C1.2** |
| **L4** | Разбиение веток на контейнеры | Паспорта контейнеров | C1.2 |
| **L5** | Разбиение контейнеров на патчи | Список патчей с зависимостями | C1.2 |
| **L6** | Реализация (код, тесты, Docker) | Код в контейнерах | C21.1 / Cline |

### 1.3. Что такое ветки (BR) и зачем они нужны

Ветка (BR — Branch) — это крупный функциональный блок системы, соответствующий **ограниченному контексту (Bounded Context)** в терминах Domain-Driven Design.

**Назначение веток:**
- Ограничивают сложность (своя модель данных, язык).
- Определяют команду (кто отвечает за ветку).
- Позволяют параллельную разработку.
- Служат основой для выделения контейнеров.
- Защищают от «большого взрыва» – развитие постепенно.

**Важно:** Выделение ограниченных контекстов — стратегическое решение, требующее вовлечения пользователя. Ни один алгоритм не может сделать это идеально без человека.

## 3. Теоретическая основа

### 3.1. Основные источники кандидатов в ветки

| Источник | Описание | Пример |
|----------|----------|--------|
| Ключевые бизнес-сущности | Главные «объекты» | Пользователь, аккаунт, сообщение |
| Основные функции | Действия системы | Мониторинг, репост, статистика |
| Внешние интеграции | Сторонние системы | Telegram API, платёжный шлюз |
| Пользовательские роли | Разные сценарии | Администратор, менеджер |
| Бизнес-процессы | Сквозные потоки | «От заявки до оплаты» |
| Границы ответственности | Разные отделы | Отдел продаж, разработки |

### 3.2. Ключевые критерии хорошей ветки

1. **Чёткая граница** – понятно, что входит, а что нет.
2. **Связность (cohesion)** – всё внутри тесно связано.
3. **Слабая связанность (low coupling)** – минимальные зависимости.
4. **Независимое развитие** – можно разрабатывать отдельно.
5. **Соответствие MVP** – достаточно маленькая для 1–3 спринтов.

### 3.3. Типичные ошибки

- Слишком крупная ветка (всё про Telegram в одной).
- Слишком мелкая ветка (форматирование даты).
- Циклические зависимости.
- Пересекающиеся данные (нарушение единого языка).

## 4. Алгоритм выделения веток (пошагово)

### 4.1. Предварительный анализ L2

C1.2 анализирует L2 и извлекает кандидатов в ветки из разделов (в порядке приоритета):

**4.1.1.** Раздел «Ветки и контейнеры» (если есть) – пользователь сам предложил структуру.  
**4.1.2.** Раздел «Основные функции» – каждая функция как кандидат.  
**4.1.3.** Раздел «Целевая аудитория и роли» – разные роли → разные сценарии.  
**4.1.4.** Раздел «Технические требования» – внешние интеграции.  
**4.1.5.** Раздел «Данные и сущности» – ключевые сущности.

**Результат:** черновой список веток (10–15 штук).  
**Пример для TG Keyword Monitor:**

| Источник | Кандидат в ветку |
|----------|------------------|
| Основные функции | Управление аккаунтами, Мониторинг групп, Фильтрация сообщений, Репост, Статистика |
| Роли | Администратор, Конечный пользователь |
| Интеграции | Telegram User API, Telegram Bot API |
| Сущности | Аккаунт, Группа, Ключевое слово, Сообщение |

### 4.2. Группировка кандидатов по смыслу

**4.2.1.** Система группирует кандидатов на основе связности данных, процессов, ответственности.

**Пример группировки для TG Keyword Monitor:**

| Группа | Кандидаты | Итоговая ветка |
|--------|-----------|----------------|
| Аккаунты, сессии, авторизация | Управление аккаунтами, Telegram User API, Аккаунт | BR-TG-1: Управление аккаунтами |
| Чтение, фильтрация, ключевые слова | Мониторинг групп, Фильтрация сообщений, Ключевое слово, Сообщение | BR-TG-2: Мониторинг и фильтрация |
| Отправка, форматирование | Репост в канал, Telegram Bot API | BR-TG-3: Репост и форматирование |
| Статистика, дашборд, отчёты | Статистика, Администратор | BR-TG-4: Дашборд и статистика |

### 4.3. Поиск похожих веток в векторной памяти

**4.3.1.** C1.2 формирует поисковый запрос из описаний кандидатов в ветки.  
**4.3.2.** Выполняет семантический поиск в:
- Векторной памяти текущего проекта (C2.3, `POST /api/search`).
- Глобальной памяти завода (BR2).
- Библиотеке эталонных решений (BR14 Showroom, `GET /api/showroom/search`).

**4.3.3.** Если найдены ветки с похожим описанием (score > 0.7), система сохраняет их как предложения (поле `suggested_reuse`).  
**4.3.4.** В диалоге с пользователем (шаг 4.4) система спросит, хочет ли он использовать готовую структуру.

### 4.4. Подготовка к диалогу с пользователем

**4.4.1.** Сформировать предварительный список веток (результат группировки).  
**4.4.2.** Подготовить:
- Краткое объяснение, что такое ветки (простым языком).
- Визуализацию (список или схема).
- Вопросы для обсуждения (см. раздел 5).

### 4.5. Диалог с пользователем для уточнения и утверждения веток

**Цель диалога:** помочь пользователю понять ветки, определить MVP, выявить большие ветки, утвердить окончательный список.

**Структура диалога (обязательные этапы):**

**4.5.1. Объяснение концепции веток (1–2 минуты)**  
> «Ветки — это крупные функциональные блоки вашего приложения. Например, для интернет-магазина ветками могут быть «Каталог товаров», «Корзина и заказы», «Пользователи и профили», «Администрирование». Каждая ветка будет разрабатываться отдельно, и мы можем делать их по очереди. Это позволит вам видеть результат быстрее и менять приоритеты по ходу дела.»

**4.5.2. Показ предварительного списка веток**  
> «На основе вашего описания я выделил такие ветки: [список]. Посмотрите, пожалуйста. Всё ли здесь правильно? Нет ли лишних? Не упустили ли мы что-то важное?»

**4.5.3. Уточнение приоритетов (MVP)**  
> «Теперь давайте определим приоритеты. Какие из этих веток нужны вам в первую очередь? Что вы хотите получить через 2–3 недели? Что можно сделать позже — через месяц, через полгода?»

| Категория | Описание | Действие |
|-----------|----------|----------|
| Критично для MVP | Без этого ветка не имеет смысла | Включить в активный план |
| Важно, но можно позже | Нужно, но не в первой версии | Отложить, статус `planned` |
| Расширение / когда-нибудь | Идеи на будущее | Сохранить в L2, паспорт не создавать |

**4.5.4. Обсуждение размера веток и потенциального расширения**  
> «Ветка X выглядит очень большой. Может, её разбить на две? Например, отдельно «Управление аккаунтами» и «Управление сессиями»?»  
> «Ветка Y, наоборот, маленькая. Может, объединить её с веткой Z?»  
> «Какие из этих веток, по вашему мнению, будут дорабатываться и расширяться в будущем? Нужно ли закладывать в них масштабируемость?»

**4.5.5. Фиксация итогового списка**  
Система запоминает:
- Активные ветки (для MVP) – будут созданы паспорта.
- Отложенные ветки – сохраняются в L2 с пометкой `planned`.
- Расширения – в L2 как «потенциальные расширения».

**4.5.6. Fallback при отсутствии ответа пользователя:**  
Если пользователь не отвечает в течение 10 минут, система сохраняет текущий прогресс (черновик веток) и закрывает сессию. При следующем заходе предлагает продолжить.

### 4.6. Аудит веток с LLM-судьёй

**4.6.1.** После диалога, но до создания паспортов, C1.2 вызывает LLM-судью (см. Приложение А для промпта).  
**4.6.2.** Судья проверяет предварительный список веток по критериям:
- Полнота покрытия L2 – все ли ключевые функции отражены.
- Отсутствие дублирования – нет двух веток с одинаковым смыслом.
- Оценка сложности (small/medium/large) – на основе количества подфункций и внешних зависимостей.
- Недетерминированные зоны – если в описании ветки есть неоднозначность (например, «оповещать пользователя» – как именно?), судья формирует уточняющие вопросы.
- Риски – например, сильная связь с другой веткой, отсутствие внешнего API.

**4.6.3.** Результат сохраняется в `/data/projects/{project_id}/АУДИТ_ВЕТОК_ОТЧЕТ.md`.  
**4.6.4.** Если есть замечания, система задаёт уточняющие вопросы пользователю (максимум 5 итераций).  
**4.6.5.** Если список веток идеален – переход к шагу 4.7.

**4.6.6. Обработка ошибок LLM-судьи:**  
- При таймауте (30 сек) или некорректном JSON – повторить 2 раза.
- После 3 неудач – пропустить, но пометить в отчёте, требуется ручная проверка.

### 4.7. Создание паспортов веток

Для каждой активной ветки C1.2 создаёт паспорт **в папке проекта** по пути:  
`/data/projects/{project_id}/branches/BR-{project_abbr}-{number}.md`

**Шаблон паспорта ветки (YAML + Markdown):**

```yaml
---
id: BR-TG-1
responsible: [назначить]
status: active
name: Управление аккаунтами
description: Добавление, удаление, хранение Telegram-аккаунтов. Включает авторизацию через номер телефона, управление сессиями, шифрование session-файлов.
containers: []   # заполняется на L4
priority: high   # high / medium / low
estimated_complexity: medium   # small / medium / large
requires_e2e_llm_tests: false
max_complexity_cyclomatic: 10
max_lines_per_file: 300
memory_indexed: false
dependencies: []   # список ID других веток, если есть
---
# Ветка BR-TG-1: Управление аккаунтами

## Функции
- Добавление аккаунта через номер телефона (авторизация, код).
- Получение статуса аккаунта (активен / ошибка / флуд).
- Приостановка / возобновление мониторинга.
- Удаление аккаунта.

## Зависимости от других веток
- (нет)

## Зависимости от внешних систем
- Telegram User API

## Планируемые контейнеры (L4)
- (будет заполнено позже)
```

**Пояснение полей:**
- `id` – уникальный, формат `BR-{abbr}-{number}`.
- `status` – active / planned / future.
- `containers` – заполняется на этапе L4.
- `requires_e2e_llm_tests` – true, если в ветке есть недетерминированные сценарии.
- `max_complexity_cyclomatic` – лимит цикломатической сложности.
- `max_lines_per_file` – лимит строк на файл.
- `dependencies` – список ID веток, от которых зависит данная (если есть).

### 4.8. Обновление L2

**4.8.1.** Система обновляет `ПАСПОРТ_СИСТЕМЫ.md` (в папке проекта), добавляя раздел **«Утверждённые ветки»** со списком веток, их статусом, приоритетом и кратким описанием.  
**4.8.2.** Также в L2 сохраняется информация об отложенных ветках и расширениях для будущих версий.  
**4.8.3.** Обновлённый L2 сохраняется с увеличением версии (например, `ПАСПОРТ_СИСТЕМЫ_v2.md`).

### 4.9. Индексация в векторную память проекта

**4.9.1.** После успешного аудита и создания паспортов C1.2 вызывает API индексации (C2.6 Project Memory):  

```bash
curl -X POST "http://localhost:8108/api/project/{project_id}/index" \
  -H "Content-Type: application/json" \
  -d '{
    "documents": [
      "/data/projects/{project_id}/branches/BR-TG-1.md",
      "/data/projects/{project_id}/branches/BR-TG-2.md",
      "/data/projects/{project_id}/branches/BR-TG-3.md"
    ]
  }'
```

**4.9.2.** API возвращает `{ "status": "ok", "indexed_count": N }`.  
**4.9.3.** Если индексация не удалась (ошибка, таймаут), система повторяет 3 раза.  
**4.9.4.** После 3 неудач – паспорта помечаются `memory_indexed: false`, создаётся задача в handover для ручной индексации. Переход к L4 блокируется.

### 4.10. Передача на следующий этап

После утверждения веток и индексации управление передаётся **C1.2 Patch Architect** для этапа L4 (выделение контейнеров) по протоколу `ПРОТОКОЛ_КОНТЕЙНЕРЫ.md`.

## 5. Структура диалога с пользователем (детальный чек-лист вопросов)

### 5.1. Вводные вопросы

- «Вы когда-нибудь сталкивались с понятием «модули» или «компоненты» в разработке? Ветки — это примерно то же самое, только на более высоком уровне.»  
- «Давайте посмотрим на предварительный список веток, который я подготовил на основе вашего описания. [показать список] Всё ли здесь правильно?»

### 5.2. Уточнение состава веток

- «Какие из этих веток для вас самые важные? Без каких веток приложение не имеет смысла?»  
- «Есть ли ветки, которые можно объединить? (например, потому что они очень маленькие или тесно связаны)»  
- «Есть ли ветки, которые нужно разбить на две или более? (например, потому что они слишком большие)»  
- «Не упустили ли мы какую-то важную функцию, которая должна быть отдельной веткой?»

### 5.3. Определение приоритетов (MVP vs потом)

- «Что вы хотите получить в первую очередь? (через 2–3 недели)»  
- «Что можно сделать во вторую очередь? (через 1–2 месяца)»  
- «Что будет нужно, но не срочно? (через полгода или позже)»  
- «Какие функции являются «хотелками», без которых вы готовы обойтись в первой версии?»

### 5.4. Обсуждение размера и сложности

- «Ветка X выглядит очень большой. Какие под-функции в ней самые сложные?»  
- «Ветка Y, наоборот, очень маленькая. Может, её объединить с соседней веткой?»  
- «Какие ветки, по вашему мнению, будут дорабатываться и расширяться в будущем? (чтобы мы сразу заложили архитектуру с запасом)»

### 5.5. Фиксация решений

- «Давайте зафиксируем итоговый список веток для первой версии: [список]»  
- «Вот список веток, которые мы откладываем на потом: [список]»  
- «Вот список идей, которые мы пока не оформляем в ветки, но запомним: [список]»  
- «Утверждаем?»

## 6. Аудит существующего замысла (если проект уже описан)

Если пользователь приходит с уже существующим проектом (есть паспорта веток, контейнеров, патчей или даже код), система не должна слепо доверять ему. Она обязана провести **быстрый аудит** на наличие пробелов, противоречий и несоответствий.

### 6.1. Когда запускается аудит

- Пользователь загружает готовый проект (папку с L1/L2/L3/L4/L5 или код).  
- Пользователь говорит «у меня уже есть техзадание, просто реализуйте».  
- После того как система сгенерировала L2 на основе опроса (дополнительная проверка).

### 6.2. Алгоритм аудита

**6.2.1.** Загрузить существующие артефакты проекта – `ПАСПОРТ_СИСТЕМЫ.md`, паспорта веток, паспорта контейнеров, патчи (L4, L5), код (L6).  
**6.2.2.** Сравнить их с эталонной структурой (раздел 2 «Технологии опроса»).  
**6.2.3.** Выявить, какие блоки не раскрыты или раскрыты не полностью.  
**6.2.4.** Проверить на противоречия:
- Масштаб: в L2 указано «2 пользователя», а в патчах есть балансировщик нагрузки.  
- Технологии: в L2 указана бесплатная БД, а в коде платная.  
- Функции: в L2 «простой бот», а в патчах сложная админ-панель.  
- Статусы: паспорт ветки `implemented`, а код отсутствует.

**6.2.5.** По каждому пробелу задать уточняющий вопрос («для полноты картины, уточните...»).  
**6.2.6.** Если противоречия найдены, зафиксировать в `АУДИТ_ОТЧЕТ.md` и запросить решение.  
**6.2.7.** После уточнений обновить L2 и паспорта веток, сохранить новую версию.  
**6.2.8.** Запустить LLM-судью для дополнительной валидации.

**6.2.9. Fallback:** Если пользователь не отвечает 3 дня – напоминание в Telegram. Ещё 3 дня – архив.

### 6.3. Примеры вопросов при аудите

- «В вашем описании сказано, что система для двух пользователей, но в коде есть балансировщик нагрузки. Это ошибка или вы планируете рост?»  
- «Вы указали, что база данных SQLite, но в коде используются PostgreSQL-специфичные запросы. Что правильно?»  
- «Ветка X помечена как `implemented`, но код для неё отсутствует. Нужно её реализовать или поменять статус?»

## 7. Чек-лист аудитора (Рева) для приёмки этапа L3

Аудитор (Рева) получает папку проекта и проверяет **бинарно** (ДА/НЕТ). Если любой пункт = НЕТ – этап не пройден.

### 7.1. Формальная проверка

- **F-B1:** В папке `/data/projects/{project_id}/branches/` присутствуют паспорта всех активных веток.  
- **F-B2:** Каждая ветка имеет уникальный ID `BR-{abbr}-{number}`.  
- **F-B3:** В паспорте заполнены все поля: `id, responsible, status, name, description, containers, priority, estimated_complexity, requires_e2e_llm_tests, max_complexity_cyclomatic, max_lines_per_file, memory_indexed, dependencies`.  
- **F-B4:** В `ПАСПОРТ_СИСТЕМЫ.md` добавлен раздел «Утверждённые ветки».

### 7.2. Содержательная проверка

- **C-B1:** Описание каждой ветки чёткое (нет «возможно», «например»).  
- **C-B2:** Ветки не пересекаются по функциональности.  
- **C-B3:** Все ключевые функции из L2 покрыты хотя бы одной веткой.  
- **C-B4:** Нет циклических зависимостей (если указаны в `dependencies`).  
- **C-B5:** Для веток `estimated_complexity: large` установлен `requires_e2e_llm_tests: true` (или обоснование).

### 7.3. Проверка аудита LLM-судьёй

- **C-B6:** Файл `АУДИТ_ВЕТОК_ОТЧЕТ.md` существует.  
- **C-B7:** Все замечания судьи исправлены или пользователь дал пояснения.  
- **C-B8:** Для каждой недетерминированной зоны сформулированы конкретные правила.  
- **C-B9:** Если судья был недоступен – пометка и подтверждение ручной проверки.

### 7.4. Проверка индексации

- **I-B1:** Выполнена индексация всех паспортов веток в векторную память.  
- **I-B2:** API индексации вернул `status: ok`.  
- **I-B3:** Поле `memory_indexed` в каждом паспорте ветки = `true`.  
- **I-B4:** Если индексация не удалась – создана задача в handover.

### 7.5. Проверка fallback’ов

- **F-B1:** При отсутствии ответа пользователя прогресс сохранён и восстановлен.  
- **F-B2:** Таймауты LLM-судьи обработаны корректно (не более 3 попыток).  
- **F-B3:** Если пользователь отвечал «не знаю» на вопросы о ветках – предложены варианты.

### 7.6. Итоговое решение

Если все пункты = ДА → **ПРИНЯТО**, переход к L4.  
Если хотя бы один = НЕТ → **ОТКЛОНЕНО** с указанием нарушений.

## 8. Хранение результатов проектирования

Все артефакты хранятся **в папке проекта**: `/data/projects/{project_id}/`

**Состав:**

| Файл | Описание |
|------|----------|
| `РАСПОРЯЖЕНИЕ.md` | Исходная идея |
| `ВОПРОСНИК.json` | Все заданные вопросы |
| `ОТВЕТЫ.json` | Ответы пользователя |
| `ЗАМЫСЕЛ.md` | L1 |
| `ПАСПОРТ_СИСТЕМЫ.md` | L2 (обновляется) |
| `АУДИТ_ВЕТОК_ОТЧЕТ.md` | Отчёт LLM-судьи |
| `branches/BR-*.md` | Паспорта веток |

**Правило:** каждый раз после изменения структуры веток (утверждение, правка) система обновляет `ПАСПОРТ_СИСТЕМЫ.md` и переиндексирует изменённые паспорта.

## 9. Приложение А: Пример системного промпта для LLM-судьи (для веток)

```text
Ты — эксперт по архитектуре программного обеспечения (Domain-Driven Design).  
Твоя задача — проверить список веток (BR), полученный из L2, на полноту, непротиворечивость и выявить риски.

Входные данные:
- Паспорт системы L2 (вставь содержимое)
- Предварительный список веток (вставь список)

Оцени по критериям (ответь JSON):

1. completeness_score (1-5): насколько список веток покрывает все ключевые функции L2?
2. duplicates (массив): какие ветки дублируют друг друга?
3. missing_functions (массив): какие функции из L2 не отражены ни в одной ветке?
4. oversized_branches (массив): какие ветки выглядят слишком большими (стоит разбить)?
5. undersized_branches (массив): какие ветки слишком мелкие (стоит объединить)?
6. risks (массив): риски (связность, внешние зависимости, отсутствие API).
7. questions_to_user (массив): уточняющие вопросы.

Формат ответа:
{
  "completeness_score": 4,
  "duplicates": [],
  "missing_functions": ["функция X"],
  "oversized_branches": ["BR-TG-2"],
  "undersized_branches": ["BR-TG-4"],
  "risks": ["BR-TG-2 сильно зависит от внешнего Telegram API, нет fallback"],
  "questions_to_user": ["Какую статистику вы хотите видеть в дашборде?"]
}
```
