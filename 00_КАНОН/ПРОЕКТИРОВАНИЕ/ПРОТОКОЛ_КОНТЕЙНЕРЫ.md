## 1. Назначение документа

Этот документ описывает **третий этап проектирования**: превращение утверждённой ветки (BR) в набор контейнеров (C) — микросервисов или модулей, каждый из которых отвечает за чётко определённую подзадачу внутри ветки.

**Вход:** Паспорт ветки (BR-{id}.md) с утверждённым описанием, а также общий L2 (Паспорт системы) – **оба документа лежат в папке проекта**.

**Выход:** Паспорта контейнеров (C-{id}.md) с YAML-шапкой, описанием, портами, зависимостями, а также **индексация всех созданных артефактов в векторную память проекта**.

**Аудитор (Рева)** проверяет результат по чек-листу (раздел 6) и утверждает или отклоняет переход к следующему этапу (нарезка на патчи).

## 2. Что такое контейнер и как его выделять

### 2.1. Определение контейнера

**Контейнер (C)** — это минимальный функциональный модуль, который:

- Может быть реализован как отдельный микросервис (Docker-контейнер).
- Имеет чёткую ответственность (одна задача).
- Имеет свой API (если публичный) или внутренний интерфейс.
- Может быть протестирован отдельно.
- Может быть заменён на другую реализацию без изменения других контейнеров (слабая связанность).

**Контейнер ≠ патч.** Контейнер — это логическая единица, которая будет разбита на несколько патчей на следующем этапе.

### 2.2. Принципы выделения контейнеров (мировой опыт)

Основано на Domain-Driven Design (DDD), принципах микросервисной архитектуры и практике декомпозиции.

| Принцип | Описание | Пример нарушения |
|---------|----------|------------------|
| **Единство ответственности** | Контейнер отвечает за одну функциональную область. | Контейнер, который и читает сообщения, и отправляет их. |
| **Независимость данных** | Каждый контейнер владеет своими данными. Другие получают доступ через API. | Два контейнера пишут в одну таблицу БД напрямую. |
| **Слабая связанность** | Зависимости минимизированы и явно определены (через API, очереди). | Контейнер A вызывает метод контейнера B синхронно и ждёт ответа. |
| **Сильная связность внутри** | Внутри контейнера всё тесно связано по смыслу. | Контейнер содержит и логику аккаунтов, и логику статистики. |
| **Независимое развёртывание** | Контейнер может быть развёрнут отдельно (хотя в MVP возможны исключения). | Контейнер не может стартовать без другого контейнера. |
| **Ориентация на бизнес-функции** | Контейнер = «управление аккаунтами», а не «база данных». | Контейнер «база данных» – антипаттерн. |

### 2.3. Типовые контейнеры (паттерны)

- **API Gateway** – единая точка входа для внешних запросов.
- **Сервис обработки** – реализует бизнес-логику.
- **Воркер (Listener)** – слушает очередь, канал (например, Telegram updates).
- **Хранилище (Repository)** – абстракция доступа к данным.
- **Шлюз интеграции** – общается с внешними API.
- **Планировщик (Cron)** – выполняет периодические задачи.

Для типовых проектов можно использовать начальный шаблон: `{BR}-api`, `{BR}-listener`, `{BR}-worker`, но решение принимается на основе анализа.

### 2.4. Роль векторной памяти проекта (НОВОЕ)

**Каждый проект имеет собственное векторное хранилище** (Chroma, FAISS или аналоги), которое находится **в папке проекта**:  
`/data/projects/{project_id}/.memory/vector_store/`.

Сюда индексируются:

- Все документы L1–L5.
- Паспорта веток и контейнеров.
- Спецификации патчей.
- Графы зависимостей.
- Код (на этапе L6 – по желанию).

**Зачем это нужно:**  
Агенты (C1.2, Гефест, Рева) перед началом работы над проектом **обязаны** выполнить семантический поиск по векторной памяти, чтобы извлечь релевантный контекст (похожие контейнеры, ранее принятые решения, уже существующие интерфейсы), **не забивая диалоговое окно тоннами текста**. Это реализуется через вызов API `POST /api/project/{project_id}/search` (контейнер C2.3 Semantic Search, развёрнутый локально для проекта).

**Правило:** Если при выделении контейнера C1.2 находит в памяти семантически близкий контейнер из другого проекта, он должен предложить пользователю переиспользовать его (или скопировать с адаптацией), а не создавать с нуля.

## 3. Алгоритм выделения контейнеров (пошагово)

### Шаг 1. Подготовка: входные данные

- Паспорт ветки – из папки проекта:  
  `/data/projects/{project_id}/branches/BR-{id}.md`.
- Общий Паспорт системы (L2) – там же:  
  `/data/projects/{project_id}/L2_PASSPORT.md`.
- **Векторная память проекта** – перед анализом C1.2 выполняет поиск по ключевым словам ветки, чтобы найти уже существующие контейнеры в других ветках этого же проекта или в библиотеке переиспользуемых решений (BR14 Showroom). Это позволяет избежать дублирования.

### Шаг 2. Анализ функциональности ветки

Разбей описание ветки на **логические подфункции**. Используй:

- **Глаголы** из описания (управлять, читать, фильтровать, отправлять).
- **Существительные** – ключевые сущности (аккаунт, сообщение, ключевое слово).
- **Внешние системы** (Telegram API, база данных).

**Пример для ветки «Мониторинг и фильтрация»:**
- Чтение сообщений из Telegram-групп.
- Разбивка на предложения.
- Проверка ключевых слов и стоп-слов.
- Формирование события срабатывания.

### Шаг 3. Группировка подфункций в кандидаты контейнеров

Сгруппируй подфункции, которые:
- Работают с одними и теми же сущностями.
- Имеют общий внешний интерфейс (API).
- Могут быть реализованы как один процесс.

**Правило:** не плоди контейнеры без необходимости. Для простых веток (3–5 подфункций) часто достаточно 1–2 контейнеров.

### Шаг 4. Определение зависимостей между контейнерами

- **Синхронные зависимости** – контейнер A вызывает API контейнера B и ждёт ответа (указывается явно).
- **Асинхронные** – через очередь сообщений (брокер).
- Зависимость от внешних систем (Telegram API) тоже фиксируется.

### Шаг 5. Формирование предварительного списка контейнеров

Создай таблицу (сохраняется в черновик проекта):

| ID контейнера | Название | Краткое описание | Предполагаемый порт (если HTTP) | Зависимости |
|---------------|----------|------------------|--------------------------------|--------------|
| C-TG-1.1 | Account Manager | CRUD аккаунтов, авторизация | 8100 | нет |
| C-TG-1.2 | Session Storage | Шифрование и хранение сессий | null | C-TG-1.1 |
| C-TG-2.1 | Message Listener | Чтение сообщений из Telegram | 8200 | C-TG-1.2 |
| C-TG-2.2 | Keyword Filter | Фильтрация по ключевым/стоп-словам | 8201 | C-TG-2.1 |

### Шаг 6. Проверка на типовые ошибки (самопроверка)

Перед передачей аудитору проверь:

- [ ] Нет контейнера, который делает две несвязанные вещи.
- [ ] Нет циклических зависимостей (A → B → A).
- [ ] Каждый контейнер имеет хотя бы одну чёткую ответственность.
- [ ] Если контейнер не имеет смысла без другого – возможно, их стоит объединить.
- [ ] Для каждого контейнера понятен тип (HTTP-сервис, воркер, библиотека).

### Шаг 7. Создание паспортов контейнеров

Для каждого контейнера создай файл **в папке проекта** по пути:  
`/data/projects/{project_id}/containers/{id}.md`  
(или `/data/projects/{project_id}/branches/BR-{id}/containers/{id}.md` – на выбор, но единообразие обязательно).

**Шаблон паспорта контейнера** (YAML-шапка + Markdown):

```yaml
---
id: C-TG-1.1
branch: BR-TG-1
responsible: [назначить]
status: planned   # planned | implemented
name: Account Manager
description: Управление Telegram-аккаунтами: добавление, удаление, авторизация, статус.
port: 8100        # если HTTP-сервис, иначе null
has_dockerfile: false
has_tests: false
healthcheck: false
version: 0.1
memory_indexed: false   # станет true после индексации
dependencies:
  - external: Telegram API
  - container: C-TG-1.2
# НОВЫЕ ПОЛЯ (из «ДИЛЕТАНТЫ»)
requires_e2e_llm_tests: true   # обязательный E2E-тест с LLM-судьёй
max_complexity_cyclomatic: 10  # допустимая цикломатическая сложность
max_lines_per_file: 300
requires_decomposition: false   # true для сложных контейнеров (тогда нарезка патчей будет через Планировщик→Генератор→Оценщик)
---
# Контейнер C-TG-1.1: Account Manager

## Функции
- Добавление аккаунта через номер телефона (авторизация, код).
- Получение статуса аккаунта (активен / ошибка сессии / флуд).
- Приостановка / возобновление мониторинга.
- Удаление аккаунта.

## API (если есть)
- `POST /accounts` — добавить аккаунт.
- `GET /accounts/{id}` — статус.
- `PUT /accounts/{id}/pause` — приостановить.

## Зависимости
- Telegram User API (Pyrogram) — внешняя.
- Session Storage (C-TG-1.2) — для сохранения сессий.

## Планируемые патчи (L5) – будет заполнено на следующем этапе
- ...
```

### Шаг 8. Обновление паспорта ветки

В паспорте ветки (`/data/projects/{project_id}/branches/BR-TG-1.md`) добавь список ID контейнеров в поле `containers`:

```yaml
containers: ["C-TG-1.1", "C-TG-1.2"]
```

### Шаг 9. Передача на аудит Реве

Сформированные паспорта контейнеров и обновлённый паспорт ветки передаются агенту Рева для проверки по чек-листу (раздел 6).

### Шаг 10. Индексация в векторную память (НОВЫЙ, ОБЯЗАТЕЛЬНЫЙ)

После успешного аудита C1.2 вызывает API индексации (через Мнемосину):

```bash
curl -X POST "http://localhost:8108/api/project/TG_Keyword_Monitor/index" \
  -H "Content-Type: application/json" \
  -d '{
    "documents": [
      "/data/projects/TG_Keyword_Monitor/branches/BR-TG-1.md",
      "/data/projects/TG_Keyword_Monitor/containers/C-TG-1.1.md",
      "/data/projects/TG_Keyword_Monitor/containers/C-TG-1.2.md"
    ]
  }'
```

После успешной индексации в паспортах контейнеров поле `memory_indexed` меняется на `true`.  
**Без индексации переход к следующему этапу запрещён.**

## 4. Роль пользователя на этом этапе

**Минимальна.** Пользователь не участвует в детальной декомпозиции на контейнеры, если только ветка не очень сложная или он сам не хочет уточнить. Возможно, один короткий вопрос:

> «В ветке X я выделил контейнеры A, B, C. Устраивает ли вас такое разделение? Или нужно что-то объединить/разбить?»

Но по умолчанию система принимает решение самостоятельно. Если пользователь даёт обратную связь, она фиксируется в векторной памяти.

---

## 5. Критерии качества контейнера (для самопроверки)

- Название отражает функцию (Account Manager, а не Utils).
- Описание занимает 3–5 предложений, не больше.
- Ответственность контейнера можно пересказать одной фразой.
- Зависимости явно перечислены.
- Контейнер не пытается делать две разные вещи.

## 6. Чек-лист аудитора (Рева) для проверки контейнеров

Аудитор (Рева) получает паспорта контейнеров и паспорт ветки. Проверяет **бинарно** (ДА/НЕТ). Если хоть один пункт = НЕТ — возвращает на доработку с комментариями.

### 6.1. Формальная проверка

- **F-C1:** Каждый контейнер имеет уникальный ID в формате `C-{project_abbr}-{номер}`.
- **F-C2:** В паспорте контейнера заполнены все обязательные поля: `id`, `branch`, `status`, `name`, `description`, `has_dockerfile`, `has_tests`, `healthcheck`, `version`, `memory_indexed`, `requires_e2e_llm_tests`, `max_complexity_cyclomatic`, `max_lines_per_file`, `requires_decomposition`.
- **F-C3:** Поле `port` указано (или `null`).
- **F-C4:** В паспорте ветки поле `containers` содержит список ID всех контейнеров этой ветки.
- **F-C5:** Нет дублирующихся имён или ID контейнеров в рамках проекта.
- **F-C6:** Все файлы паспортов лежат в папке проекта, а не в заводских директориях.

### 6.2. Содержательная проверка

- **C-C1:** Описание контейнера чёткое и однозначное (нет слов «возможно», «например», «и т.д.»).
- **C-C2:** Контейнер отвечает ровно за одну функциональную область (не смешивает разные ответственности).
- **C-C3:** Зависимости указаны явно (внешние системы и другие контейнеры). Нет скрытых зависимостей.
- **C-C4:** Нет циклических зависимостей между контейнерами (A → B → A).
- **C-C5:** Контейнер имеет смысл даже без других контейнеров (минимальная независимость). Если нет — проверь, не нужно ли объединить.
- **C-C6:** Количество контейнеров в ветке разумно (обычно 1–5, не более 10). Если больше — возможно, нужна подветка или пересмотр.
- **C-C7:** Все контейнеры используют разрешённые слои (из Золотого стандарта или глобальных правил).
- **C-C8:** Ни один контейнер не нарушает запрет на прямой доступ к БД других контейнеров (если такое запрещено).

### 6.3. Новые проверки из «ДИЛЕТАНТЫ»

- **C-C9 (Векторная память):** После аудита выполнена индексация всех паспортов в векторную память проекта. Поле `memory_indexed` стало `true`.
- **C-C10 (E2E-тесты с LLM-судьями):** В паспорте контейнера указано `requires_e2e_llm_tests: true` (для всех контейнеров, кроме самых тривиальных). Это гарантирует, что на этапе L5 будет создан патч на написание таких тестов.
- **C-C11 (Контроль здоровья кода):** Установлены допустимые метрики сложности (цикломатическая сложность ≤ 10, строк на файл ≤ 300). Если контейнер заведомо сложный, значения могут быть увеличены, но с обоснованием в комментарии.
- **C-C12 (Архитектура «Планировщик→Генератор→Оценщик»):** Если контейнер помечен `requires_decomposition: true`, это допустимо, но тогда на этапе L5 C1.2 должен использовать трёхзвенную схему (а не линейную нарезку).

### 6.4. Итоговое решение

Если все пункты = ДА → **ПРИНЯТО**.  
Если хотя бы один = НЕТ → **ОТКЛОНЕНО** с указанием, какие пункты нарушены и что исправить.

## 7. Переход к следующему этапу

После утверждения контейнеров аудитором:

- Паспорта контейнеров сохранены в папке проекта.
- Векторная память проекта обновлена (индексация выполнена).
- Управление передаётся **C1.2 Patch Architect** для выполнения следующего этапа — **нарезки контейнеров на патчи (L4 → L5)**. Этот этап описан в отдельном протоколе `ПРОТОКОЛ_ПАТЧИ.md`.

## 8. Пример полного цикла (ветка → контейнеры) с учётом улучшений

**Вход:** Паспорт ветки `BR-TG-1` (Управление аккаунтами) в папке проекта `/data/projects/TG_Keyword_Monitor/branches/BR-TG-1.md`.

**Шаг 2 (анализ):** подфункции: добавление аккаунта, авторизация, хранение сессий, управление статусом.

**Шаг 3 (группировка):**
- Группа 1: добавление, авторизация, статус → один контейнер (Account Manager).
- Группа 2: хранение сессий (шифрование) → отдельный контейнер (Session Storage).

**Шаг 4 (зависимости):** Account Manager зависит от Session Storage.

**Шаг 5 (таблица):** создана.

**Шаг 7 (паспорта):** созданы два файла в `/data/projects/TG_Keyword_Monitor/containers/`.

**Шаг 9 (аудит):** проверка пройдена.

**Шаг 10 (индексация):** выполнена, `memory_indexed: true`.

**Результат:** готово к нарезке на патчи. В паспортах контейнеров проставлены `requires_e2e_llm_tests: true`, `max_complexity_cyclomatic: 10`, `requires_decomposition: false`.
