## 🛡️ Протокол аудитора: приёмка этапов проектирования

**ID:** PROTOCOL-AUDITOR-001  
**Версия:** 1.0  
**Статус:** Утверждён  
**Дата:** 2026-04-05  
**Область действия:** Рева (агент-аудитор), C1.2 Patch Architect (отправитель запросов на аудит), Аргус (эскалация)

---

### 0. Ответственные роли и их функции

| Роль/Агент | Функция в процессе аудита | Взаимодействие |
|------------|---------------------------|----------------|
| **Рева** | Проводит аудит этапа по чек-листу, фиксирует результат, принимает решение | Читает файлы проекта, вызывает API проверки, пишет отчёт |
| **C1.2 Patch Architect** | Отправляет запрос на аудит после завершения этапа | Вызывает `POST /api/audit/request` |
| **Аргус** | Получает эскалацию, если аудит не может быть завершён автоматически или требуется ручное решение | Читает отчёт, принимает решение, создаёт задачи |
| **Мнемосина** | Индексирует отчёты аудита в векторную память | Вызывается после фиксации результата |

## 1. Назначение документа

Описать **сквозной процесс аудита этапов проектирования** (L2–L5), который выполняет агент Рева. Документ определяет:

- Как Рева получает задание на аудит.
- Как выбирает и применяет соответствующий чек-лист.
- Как фиксирует нарушения и принимает решение.
- Какой формат отчёта использовать.
- Когда и как эскалировать проблему Аргусу или создавать задачу в handover.

**Без этого документа аудит каждого этапа может выполняться непоследовательно, а решения – быть недетерминированными.**

## 2. Место аудитора в процессе проектирования

| Этап | Что делаем | Аудитор проверяет | Документ с чек-листом |
|------|-----------|-------------------|----------------------|
| **L2 (Замысел)** | Опрос пользователя, формирование L2 | Полнота, непротиворечивость, наличие индексации | `ПРОТОКОЛ_ОПРОСА.md`, раздел 7 |
| **L3 (Ветки)** | Разбиение L2 на ветки | Формальная и содержательная корректность веток, аудит LLM-судьи | `ПРОТОКОЛ_ПРОЕКТИРОВАНИЯ_ВЕТКИ.md`, раздел 7 |
| **L4 (Контейнеры)** | Разбиение веток на контейнеры | Паспорта контейнеров, зависимости, индексация | `ПРОТОКОЛ_КОНТЕЙНЕРЫ.md`, раздел 6 |
| **L5 (Патчи)** | Разбиение контейнеров на патчи | Атомарность, граф, спецификации, индексация | `ПРОТОКОЛ_ПАТЧИ.md`, раздел 7 |
| **Очередь исполнения** | Склейка патчей в глобальный порядок | Топологическая сортировка, полнота, режимы | `ПРОТОКОЛ_ОЧЕРЕДЬ.md`, раздел 7 |

После успешного аудита этапа Рева выдаёт **ПРИНЯТО**, и управление переходит к следующему этапу. Если **ОТКЛОНЕНО** – возврат на доработку с указанием нарушений.

## 3. Общий процесс аудита (пошагово)

### 3.1. Получение запроса на аудит

**3.1.1.** C1.2 (или другой агент) отправляет Реве запрос через handover или прямой вызов API:

```bash
curl -X POST "http://localhost:8080/api/audit/request" \
  -H "Content-Type: application/json" \
  -d '{
    "project_id": "TG_Keyword_Monitor",
    "stage": "L3_BRANCHES",
    "artifacts_path": "/data/projects/TG_Keyword_Monitor"
  }'
```

**3.1.2.** Рева проверяет, что переданный этап существует и для него определён чек-лист. Если нет – возвращает ошибку.

### 3.2. Загрузка артефактов

**3.2.1.** Рева читает все необходимые файлы из папки проекта:
- Для L2: `ПАСПОРТ_СИСТЕМЫ.md`, `ОТВЕТЫ.json`, `АУДИТ_ОТЧЕТ.md` (если есть).
- Для L3: паспорта веток (`branches/BR-*.md`), `ПАСПОРТ_СИСТЕМЫ.md`.
- Для L4: паспорта контейнеров (`containers/C-*.md`), паспорта веток.
- Для L5: спецификации (`specs/P-*.md`), файлы графов (`patches/*_PATCHES.md`).
- Для очереди: `ОЧЕРЕДЬ_ИСПОЛНЕНИЯ__vX.X.md`, `ГРАФ_ЗАВИСИМОСТЕЙ.json`.

**3.2.2.** Если какой-то обязательный файл отсутствует, Рева возвращает **ОТКЛОНЕНО** с указанием: «Отсутствует файл [путь]».

### 3.3. Выбор и применение чек-листа

**3.3.1.** Рева загружает соответствующий протокол (из `00_КАНОН/Методология/`) и извлекает раздел с чек-листом.  
**3.3.2.** Проходит по каждому пункту чек-листа, выполняя проверки:
- Формальные (существование файлов, наличие полей).
- Содержательные (сверка с эталоном, проверка зависимостей).
- Для L3/L4/L5 – проверка результатов LLM-судьи (если применимо).
- Проверка индексации в векторную память (если требуется).

**3.3.3.** Для каждого пункта фиксирует результат: ДА / НЕТ.

**3.3.4. Обработка ошибок:** если какой-то пункт чек-листа невозможно проверить автоматически (например, требуется семантический анализ, который не реализован), Рева помечает его как `MANUAL_REQUIRED` и эскалирует (см. раздел 6).

### 3.4. Фиксация нарушений

**3.4.1.** Если хотя бы один пункт чек-листа = НЕТ, Рева собирает список нарушений в структурированном виде:

```json
{
  "violations": [
    {
      "stage": "L3_BRANCHES",
      "check_id": "C-B1",
      "description": "Описание ветки BR-TG-1 содержит неоднозначность: «возможно, будет авторизация»",
      "fix": "Убрать слово «возможно», заменить на чёткое описание."
    }
  ]
}
```

**3.4.2.** Если все пункты = ДА – нарушений нет.

### 3.5. Принятие решения

**3.5.1.** Если нарушений нет → **ПРИНЯТО**.  
**3.5.2.** Если есть нарушения → **ОТКЛОНЕНО**.

**3.5.3.** В случае `MANUAL_REQUIRED` (пункт нельзя проверить автоматически) → Рева эскалирует Аргусу (см. раздел 6).

### 3.6. Формирование отчёта аудитора

**3.6.1.** Рева создаёт файл отчёта в папке проекта:  
`/data/projects/{project_id}/АУДИТ_{stage}_{timestamp}.md`  
по шаблону (раздел 5).

**3.6.2.** Если результат **ПРИНЯТО**, Рева также:
- Обновляет статус этапа в `ПАСПОРТ_СИСТЕМЫ.md` (например, `L3_status: approved`).
- Вызывает индексацию отчёта в векторную память (через C2.6).

**3.6.3.** Если результат **ОТКЛОНЕНО**, Рева:
- Не обновляет статус этапа.
- Возвращает управление C1.2 с указанием, какие нарушения исправить.

### 3.7. Эскалация и создание задач

**3.7.1.** Если аудит не может быть завершён автоматически (MANUAL_REQUIRED), Рева создаёт задачу в handover:

```bash
curl -X POST "http://localhost:8080/api/handover/tasks" \
  -H "Content-Type: application/json" \
  -d '{
    "title": "Ручная проверка этапа L3 для проекта TG_Keyword_Monitor",
    "description": "Пункт чек-листа C-B5 требует ручной оценки. Артефакты в /data/projects/TG_Keyword_Monitor",
    "assigned_to": "АРГУС",
    "priority": "medium"
  }'
```

**3.7.2.** Аргус получает задачу, выполняет ручную проверку и либо утверждает этап, либо возвращает на доработку.

## 4. Чек-лист для самого аудитора (мета-проверка)

Аудитор (Рева) перед началом работы над проектом должен убедиться, что:

- **M-A1:** У него есть доступ на чтение к папке проекта `/data/projects/{project_id}/`.  
- **M-A2:** Он знает, какой этап проверяет (передан в запросе).  
- **M-A3:** Соответствующий протокол с чек-листом существует в `00_КАНОН/Методология/`.  
- **M-A4:** Он может вызвать API индексации (C2.6) и handover (BR7).  
- **M-A5:** У него есть право принимать решение ПРИНЯТО/ОТКЛОНЕНО без дополнительных согласований (кроме эскалации).

Если хотя бы один пункт не выполнен – Рева не начинает аудит и сообщает об ошибке.

## 6. Обработка ошибок и особых ситуаций

| Ситуация | Действие Ревы |
|----------|---------------|
| Нет доступа к папке проекта | Вернуть ОТКЛОНЕНО с комментарием «нет прав на чтение». Создать задачу для Гермеса. |
| Чек-лист ссылается на несуществующий API (например, LLM-судья не отвечает) | Пометить пункт как MANUAL_REQUIRED, эскалировать Аргусу. |
| Пользователь внёс изменения в артефакты во время аудита (изменился файл) | Прервать аудит, вернуть ОТКЛОНЕНО с комментарием «артефакты изменены, повторите аудит». |
| Аудит занял более 10 минут (таймаут) | Прервать, вернуть ОТКЛОНЕНО, создать задачу для оптимизации. |
| Рева не может однозначно интерпретировать пункт чек-листа | Запросить уточнение у Аргуса через handover. |

## 7. Интеграция с векторной памятью

**7.1.** После успешного аудита (ПРИНЯТО) Рева вызывает индексацию отчёта:

```bash
curl -X POST "http://localhost:8108/api/project/{project_id}/index" \
  -H "Content-Type: application/json" \
  -d '{
    "documents": ["/data/projects/{project_id}/АУДИТ_{stage}_{timestamp}.md"]
  }'
```

**7.2.** Если индексация не удалась, Рева создаёт задачу в handover для Мнемосины, но не блокирует переход к следующему этапу.
