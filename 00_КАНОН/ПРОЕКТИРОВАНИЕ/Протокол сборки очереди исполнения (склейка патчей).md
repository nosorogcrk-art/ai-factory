## 1. Цель документа

Описать **алгоритм построения глобального линейного порядка исполнения патчей** из всех контейнеров и веток проекта, пригодного для автоматического выполнения.

**Выход этапа:**
- Файл **«ОЧЕРЕДЬ_ИСПОЛНЕНИЯ__vX.X.md»** со строгим линейным списком патчей.
- JSON-копия графа зависимостей.
- Индексация очереди в векторную память проекта.
- **Чек-лист аудитора** для формальной приёмки очереди.

Без этого документа **завод не может автоматически определить, в каком порядке исполнять патчи**, а без чек-листа аудитор не может подтвердить корректность.

|---------|-----------|-----------|---------------|

## 3. Исходные данные

На входе у C1.2 (или выделенного сборщика очереди) есть:

**3.1.** Список всех спецификаций L5 – **в папке проекта**:  
`/data/projects/{project_id}/specs/P-*.md` для всех контейнеров.

**3.2.** Граф зависимостей внутри каждого контейнера – из файлов:  
`/data/projects/{project_id}/patches/{container_id}_PATCHES.md`.

**3.3.** Паспорта контейнеров – `/data/projects/{project_id}/containers/{container_id}.md` (для определения базового порядка контейнеров и флагов MVP).

**3.4.** Паспорта веток – `/data/projects/{project_id}/branches/BR-*.md` (для понимания, какие ветки активны, а какие отложены).

**3.5.** Критерии MVP – какие ветки/контейнеры должны быть реализованы в первую очередь (поле `status: active` в паспортах).

**3.6.** Если хотя бы один контейнер не имеет утверждённого списка патчей – этап не начинается, возврат на L5 (протокол патчей).

## 4. Теоретическая основа: что такое правильная очередь исполнения

Очередь исполнения – это **топологически отсортированный список всех патчей**, удовлетворяющий:

1. **Все зависимости соблюдены** – если патч A зависит от B, то B идёт раньше A.
2. **Нет циклов** – граф ацикличен.
3. **Достижимость** – каждый патч может быть выполнен (нет «висящих» зависимостей).
4. **Базовый порядок контейнеров** – если нет зависимостей, контейнеры идут по возрастанию номера (BR1_C1 → BR1_C2 → BR2_C1 и т.д.).
5. **Приоритет зависимостей** – если зависимость требует выполнения патча из более позднего контейнера раньше, очередь это отражает.

**Мировой опыт (Agile, CI/CD, dependency management):**  
Порядок исполнения должен быть **детерминированным** и **воспроизводимым**. Топологическая сортировка – единственный корректный способ.

## 5. Алгоритм сборки очереди (пошагово)

### 5.1. Собрать все патчи проекта в единый реестр

**5.1.1.** C1.2 сканирует папку `/data/projects/{project_id}/specs/` и извлекает из каждого файла:
- ID патча (из YAML-шапки или заголовка).
- Контейнер (из поля `container` или из имени файла).
- Ветку (из паспорта контейнера).
- Список зависимостей (из поля `depends_on` в спецификации).

**5.1.2.** Результат – JSON-объект:

```json
{
  "patches": [
    {"id": "P-TG-1.1.0", "container": "C-TG-1.1", "branch": "BR-TG-1", "depends_on": []},
    {"id": "P-TG-1.1.1", "container": "C-TG-1.1", "branch": "BR-TG-1", "depends_on": ["P-TG-1.1.0"]},
    ...
  ]
}
```

**5.1.3. Проверка целостности:**  
- Все ID в `depends_on` существуют в реестре.  
- Если нет – ошибка, возврат на L5 (исправить спецификации).  
- Если контейнер или ветка не найдены – ошибка.

### 5.2. Построить глобальный ориентированный граф

**5.2.1.** Для каждого патча создать узел. Для каждой зависимости из `depends_on` добавить ребро `зависимость → патч`.  
**5.2.2.** Сохранить граф в `/data/projects/{project_id}/ГРАФ_ЗАВИСИМОСТЕЙ.json` (копия для отладки).

### 5.3. Проверить граф на циклы

**5.3.1.** Выполнить поиск циклов (алгоритм DFS с цветами или топологическая сортировка с подсчётом входящих рёбер).  
**5.3.2.** Если цикл найден:  
- Зафиксировать цикл (например, `P-A → P-B → P-C → P-A`).  
- Вернуть ошибку с указанием цикла. Этап не может быть продолжен, требуется исправление зависимостей в L5.  
- Создать задачу в handover для архитектора.

### 5.4. Выполнить топологическую сортировку

**5.4.1.** Использовать алгоритм Кана (Kahn):

```
1. Вычислить входящие степени для всех узлов.
2. Поместить все узлы с degree = 0 в очередь.
3. Пока очередь не пуста:
   - Извлечь узел U.
   - Добавить U в результат.
   - Для каждого V, где есть ребро U→V, уменьшить degree[V] на 1.
   - Если degree[V] стал 0, добавить V в очередь.
4. Если размер результата меньше числа узлов – есть цикл (уже проверено).
```

**5.4.2. Правила при сортировке (если несколько узлов имеют degree = 0):**  
Применять **вторичную сортировку** по:
1. Номеру ветки (BR1 → BR2 → …) – извлекается из ID патча или паспорта ветки.
2. Номеру контейнера внутри ветки (C1 → C2 → …).
3. Номеру патча внутри контейнера (P0 → P1 → …).

**5.4.3.** Результат – линейный список `[P-A, P-B, P-C, ...]`.

### 5.5. Проверить достижимость всех патчей

**5.5.1.** Убедиться, что каждый патч из реестра включён в отсортированный список.  
**5.5.2.** Если какой-то патч отсутствует – граф несвязен или есть недостижимые узлы (ошибка в зависимостях). Вернуть ошибку с перечнем недостижимых патчей.

### 5.6. (Опционально) Проверить соответствие базовому порядку контейнеров

**5.6.1.** Если в отсортированном списке патч из контейнера `C5` идёт раньше патча из `C2`, но при этом нет явной зависимости, это допустимо (зависимости имеют приоритет).  
**5.6.2.** Если **нет никакой причины** для такого порядка (ни зависимости, ни вторичной сортировки) – система должна зафиксировать это как предупреждение в логах, но не блокировать.

### 5.7. Сгенерировать файл очереди исполнения

**5.7.1.** По шаблону (Приложение А) создать файл **в папке проекта**:  
`/data/projects/{project_id}/ОЧЕРЕДЬ_ИСПОЛНЕНИЯ__v1.0.md`.

**5.7.2. Обязательные разделы:**
- **Идентификация ветки** – название проекта, контур.
- **Глобальный порядок патчей** – линейный список (ID + краткое название).
- **Детали по контейнерам** – группировка патчей по контейнерам, с указанием для каждого патча:
  - РИСК (из спецификации L5)
  - РЕЖИМ (быстрый/строгий – вычисляется по риску: высокий → строгий, низкий → быстрый, средний – берётся из L5 или по умолчанию быстрый)
  - ОБЯЗАТЕЛЬНАЯ ПРОВЕРКА (из критериев готовности патча, первая команда)
- **ПРОВЕРКА ГРАФА ЗАВИСИМОСТЕЙ** – блок со статистикой и подтверждением валидности (все чек-боксы должны быть отмечены).
- **Готовность к исполнению** – чек-боксы.

**5.7.3.** Нумерация версий: каждый пересчёт очереди увеличивает версию (v1.0 → v1.1 → …).

### 5.8. Индексация очереди в векторную память

**5.8.1.** После успешной генерации C1.2 вызывает API индексации (C2.6):

```bash
curl -X POST "http://localhost:8108/api/project/{project_id}/index" \
  -H "Content-Type: application/json" \
  -d '{
    "documents": ["/data/projects/{project_id}/ОЧЕРЕДЬ_ИСПОЛНЕНИЯ__v1.0.md"]
  }'
```

**5.8.2.** API возвращает `{ "status": "ok", "indexed_count": 1 }`.  
**5.8.3.** Если индексация не удалась (ошибка, таймаут) – повтор 3 раза.  
**5.8.4.** После 3 неудач – создать задачу в handover для ручной индексации. **Переход к L6 блокируется.**

### 5.9. Передать очередь аудитору (Рева)

**5.9.1.** Сгенерированный файл и JSON-граф передаются Реве для формальной проверки по **Чек-листу аудитора очереди** (раздел 7).  
**5.9.2.** Рева возвращает `ПРИНЯТО` или `ОТКЛОНЕНО`.  
**5.9.3.** Если `ОТКЛОНЕНО` – C1.2 исправляет замечания (обычно это ошибки в исходных L5, которые нужно вернуть на этап L5). Максимум 3 итерации.  
**5.9.4.** После 3 неудач – создать задачу в handover для ручного вмешательства.

## 6. Пример: очередь для TG Keyword Monitor (фрагмент)

**Исходные данные:**
- Ветка BR-TG-1 (Управление аккаунтами) с контейнером C-TG-1.1, патчи P0..P9.
- Ветка BR-TG-2 (Мониторинг и фильтрация) с контейнером C-TG-2.1, патчи P10..P19.

**Зависимости:**
- P10 (база мониторинга) не зависит от аккаунтов.
- P11 (чтение сообщений) зависит от P1 (создание аккаунта).
- P12 (фильтрация) зависит от P11.

**Топологическая сортировка даст порядок:**

```
1. P-TG-1.1.0 – Базовая структура (аккаунты)
2. P-TG-1.1.1 – Создание аккаунта
3. P-TG-2.1.0 – Базовая структура (мониторинг)   // нет зависимости, может идти после P0
4. P-TG-1.1.2 – Чтение аккаунта
5. P-TG-2.1.1 – Чтение сообщений                  // зависит от P1
6. P-TG-2.1.2 – Фильтрация                        // зависит от P11
...
```

**Фрагмент файла очереди:**

```markdown
## ГЛОБАЛЬНЫЙ ПОРЯДОК ПАТЧЕЙ
1. P-TG-1.1.0 – Базовая структура (аккаунты)
2. P-TG-1.1.1 – Создание аккаунта
3. P-TG-2.1.0 – Базовая структура (мониторинг)
4. P-TG-1.1.2 – Чтение аккаунта
5. P-TG-2.1.1 – Чтение сообщений
6. P-TG-2.1.2 – Фильтрация
...

## КОНТЕЙНЕР BR-TG-1 / C-TG-1.1
### ПАТЧ P-TG-1.1.0
РИСК: низкий
РЕЖИМ: быстрый
ОБЯЗАТЕЛЬНАЯ ПРОВЕРКА: pytest tests/test_models.py

### ПАТЧ P-TG-1.1.1
РИСК: средний
РЕЖИМ: быстрый
ОБЯЗАТЕЛЬНАЯ ПРОВЕРКА: curl -X POST http://localhost:8100/accounts -d '{"phone":"..."}' && echo "201"
```

## 7. Чек-лист аудитора (Рева) для приёмки очереди исполнения

**Назначение:** Дать бинарный результат ПРИНЯТО / ОТКЛОНЕНО.  
Если хотя бы один пункт = НЕТ – очередь недействительна, возврат на доработку (исправление зависимостей в L5 или пересборка очереди).

### 7.1. Формальная проверка

- **F-Q1:** Файл `/data/projects/{project_id}/ОЧЕРЕДЬ_ИСПОЛНЕНИЯ__vX.X.md` существует.  
- **F-Q2:** Файл соответствует шаблону (Приложение А) – есть все обязательные разделы.  
- **F-Q3:** Блок ПРОВЕРКА ГРАФА ЗАВИСИМОСТЕЙ полностью заполнен (все чек-боксы отмечены, нет шаблонных значений).  
- **F-Q4:** Версия в имени файла соответствует содержимому (нет расхождений).

### 7.2. Полнота

- **C-Q1:** В глобальном порядке перечислены **все** патчи из всех утверждённых контейнеров (сверка с реестром L5).  
- **C-Q2:** Нет лишних патчей (которых нет в L5).  
- **C-Q3:** Каждый патч встречается ровно один раз.  
- **C-Q4:** Для каждого патча указаны РИСК, РЕЖИМ, ОБЯЗАТЕЛЬНАЯ ПРОВЕРКА.  
- **C-Q5:** Все патчи из отложенных веток (status: planned) **не включены** в очередь (если только не указано иное в MVP).

### 7.3. Корректность графа (повторная проверка)

- **G-Q1:** Все зависимости из L5 соблюдены в глобальном порядке (если A зависит от B, то B идёт раньше A).  
- **G-Q2:** Нет циклов (повторная проверка топологической сортировки).  
- **G-Q3:** Все патчи достижимы (нет «висящих» зависимостей).  
- **G-Q4:** Порядок получен топологической сортировкой (а не ручной правкой).  
- **G-Q5:** JSON-граф `/data/projects/{project_id}/ГРАФ_ЗАВИСИМОСТЕЙ.json` соответствует порядку.

### 7.4. Соответствие режима риску

- **R-Q1:** Для патчей с РИСК = высокий → РЕЖИМ = строгий.  
- **R-Q2:** Для патчей с РИСК = низкий → РЕЖИМ = быстрый.  
- **R-Q3:** Для РИСК = средний – допустим любой режим, но он должен быть указан явно (не пусто).

### 7.5. Межконтейнерные зависимости

- **M-Q1:** Если патч из контейнера A зависит от патча из контейнера B, в глобальном порядке патч из B идёт раньше (независимо от номеров контейнеров).  
- **M-Q2:** Нет зависимостей от контейнеров, помеченных как `planned` (отложенных) – если такой контейнер не входит в MVP, патч не может быть выполнен (ошибка).

### 7.6. Язык и формулировки

- **L-Q1:** В ОБЯЗАТЕЛЬНАЯ ПРОВЕРКА нет общих слов («проверить работоспособность», «убедиться»). Только конкретные действия (команды curl, pytest, ручные шаги).  
- **L-Q2:** РИСК указан строго как `низкий`, `средний`, `высокий` (без опечаток).  
- **L-Q3:** РЕЖИМ указан строго как `быстрый` или `строгий`.

### 7.7. Проверка индексации

- **I-Q1:** Выполнена индексация очереди в векторную память проекта.  
- **I-Q2:** API индексации вернул `status: ok`.  
- **I-Q3:** Если индексация не удалась – создана задача в handover.

### 7.8. Итоговое решение

Если все пункты = ДА → **ПРИНЯТО**, переход к реализации (L6).  
Если хотя бы один = НЕТ → **ОТКЛОНЕНО** с указанием нарушений.

## 8. Итоговый отчёт аудитора

Аудитор (Рева) после проверки выдаёт файл в папке проекта:

`/data/projects/{project_id}/АУДИТ_ОЧЕРЕДИ_{timestamp}.md`

**Формат:**

```markdown
# АУДИТ ОЧЕРЕДИ ИСПОЛНЕНИЯ

**Проект:** {project_id}
**Дата:** ГГГГ-ММ-ДД
**Версия очереди:** vX.X

## Результат: ПРИНЯТО / ОТКЛОНЕНО

## Нарушения (если ОТКЛОНЕНО)
- [ ] Пункт C-Q1 – отсутствует патч P-TG-2.1.3 в глобальном порядке.
- [ ] Пункт G-Q1 – нарушена зависимость: P-TG-2.1.1 идёт раньше P-TG-1.1.1, но зависит от него.

## Рекомендации
1. Вернуться на этап L5 и исправить зависимости в спецификации P-TG-2.1.1.
2. Пересобрать очередь.

## Статус очереди: ВАЛИДНА / НЕВАЛИДНА
```

Если **ПРИНЯТО** – очередь финализируется, и завод переходит к **реализации (L6)**.  
Cline (или C21.1 Code Generator) берёт первый патч из очереди и исполняет по его спецификации L5.

## 9. Хранение результатов

Все артефакты хранятся **в папке проекта**: `/data/projects/{project_id}/`

## 11. Заключение

Этот документ описывает алгоритм сборки глобальной очереди исполнения патчей на основе графов зависимостей из всех контейнеров проекта. Он основан на теории графов и лучших практиках CI/CD, адаптированных для автоматического выполнения C1.2 Patch Architect, с добавлением:

- **Топологической сортировки** с детерминированными правилами вторичной сортировки.
- **Проверки целостности** всех зависимостей.
- **Чек-листа аудитора** для формальной приёмки.
- **Хранения всех артефактов в папке проекта** – переносимость.
- **Обработки ошибок и fallback’ов** – устойчивость.
- **Индексации очереди в векторную память** – для будущих проектов.

Сам документ (методология) хранится в `00_КАНОН/Методология/ПРОТОКОЛ_ОЧЕРЕДЬ.md`.  
**Артефакты (очередь, граф, отчёты) – в папке проекта.**

После успешного завершения этапа сборки очереди завод переходит к **реализации (L6)**, где Cline (или C21.1 Code Generator) последовательно выполняет патчи строго по очереди.
