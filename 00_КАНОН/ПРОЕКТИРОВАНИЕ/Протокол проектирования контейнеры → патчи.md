## 1. Цель документа

Описать **алгоритм превращения контейнера (C) в набор атомарных патчей (P) с явными зависимостями** – графом, пригодным для построения очереди исполнения.

**Выход этапа:**
- Список патчей для каждого контейнера с уникальными ID.
- Граф зависимостей между патчами (внутри контейнера).
- Спецификации L5 для каждого патча.
- Индексация всех артефактов в векторную память проекта.
- **Чек-лист аудитора** для формальной приёмки результата.

Без этого документа **C1.2 не может автономно разбивать контейнеры на патчи**, а без чек-листа аудитор не может принять результат.

## 4. Теоретическая основа: что такое правильный патч

Патч (P) – **атомарная, проверяемая, откатываемая единица изменения**.

Мировой опыт (Agile, DDD, CI/CD) выделяет признаки хорошего патча:

| Признак | Описание | Пример нарушения |
|---------|----------|------------------|
| **Атомарность** | Патч решает ровно одну логическую задачу | «Добавить API и тесты» – два действия |
| **Проверяемость** | Критерий готовности можно проверить командой | «Улучшить производительность» – не проверяемо |
| **Откатываемость** | Патч можно отменить без последствий | Удаление таблицы БД – откат сложен |
| **Размер** | Не более 5 файлов, не более 200 строк кода | Патч на 20 файлов – не атомарен |
| **Единство слоя** | Патч трогает только один слой | Меняет UI + БД |
| **Отсутствие скрытых зависимостей** | Если патч требует другого патча – это явно указано | Патч использует новую функцию из ещё не сделанного патча |

**Золотое правило:**  
> Если патч нельзя описать в одном предложении как «Добавить X» или «Исправить Y» – он не атомарен.

## 5. Алгоритм нарезки контейнера на патчи (пошагово)

### 5.1. Анализ ответственности контейнера

**5.1.1.** Из паспорта контейнера извлечь:
- **Что делает контейнер** (описание).
- **Какие внешние зависимости** (другие контейнеры, API, БД).
- **Какие данные хранит** (сущности, таблицы).

**5.1.2.** Результат: список «зон ответственности» (например, для контейнера «Управление аккаунтами»: авторизация, хранение сессий, проверка статуса).

### 5.2. Выделение сквозных операций (CRUD + бизнес-логика)

**5.2.1.** Для каждой зоны определить операции по таблице:

| Тип операции | Пример | Должен ли быть отдельным патчем? |
|--------------|--------|----------------------------------|
| Базовая структура | Модели БД, скелет API, конфиги | **Да**, всегда первый патч |
| Создание (Create) | Эндпоинт POST | Да, если операция независима |
| Чтение (Read) | Эндпоинт GET | Да, если есть бизнес-логика |
| Обновление (Update) | Эндпоинт PUT/PATCH | Да |
| Удаление (Delete) | Эндпоинт DELETE | Да |
| Бизнес-логика | Проверка подписки, фильтрация | Да, отдельно от CRUD |
| Интеграция с внешним API | Вызов Telegram API | Да |
| Логирование + healthcheck | Отправка логов в BR18, `/health` | **Да, обязательный патч** |
| Тесты | Юнит-тесты, интеграционные | **Да, обязательный патч** |

**5.2.2.** Правило: если операция не тривиальна (требует валидации, преобразования, вызова внешнего сервиса) – она достойна отдельного патча.

### 5.3. Формирование чернового списка патчей

**5.3.1.** Создать список кандидатов в следующем порядке (от фундамента к интерфейсу):

1. **P0. Базовая структура**  
   - Файлы: `models.py`, `repositories.py`, скелет `main.py`, `requirements.txt`, `Dockerfile`.
   - Тесты: минимальные (проверка импортов, создание таблиц).

2. **P1. CRUD операции** (по одной на патч, если они независимы, или объединить, если маленькие)  
   - Пример: `P1 – Создание`, `P2 – Чтение`, `P3 – Обновление`, `P4 – Удаление`.

3. **P2. Бизнес-логика / специфические операции**  
   - Пример: `P5 – Проверка статуса`, `P6 – Авторизация`.

4. **P3. Интеграция с внешними API**  
   - Пример: `P7 – Вызов Telegram API`.

5. **P4. Логирование и healthcheck**  
   - `P8 – Отправка логов в BR18`, `P9 – Эндпоинт /health`.

6. **P5. Тесты**  
   - `P10 – Юнит-тесты`, `P11 – Интеграционные тесты`.

**5.3.2.** Итог: для типового контейнера получается 6–12 патчей.

### 5.4. Определение зависимостей между патчами (граф)

**5.4.1.** Для каждого патча указать, от каких других патчей он **зависит** (должны быть выполнены раньше).

**5.4.2. Правила зависимостей:**
- Базовая структура (P0) – не имеет зависимостей (первый).
- CRUD операции зависят от P0.
- Бизнес-логика может зависеть от соответствующих CRUD-патчей.
- Интеграция с внешним API может зависеть от CRUD (нужны данные).
- Логирование и healthcheck зависят от P0 (можно делать в конце).
- Тесты зависят от тех патчей, которые они тестируют.

**5.4.3. Пример графа для контейнера C-TG-1.1 (Управление аккаунтами):**

```
P0 (база) 
  ↓
P1 (создание) ← P2 (чтение) ← P3 (обновление) ← P4 (удаление)
  ↓                ↓
P5 (статус)      P6 (авторизация)
  ↓                ↓
P7 (лог+health) ← P8 (тесты)
```

**5.4.4. Проверка графа:**
- Нет циклов (алгоритмом DFS).
- Каждый патч достижим из начальных (без зависимостей).
- Нет ссылок на несуществующие патчи.

### 5.5. (Опционально) Поиск похожих патчей в векторной памяти

**5.5.1.** C1.2 может выполнить семантический поиск по `C2.3` для каждого кандидата в патчи.  
**5.5.2.** Если найден патч с высокой схожестью (score > 0.8), система предлагает использовать его как основу (автоматически, без диалога с пользователем).  
**5.5.3.** Ссылка на исходный патч сохраняется в спецификации L5 в поле `reused_from`.

**5.5.4. Обработка ошибок:** если поиск недоступен, пропустить шаг (не блокирует).

### 5.6. Генерация спецификаций L5 для каждого патча

**5.6.1.** Для каждого патча создать файл **в папке проекта** по пути:  
`/data/projects/{project_id}/specs/P-{project_abbr}-{container_short}-{number}.md`  
по шаблону (см. Приложение Б).

**5.6.2. Обязательные поля в спецификации:**
- `ID` – уникальный.
- `Цель` – одна фраза.
- `Модифицируемые файлы` – список файлов.
- `Зависимости` – список ID патчей (из этого же контейнера и/или из других контейнеров).
- `Критерии готовности` – проверяемые команды.
- `Тесты` – команды запуска.
- `Лимиты` – `max_complexity_cyclomatic`, `max_lines_per_file` (из паспорта контейнера).

**5.6.3.** Зависимости на патчи из **других контейнеров** указываются явно в формате `P-{project_abbr}-{container_short}-{number}`.

### 5.7. Проверка полноты и атомарности (самопроверка C1.2)

Перед передачей аудитору C1.2 обязан проверить:

- [ ] **A1:** У каждого патча есть ID.
- [ ] **A2:** У каждого патча есть цель (одна, измеримая).
- [ ] **A3:** Патч затрагивает не более 5 файлов.
- [ ] **A4:** Патч трогает только один слой (из Золотого стандарта).
- [ ] **A5:** Зависимости указаны явно и ведут к существующим патчам (внутри контейнера или внешним).
- [ ] **A6:** Нет циклических зависимостей внутри контейнера.
- [ ] **A7:** Есть патч на базовую структуру (первый).
- [ ] **A8:** Есть патчи на логирование/healthcheck и на тесты.
- [**A9:** Каждый патч может быть проверен независимо.

**Если хотя бы один пункт нарушен** – C1.2 **не передаёт** результат аудитору, а исправляет сам (перегенерирует).

### 5.8. Аудит списка патчей с LLM-судьёй

**5.8.1.** C1.2 вызывает LLM-судью с системным промптом (Приложение А).  
**5.8.2.** Судья проверяет список патчей по критериям:
- Атомарность (нет ли «смешанных» патчей).
- Полнота (покрыты ли все функции контейнера).
- Размер (нет ли патчей, которые явно больше 5 файлов).
- Риски (например, патч меняет БД и одновременно логику – риск).
- Недетерминированные зоны (если в описании патча есть неоднозначность).

**5.8.3.** Результат сохраняется в `/data/projects/{project_id}/АУДИТ_ПАТЧЕЙ_{container_id}.md`.  
**5.8.4.** Если судья находит проблемы, C1.2 корректирует список патчей (максимум 3 итерации).  
**5.8.5.** Если после 3 итераций проблемы остались – создаётся задача в handover для ручного вмешательства (Архитектор).

**5.8.6. Обработка ошибок LLM-судьи:**  
- Таймаут (30 сек) или некорректный JSON → повтор 2 раза.  
- После 3 неудач – пропустить, но пометить в отчёте, требуется ручная проверка.

### 5.9. Сохранение списка патчей и графа

**5.9.1.** C1.2 создаёт файл **в папке проекта**:  
`/data/projects/{project_id}/patches/{container_id}_PATCHES.md`  
содержащий:
- Список патчей (ID, название, цель).
- Граф зависимостей в виде текста или JSON.
- Ссылки на файлы спецификаций L5.

**5.9.2.** Формат графа (JSON):

```json
{
  "container_id": "C-TG-1.1",
  "patches": [
    {"id": "P-TG-1.1.0", "depends_on": []},
    {"id": "P-TG-1.1.1", "depends_on": ["P-TG-1.1.0"]},
    ...
  ]
}
```

### 5.10. Индексация в векторную память проекта

**5.10.1.** После успешного аудита C1.2 вызывает API индексации (C2.6):

```bash
curl -X POST "http://localhost:8108/api/project/{project_id}/index" \
  -H "Content-Type: application/json" \
  -d '{
    "documents": [
      "/data/projects/{project_id}/specs/P-TG-1.1.0.md",
      "/data/projects/{project_id}/specs/P-TG-1.1.1.md",
      ...
    ]
  }'
```

**5.10.2.** API возвращает `{ "status": "ok", "indexed_count": N }`.  
**5.10.3.** Если индексация не удалась (ошибка, таймаут) – повтор 3 раза.  
**5.10.4.** После 3 неудач – создать задачу в handover для ручной индексации. Переход к L6 блокируется.

### 5.11. Передача на следующий этап

**5.11.1.** После утверждения патчей и индексации управление передаётся **сборщику очереди исполнения** (протокол `ПРОТОКОЛ_ОЧЕРЕДЬ.md`) для глобальной топологической сортировки патчей из всех контейнеров.

## 6. Аудит существующего замысла (если контейнер уже имеет патчи)

Если пользователь загружает проект, в котором для контейнера уже есть патчи (L5), система не должна слепо доверять им. Она обязана провести **быстрый аудит**.

### 6.1. Когда запускается аудит

- Загружен проект с уже существующими патчами (спецификациями L5).
- Пользователь говорит «у меня уже есть патчи, просто добавь новые» (тогда аудит только новых).
- После того как C1.2 сгенерировал патчи (как дополнительная проверка).

### 6.2. Алгоритм аудита

**6.2.1.** Загрузить существующие спецификации L5 из папки проекта.  
**6.2.2.** Сравнить их с эталонной структурой (атомарность, размер, зависимости).  
**6.2.3.** Выявить:
- Патчи, нарушающие атомарность (смешанные ответственности).
- Патчи, которые можно разбить или объединить.
- Отсутствие обязательных патчей (базовая структура, тесты, логирование).
- Циклические зависимости.

**6.2.4.** Сформировать отчёт в `АУДИТ_ПАТЧЕЙ_{container_id}.md`.  
**6.2.5.** Если есть критические нарушения – заблокировать этап и запросить ручное исправление.  
**6.2.6.** Если нарушения некритичны – предложить пользователю исправить, но можно продолжить.

## 7. Чек-лист аудитора (Рева) для приёмки этапа L5

Аудитор (Рева) получает папку проекта и проверяет **бинарно** (ДА/НЕТ). Если любой пункт = НЕТ – этап не пройден.

### 7.1. Формальная проверка

- **F-P1:** В папке `/data/projects/{project_id}/patches/` присутствует файл `{container_id}_PATCHES.md`.  
- **F-P2:** В папке `/data/projects/{project_id}/specs/` присутствуют спецификации для всех патчей из списка.  
- **F-P3:** Каждый патч имеет уникальный ID `P-{abbr}-{container_short}-{number}`.  
- **F-P4:** В каждой спецификации заполнены поля: `ID, Цель, Файлы, Зависимости, Критерии готовности, Тесты`.  
- **F-P5:** В графе зависимостей (JSON) нет ссылок на несуществующие ID.

### 7.2. Атомарность и размер

- **A-P1:** Цель каждого патча – одно действие (нет «и», «а также»).  
- **A-P2:** Список файлов в спецификации содержит не более 5 путей.  
- **A-P3:** Патч трогает только один слой (сверка с Золотым стандартом).  
- **A-P4:** Нет патча, который можно разбить на два независимых (оценка LLM-судьёй или экспертная).

### 7.3. Зависимости и граф

- **D-P1:** У каждого патча указаны зависимости (или `[]`).  
- **D-P2:** Все зависимости ведут к существующим патчам (в этом же контейнере или других).  
- **D-P3:** Нет циклических зависимостей (проверка топологической сортировкой).  
- **D-P4:** Патч «Базовая структура» (P0) не имеет зависимостей (или только от внешних контейнеров).  
- **D-P5:** Патчи на тесты зависят от всех патчей, которые они тестируют.

### 7.4. Полнота

- **C-P1:** Есть патч на базовую структуру (models, repositories, скелет main).  
- **C-P2:** Есть патч на логирование и healthcheck.  
- **C-P3:** Есть патч на юнит-тесты и патч на интеграционные тесты.  
- **C-P4:** Все операции из паспорта контейнера покрыты хотя бы одним патчем.  
- **C-P5:** Если в паспорте контейнера `requires_e2e_llm_tests: true`, то есть соответствующий E2E-патч.

### 7.5. Межконтейнерные зависимости

- **M-P1:** Если патч зависит от другого контейнера, эта зависимость явно указана и ссылается на существующий контейнер.  
- **M-P2:** Нет зависимостей от контейнеров, которые не входят в MVP (если отложены – патч не может быть выполнен).

### 7.6. Проверка LLM-судьи

- **L-P1:** Файл `АУДИТ_ПАТЧЕЙ_{container_id}.md` существует.  
- **L-P2:** Все замечания судьи исправлены (или признаны ложными).  
- **L-P3:** Если судья был недоступен – есть пометка и подтверждение ручной проверки.

### 7.7. Проверка индексации

- **I-P1:** Выполнена индексация всех спецификаций в векторную память.  
- **I-P2:** API индексации вернул `status: ok`.  
- **I-P3:** Если индексация не удалась – создана задача в handover.

### 7.8. Итоговое решение

Если все пункты = ДА → **ПРИНЯТО**, переход к сборке глобальной очереди.  
Если хотя бы один = НЕТ → **ОТКЛОНЕНО** с указанием нарушений.
