
### 📄 СПЕЦИФИКАЦИЯ ПАТЧА P18.3.2 (LEVEL 5)

**ID:** P18.3.2  
**Контейнер:** C18.3 (Alert Manager)  
**Название:** Механизм проверки правил  

**Зависимости:** P18.3.1

---

#### 1. ЗАМЫСЕЛ ПАТЧА  
Добавить фоновый процесс, который периодически опрашивает источники метрик (C18.2) и проверяет условия всех активных правил. При срабатывании правила генерируется событие алерта, которое будет обработано в следующих патчах. Это ядро логики оповещений.

---

#### 2. ТЕХНИЧЕСКИЕ ПАРАМЕТРЫ  

- **Планировщик:** использовать `APScheduler` для запуска задачи каждые `CHECK_INTERVAL` секунд (по умолчанию 10).  
- **Источники метрик:**  
  - **C18.2 Metrics Dashboard:** API для получения текущих агрегатов (`GET /api/metrics`). Адрес задаётся переменной окружения `METRICS_URL` (по умолчанию `http://c18.2:8094`).  
  - В будущем можно добавить другие источники (логи, затраты).  
- **Парсинг условий:**  
  - Условия хранятся в виде строк, например `cpu_usage > 90`. Для упрощения можно использовать безопасное `eval` с ограниченным контекстом (только арифметические операции и имена метрик). Либо использовать библиотеку для парсинга выражений. На первом этапе можно ограничиться простым сравнением: разбивать строку на три части (метрика, оператор, порог) и проверять.  
  - Поддерживаемые операторы: `>`, `<`, `>=`, `<=`, `==`.  
- **Логика проверки:**  
  1. Получить текущие метрики из C18.2.  
  2. Для каждого правила извлечь метрику из условия, найти её значение в ответе.  
  3. Вычислить условие. Если истинно и прошло больше `cooldown_minutes` с момента последнего срабатывания, считать правило сработавшим.  
  4. Записать событие в очередь (или в память) для последующей отправки.  
- **Состояние срабатываний:** хранить в памяти (словарь) для каждого правила время последнего срабатывания.  
- **Логирование:** все проверки и срабатывания логируются локально.  

---

#### 3. РЕАЛИЗАЦИЯ (L6 — КОД) – ОПИСАНИЕ  

- Добавить в приложение фоновую задачу `check_rules()`, запускаемую по таймеру.  
- В задаче загрузить все правила, запросить метрики из C18.2 (используя `httpx`).  
- Для каждого правила применить условие. Если условие выполнено и cooldown соблюдён, добавить запись в глобальный список `triggered_alerts` (или сразу вызывать обработчик отправки, но отправка будет в следующем патче).  
- Обновить время последнего срабатывания.  
- Логировать результаты.  

---

#### 4. КРИТЕРИЙ ПРИЕМКИ (DoD)  

- Планировщик запускается и периодически выполняет проверку.  
- При выполнении условия правила (например, `cpu_usage > 0` для теста) событие фиксируется.  
- При повторном срабатывании в пределах cooldown новое событие не генерируется.  
- Ошибки (недоступность C18.2, некорректное условие) логируются.  
- Состояние срабатываний сохраняется между итерациями.
