#### 1. ФУНКЦИОНАЛЬНОЕ ПРЕДНАЗНАЧЕНИЕ
Централизованная система оповещений, которая отслеживает ключевые метрики завода и уведомляет ответственных лиц или другие системы при выходе показателей за допустимые пределы. Поддерживает гибкую настройку правил (пороговые значения, условия срабатывания) и множество каналов доставки (Telegram, Slack, email, webhook). Интегрируется с источниками метрик (C18.2, C18.5, а также может напрямую подписываться на события из логов C18.1). Все события алертов логируются в C18.1 для последующего анализа.

#### 2. ТЕХНИЧЕСКАЯ ЛОГИКА (МЕХАНИКА)

- **Источники данных для проверки правил:**  
  – Периодический опрос API метрик C18.2 (например, каждые 10 секунд) для получения текущих значений.  
  – Подписка на поток событий из C18.1 (Log Aggregator) для немедленного реагирования на определённые типы логов (например, ошибки агентов).  
  – Получение данных о затратах из C18.5 (Cost Tracker) для контроля бюджета.  

- **Хранение правил:**  
  – Правила оповещений хранятся в конфигурационном файле (например, `alerts_rules.json`) или в легковесной БД (SQLite).  
  – Каждое правило содержит: уникальный ID, название, описание, условие (например, `metric > threshold`), порог, каналы уведомления, периоды тишины (чтобы не спамить).  
  – Правила могут создаваться, изменяться и удаляться через API (для интеграции с C4.3 Command Console).  

- **Проверка и срабатывание:**  
  – Фоновый процесс (воркер) периодически или по событию проверяет все активные правила.  
  – При выполнении условия генерируется событие алерта. Если алерт уже был отправлен и не сброшен, может применяться политика повторных уведомлений (например, не чаще раза в час).  
  – Для предотвращения ложных срабатываний может использоваться механизм «ok only after two consecutive failures» (настраивается).  

- **Доставка уведомлений:**  
  – Поддерживаемые каналы: Telegram (бот), Slack (входящий webhook), email (SMTP), HTTP webhook (для интеграции с BR1, BR15 и другими).  
  – Для каждого канала в конфигурации хранятся параметры подключения (токены, URL).  
  – Формат сообщения настраивается шаблонами (включает название правила, текущее значение, порог, время, ссылку на дашборд).  

- **API:**  
  – `GET /api/rules` – список всех правил.  
  – `POST /api/rules` – создание нового правила.  
  – `PUT /api/rules/{id}` – обновление правила.  
  – `DELETE /api/rules/{id}` – удаление правила.  
  – `GET /api/alerts/history` – история сработавших алертов.  
  – `POST /api/test` – тестирование канала уведомления (отправка тестового сообщения).  

- **Логирование:**  
  – Каждое срабатывание, а также ошибки доставки, отправляются в C18.1 (Log Aggregator) в формате:  
    ```json
    {
      "timestamp": "2026-03-18T12:00:00Z",
      "service": "C18.3",
      "event_type": "alert_triggered",
      "details": {
        "rule_id": "cpu_high",
        "metric": "cpu_usage",
        "value": 95.2,
        "threshold": 90,
        "channels": ["telegram", "slack"],
        "success": true
      }
    }
    ```

#### 3. ВХОДЫ И ВЫХОДЫ (INTERFACES)

- **REST API (внутри Docker-сети, порт 8095):**  
  – Все эндпоинты возвращают JSON.  
  – Пример создания правила:  
    `POST /api/rules`  
    ```json
    {
      "name": "CPU High",
      "description": "CPU usage above 90%",
      "condition": "cpu_usage > 90",
      "channels": ["telegram", "slack"],
      "cooldown_minutes": 60
    }
    ```  
    Ответ: `{ "id": "cpu_high", "status": "created" }`

- **Исходящие webhook-уведомления:**  
  – При срабатывании правила отправляется POST-запрос на настроенный URL с JSON-телом, содержащим детали алерта.
