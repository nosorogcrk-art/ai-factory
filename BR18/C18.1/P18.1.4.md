
### 📄 СПЕЦИФИКАЦИЯ ПАТЧА P18.1.4 (LEVEL 5) – ОПЦИОНАЛЬНО

**ID:** P18.1.4  
**Контейнер:** C18.1 (Log Aggregator)  
**Название:** API для чтения логов  

**Зависимости:** P18.1.3

---

#### 1. ЗАМЫСЕЛ ПАТЧА  
Добавить эндпоинт для получения логов с возможностью фильтрации по времени, источнику и типу события. Это позволит другим компонентам (например, C18.4 Traceability Index) выгружать логи для анализа, а также даст возможность ручного просмотра.

---

#### 2. ТЕХНИЧЕСКИЕ ПАРАМЕТРЫ  

- **Эндпоинт:** `GET /api/logs`  
- **Параметры запроса (query string):**  
  - `from` – начало временного диапазона (ISO 8601).  
  - `to` – конец временного диапазона.  
  - `service` – фильтр по сервису (можно несколько через запятую).  
  - `event_type` – фильтр по типу события.  
  - `limit` – максимальное количество записей (по умолчанию 100).  
  - `offset` – смещение для пагинации.  
- **Ответ:** JSON-массив объектов логов, соответствующих фильтрам.  
- **Поиск по файлам:**  
  – Логи хранятся в ежедневных файлах. Для быстрого поиска можно предварительно построить индекс (но на данном этапе можно просто сканировать файлы в заданном диапазоне дат, читать их построчно и фильтровать). Это может быть медленно, но для малых объёмов допустимо.  
- **Производительность:** для больших объёмов рекомендуется использовать индексацию (но это выходит за рамки патча).  

---

#### 3. РЕАЛИЗАЦИЯ (L6 — КОД) – ОПИСАНИЕ  

- Добавить эндпоинт `GET /api/logs`.  
- Определить функцию, которая по параметрам определяет список дат (файлов) для просмотра.  
- Для каждого файла читать строки, парсить JSON, применять фильтры, накапливать результат до достижения `limit`.  
- Вернуть массив.  

---

#### 4. КРИТЕРИЙ ПРИЕМКИ (DoD)  

- При запросе без параметров возвращаются последние 100 записей (из текущего файла).  
- Фильтрация по дате работает (логи за указанный период).  
- Фильтрация по сервису и типу события работает.  
- Пагинация через `limit` и `offset` работает.  
- При некорректных параметрах – 400.

### 📄 СПЕЦИФИКАЦИЯ ПАТЧА P18.1.5 (LEVEL 5)

**ID:** P18.1.5  
**Контейнер:** C18.1 (Log Aggregator)  
**Название:** Интеграция с C18.4 (уведомления)  

**Зависимости:** P18.1.3

---

#### 1. ЗАМЫСЕЛ ПАТЧА  
Организовать передачу новых логов в Traceability Index (C18.4) для построения индекса прослеживаемости. Это может быть реализовано через механизм событий: при поступлении нового лога отправлять его копию в C18.4 по HTTP. Либо можно использовать более эффективный метод, например, запись в общую очередь.

---

#### 2. ТЕХНИЧЕСКИЕ ПАРАМЕТРЫ  

- **Адрес C18.4:** переменная окружения `TRACEABILITY_INDEX_URL` (по умолчанию `http://c18.4:8096/api/logs` – предположительный эндпоинт для приёма логов).  
- **Механизм:**  
  – После успешной записи лога в файл (или пакета логов) асинхронно отправлять POST-запрос на указанный URL с тем же JSON-объектом (или массивом).  
  – Не блокировать основной процесс – использовать фоновые задачи FastAPI (`BackgroundTasks`).  
  – Если C18.4 недоступен, логировать ошибку, но не терять лог (он уже сохранён в файле).  
  – Для пакетной отправки можно отправлять логи по одному или группой – по согласованию с C18.4.  
- **Конфигурация:** добавить переменную `ENABLE_TRACEABILITY_FORWARD` для включения/отключения.  

---

#### 3. РЕАЛИЗАЦИЯ (L6 — КОД) – ОПИСАНИЕ  

- В эндпоинте `POST /api/logs` после успешной записи добавить вызов функции `forward_to_traceability(log_entry, background_tasks)`.  
- Функция отправляет POST-запрос к C18.4 с тем же JSON.  
- При ошибке логировать, но не прерывать выполнение.  

---

#### 4. КРИТЕРИЙ ПРИЕМКИ (DoD)  

- При включённой опции каждый принятый лог (или пакет) отправляется в C18.4.  
- При недоступности C18.4 ошибка логируется, но основной процесс не страдает.  
- Отправка асинхронна, не задерживает ответ клиенту.  

---
