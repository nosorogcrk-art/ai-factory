
### 📄 СПЕЦИФИКАЦИЯ ПАТЧА P6.1.3 (LEVEL 5)

**ID:** P6.1.3  
**Контейнер:** C6.1 (Chaos Monkey)  
**Название:** Планировщик (cron)

**Зависимости:** P6.1.2

---

#### 1. ЗАМЫСЕЛ ПАТЧА  
Добавить возможность запуска Chaos Monkey по расписанию с автоматическим выбором целей и типов сбоев согласно вероятностной конфигурации. Это позволит проводить регулярные тестирования без ручного вмешательства.

---

#### 2. ТЕХНИЧЕСКИЕ ПАРАМЕТРЫ  

- **Планировщик:** использовать `APScheduler` (или простой `threading.Timer` с периодическим запуском).  
- **Конфигурационный файл:** `chaos_config.json` со структурой:  
  ```json
  {
    "schedule": {
      "interval_minutes": 60,
      "jitter_minutes": 10,
      "time_range_start": "00:00",
      "time_range_end": "23:59"
    },
    "targets": {
      "include": ["br0", "br1", "br2", "br3", "br7", "br10"],
      "exclude": ["br6"]  // исключаем самого себя
    },
    "experiment_types": {
      "container_stop": 0.3,
      "container_rm": 0.2,
      "network_loss": 0.2,
      "cpu_stress": 0.1,
      "memory_stress": 0.1,
      "network_latency": 0.1
    },
    "params": {
      "stress_duration_sec": 30,
      "latency_ms": 500
    }
  }
  ```  
- **Процесс:**  
  – При запуске читается конфигурация.  
  – Планировщик запускает функцию `run_random_experiment()` каждые `interval_minutes ± jitter`.  
  – Функция выбирает случайный контейнер из списка целей (исключая исключённые) и случайный тип сбоя согласно вероятностям.  
  – Запускается эксперимент, результат логируется.  

---

#### 3. РЕАЛИЗАЦИЯ (L6 — КОД) – ОПИСАНИЕ  

- В основном файле добавить функцию `start_scheduler()`, которая инициализирует `BackgroundScheduler`.  
- При запуске приложения проверять наличие конфигурации и запускать планировщик.  
- Для случайного выбора использовать `random.choices` с весами.  

---

#### 4. КРИТЕРИЙ ПРИЕМКИ (DoD)  

- Планировщик запускает эксперименты с заданной периодичностью.  
- Выбор цели и типа соответствует конфигурации.  
- Результаты экспериментов логируются.  
- При изменении конфигурации планировщик перезапускается (опционально).

### 📄 СПЕЦИФИКАЦИЯ ПАТЧА P6.1.4 (LEVEL 5)

**ID:** P6.1.4  
**Контейнер:** C6.1 (Chaos Monkey)  
**Название:** API для ручного запуска

**Зависимости:** P6.1.3

---

#### 1. ЗАМЫСЕЛ ПАТЧА  
Создать REST API на базе FastAPI для ручного запуска экспериментов, просмотра конфигурации и результатов. Это позволит интегрировать Chaos Monkey с командной консолью (C4.3) и другими инструментами.

---

#### 2. ТЕХНИЧЕСКИЕ ПАРАМЕТРЫ  

- **Эндпоинты:**  
  - `POST /experiment` – запуск эксперимента. Тело JSON (опционально):  
    ```json
    {
      "container": "br1",
      "type": "container_stop",
      "params": {"duration_sec": 30}
    }
    ```  
    Если параметры не указаны, используются случайные. Возвращает ID эксперимента.  
  - `GET /experiment/{id}` – получение статуса и результата.  
  - `GET /config` – просмотр текущей конфигурации.  
  - `PUT /config` – обновление конфигурации (требует прав администратора).  
- **Формат ответа:** JSON с полями `status`, `result` и т.д.  
- **Хранение результатов:** каждый эксперимент сохраняется в локальной БД (SQLite) с ID, параметрами, временем, результатом.  
- **Интеграция с C4.3:** эндпоинты доступны из внутренней сети.  

---

#### 3. РЕАЛИЗАЦИЯ (L6 — КОД) – ОПИСАНИЕ  

- Добавить FastAPI-приложение в отдельный файл или встроить в существующий.  
- Реализовать функции для запуска эксперимента и сохранения в БД.  
- Для случайного выбора использовать те же функции, что и в планировщике.  

---

#### 4. КРИТЕРИЙ ПРИЕМКИ (DoD)  

- При запросе `POST /experiment` запускается эксперимент, возвращается ID.  
- `GET /experiment/{id}` возвращает результат (если завершён) или статус.  
- API доступно изнутри Docker-сети.  
- Изменение конфигурации работает.

### 📄 СПЕЦИФИКАЦИЯ ПАТЧА P6.1.5 (LEVEL 5)

**ID:** P6.1.5  
**Контейнер:** C6.1 (Chaos Monkey)  
**Название:** Логирование в BR18

**Зависимости:** P6.1.4

---

#### 1. ЗАМЫСЕЛ ПАТЧА  
Добавить отправку всех событий Chaos Monkey (запуск экспериментов, результаты) в центральный лог-агрегатор BR18 (C18.1). Это обеспечит наблюдаемость тестов и позволит анализировать устойчивость системы.

---

#### 2. ТЕХНИЧЕСКИЕ ПАРАМЕТРЫ  

- **Формат лога:**  
  ```json
  {
    "timestamp": "ISO 8601",
    "service": "C6.1",
    "event_type": "chaos_experiment",
    "details": {
      "container": "br1",
      "experiment_type": "container_stop",
      "duration_sec": 30,
      "recovered": true,
      "recovery_time_ms": 2500,
      "error": null
    }
  }
  ```  
- **Адрес BR18:** переменная окружения `BR18_URL` (по умолчанию `http://br18:8080/api/logs`).  
- **Асинхронность:** отправка логов не блокирует основной процесс.  

---

#### 3. РЕАЛИЗАЦИЯ (L6 — КОД) – ОПИСАНИЕ  

- Создать функцию `send_log_to_br18(details)`, которая отправляет POST-запрос.  
- В каждом месте, где завершается эксперимент (в планировщике, в API), вызывать эту функцию.  
- Использовать `httpx.AsyncClient` в фоновой задаче (или `asyncio.create_task`).  

---

#### 4. КРИТЕРИЙ ПРИЕМКИ (DoD)  

- При каждом эксперименте отправляется лог в BR18.  
- Лог содержит все обязательные поля.  
- При недоступности BR18 ошибка не влияет на выполнение эксперимента.
