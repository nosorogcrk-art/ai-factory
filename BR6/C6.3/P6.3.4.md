
### 📄 СПЕЦИФИКАЦИЯ ПАТЧА P6.3.4 (LEVEL 5)

**ID:** P6.3.4  
**Контейнер:** C6.3 (Token Guard)  
**Название:** Интеграция с BR18

**Зависимости:** P6.3.3

---

#### 1. ЗАМЫСЕЛ ПАТЧА  
Добавить отправку агрегированной статистики в Cost Tracker (C18.5) и алертов в Alert Manager (C18.3) при превышении лимитов. Также все значимые события логируются в Log Aggregator (C18.1). Это обеспечит централизованный мониторинг затрат.

---

#### 2. ТЕХНИЧЕСКИЕ ПАРАМЕТРЫ  

- **Периодическая отправка статистики:**  
  – Фоновый процесс (например, раз в час) собирает из таблицы `usage` данные за последний час и отправляет их в C18.5 (эндпоинт `/cost`).  
  – Формат данных: агрегированные суммы токенов и стоимости по агентам, веткам, моделям.  
- **Алерты:**  
  – При каждом отклонении запроса из-за превышения лимита (или при первом превышении) отправлять событие в C18.3 (Alert Manager).  
  – Формат алерта:  
    ```json
    {
      "severity": "warning",
      "source": "C6.3",
      "message": "Token limit exceeded for agent ГЕФЕСТ",
      "details": {"agent": "ГЕФЕСТ", "limit": 50000, "current": 52000}
    }
    ```  
- **Логирование в C18.1:**  
  – Каждый вызов `/check` и `/report`, а также ошибки отправлять в Log Aggregator.  
  – Использовать асинхронную отправку.  

---

#### 3. РЕАЛИЗАЦИЯ (L6 — КОД) – ОПИСАНИЕ  

- Добавить в приложение фоновую задачу (APScheduler), которая раз в час собирает статистику и отправляет в C18.5.  
- В функции `check_limits` при возврате `allowed: false` отправлять алерт в C18.3.  
- В эндпоинтах добавить вызов `send_log_to_br18`.  
- Использовать `httpx.AsyncClient` для асинхронных запросов.  

---

#### 4. КРИТЕРИЙ ПРИЕМКИ (DoD)  

- Раз в час отправляется статистика в C18.5.  
- При каждом отказе из-за лимита отправляется алерт в C18.3.  
- Все обращения к API логируются в C18.1.  
- При недоступности BR18 ошибки не ломают основной процесс.
