### 📄 СПЕЦИФИКАЦИЯ ПАТЧА P6.3.3 (LEVEL 5)

**ID:** P6.3.3  
**Контейнер:** C6.3 (Token Guard)  
**Название:** Автоматическое переключение моделей

**Зависимости:** P6.3.2

---

#### 1. ЗАМЫСЕЛ ПАТЧА  
Усовершенствовать логику выбора альтернативной модели: теперь при превышении лимита для запрашиваемой модели Token Guard может автоматически предложить более дешёвую модель, а также учитывать приоритеты моделей (например, сначала пробовать самую дешёвую). Также добавить возможность для агента принять предложение и выполнить запрос к другой модели (это уже поддерживается предыдущим патчем). В данном патче фокус на улучшении конфигурации и алгоритма выбора.

---

#### 2. ТЕХНИЧЕСКИЕ ПАРАМЕТРЫ  

- **Конфигурация моделей:**  
  – В `limits_config.json` добавить раздел `models` с приоритетами и стоимостью за токен:  
    ```json
    {
      "models": {
        "gpt-4": {"priority": 1, "cost_per_token": 0.00003},
        "gpt-3.5-turbo": {"priority": 2, "cost_per_token": 0.000002},
        "claude-instant": {"priority": 3, "cost_per_token": 0.0000015}
      }
    }
    ```  
  – Альтернативы теперь можно не указывать явно, а генерировать на основе приоритетов: при превышении лимита для модели с более высоким приоритетом (дорогой) предлагается модель с меньшим приоритетом (более дешёвая), если она доступна и её лимиты не превышены.  
- **Логика выбора:**  
  – Получить список моделей, отсортированных по приоритету (меньше приоритет – дороже).  
  – Начиная с запрошенной модели, двигаться к более дешёвым и проверять, есть ли у них достаточный остаток (с учётом estimated_tokens).  
  – Вернуть первую подходящую.  
- **Обработка случая, когда ни одна модель не подходит:** возвращать `{"allowed": false}`.  

---

#### 3. РЕАЛИЗАЦИЯ (L6 — КОД) – ОПИСАНИЕ  

- Модифицировать функцию `check_limits`, чтобы она использовала новую конфигурацию.  
- Вместо хардкода альтернатив, вычислять список кандидатов на основе приоритетов.  
- Учесть, что для каждой модели могут быть свои лимиты (в том числе отдельные).  

---

#### 4. КРИТЕРИЙ ПРИЕМКИ (DoD)  

- При превышении лимита для дорогой модели предлагается более дешёвая, если у неё есть запас.  
- Если у дешёвой тоже превышение, проверяется следующая.  
- Если ни одна не подходит, возвращается запрет.  
- Конфигурация моделей читается корректно.

### 📄 СПЕЦИФИКАЦИЯ ПАТЧА P6.3.4 (LEVEL 5)

**ID:** P6.3.4  
**Контейнер:** C6.3 (Token Guard)  
**Название:** Интеграция с BR18

**Зависимости:** P6.3.3

---

#### 1. ЗАМЫСЕЛ ПАТЧА  
Добавить отправку агрегированной статистики в Cost Tracker (C18.5) и алертов в Alert Manager (C18.3) при превышении лимитов. Также все значимые события логируются в Log Aggregator (C18.1). Это обеспечит централизованный мониторинг затрат.

---

#### 2. ТЕХНИЧЕСКИЕ ПАРАМЕТРЫ  

- **Периодическая отправка статистики:**  
  – Фоновый процесс (например, раз в час) собирает из таблицы `usage` данные за последний час и отправляет их в C18.5 (эндпоинт `/cost`).  
  – Формат данных: агрегированные суммы токенов и стоимости по агентам, веткам, моделям.  
- **Алерты:**  
  – При каждом отклонении запроса из-за превышения лимита (или при первом превышении) отправлять событие в C18.3 (Alert Manager).  
  – Формат алерта:  
    ```json
    {
      "severity": "warning",
      "source": "C6.3",
      "message": "Token limit exceeded for agent ГЕФЕСТ",
      "details": {"agent": "ГЕФЕСТ", "limit": 50000, "current": 52000}
    }
    ```  
- **Логирование в C18.1:**  
  – Каждый вызов `/check` и `/report`, а также ошибки отправлять в Log Aggregator.  
  – Использовать асинхронную отправку.  

---

#### 3. РЕАЛИЗАЦИЯ (L6 — КОД) – ОПИСАНИЕ  

- Добавить в приложение фоновую задачу (APScheduler), которая раз в час собирает статистику и отправляет в C18.5.  
- В функции `check_limits` при возврате `allowed: false` отправлять алерт в C18.3.  
- В эндпоинтах добавить вызов `send_log_to_br18`.  
- Использовать `httpx.AsyncClient` для асинхронных запросов.  

---

#### 4. КРИТЕРИЙ ПРИЕМКИ (DoD)  

- Раз в час отправляется статистика в C18.5.  
- При каждом отказе из-за лимита отправляется алерт в C18.3.  
- Все обращения к API логируются в C18.1.  
- При недоступности BR18 ошибки не ломают основной процесс.

### 📄 СПЕЦИФИКАЦИЯ ПАТЧА P6.3.5 (LEVEL 5)

**ID:** P6.3.5  
**Контейнер:** C6.3 (Token Guard)  
**Название:** API для управления

**Зависимости:** P6.3.4

---

#### 1. ЗАМЫСЕЛ ПАТЧА  
Создать административные эндпоинты для просмотра и изменения лимитов, сброса статистики, а также для интеграции с командной консолью (C4.3). Это позволит оперативно управлять бюджетом токенов.

---

#### 2. ТЕХНИЧЕСКИЕ ПАРАМЕТРЫ  

- **Эндпоинты:**  
  - `GET /limits` – возвращает текущие лимиты и расходы.  
  - `PUT /limits` – обновляет лимиты. Тело запроса должно соответствовать структуре `limits_config.json`.  
  - `POST /reset` – сбрасывает статистику (например, начало нового месяца). Принимает опциональный параметр `level` (global, branch, agent).  
- **Авторизация:**  
  – Эндпоинты доступны только при наличии заголовка `X-Admin-Key` с правильным ключом (ключ задаётся в конфиге).  
- **Логирование:**  
  – Все изменения лимитов и сбросы логируются в C18.1.  

---

#### 3. РЕАЛИЗАЦИЯ (L6 — КОД) – ОПИСАНИЕ  

- Добавить проверку авторизации через зависимость FastAPI.  
- Реализовать чтение и запись `limits_config.json` (и, возможно, синхронизацию с БД).  
- При сбросе статистики обнулять счётчики в таблице `budget` и, возможно, архивировать старые записи.  

---

#### 4. КРИТЕРИЙ ПРИЕМКИ (DoD)  

- `GET /limits` возвращает текущую конфигурацию и расходы.  
- `PUT /limits` обновляет лимиты и перезагружает конфигурацию.  
- `POST /reset` сбрасывает счётчики.  
- Без правильного ключа доступ запрещён (401/403).  
- Все операции логируются.
