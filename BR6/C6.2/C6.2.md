### **C6.2: Semantic Auditor (Семантический аудитор)**

**Ветка-родитель:** BR6 | **ID:** C6.2 | **Ответственный:** РЕВА

**1. ФУНКЦИОНАЛЬНОЕ ПРЕДНАЗНАЧЕНИЕ**  
Автоматическая проверка целостности и качества семантической структуры завода: документов Вики-Вселенной (BR2), связей патчей с исходными смыслами (traceability), графа зависимостей навыков (BR17) и соответствия метаданных установленным стандартам. При обнаружении критических нарушений (отсутствие traceability, циклические зависимости навыков) инициирует блокировку связанных артефактов и отправляет алерты в систему мониторинга (BR18). Аудит выполняется по расписанию и по запросу, результаты сохраняются для последующего анализа.

**2. ТЕХНИЧЕСКАЯ ЛОГИКА (МЕХАНИКА)**  

- **Типы проверок:**  
  1. **Traceability патчей:** для каждого патча (L4) из реестра задач проверяется наличие связи с узлом Вики-Вселенной (поле `related_entities` или явная ссылка `[[ID]]` в спецификации). Отсутствие связи → критическое нарушение, патч блокируется.  
  2. **Логические противоречия в документах:**  
     – С помощью семантического поиска (C2.3) и, при необходимости, вызова LLM выявляются документы, содержащие противоположные утверждения.  
     – Противоречия классифицируются по уровню критичности; при высоком уровне могут блокироваться связанные патчи.  
  3. **«Мусорные» смыслы:** поиск документов без входящих/исходящих ссылок («сироты»), а также устаревших версий (если поддерживается версионирование). Такие документы не блокируются, но фиксируются в отчёте.  
  4. **Граф навыков (BR17):** проверка на наличие циклов (например, A→B→C→A) и ссылок на несуществующие навыки. Циклы приводят к пометке навыка как `invalid`, несуществующие зависимости – к попытке автоматического исправления или уведомлению.  
  5. **Метаданные документов:** сверка с шаблонами (наличие обязательных полей, корректность формата). Несоответствие фиксируется в отчёте, но не блокируется автоматически.

- **Источники данных:**  
  – **BR2:** через API C2.2 (индексатор) для получения списка документов и их метаданных; C2.3 для семантического сравнения.  
  – **BR17:** через C17.3 (Skill Graph) для графа зависимостей навыков.  
  – **BR1/BR7:** через чтение реестра задач и графа патчей (API или прямое чтение файлов, если доступно).  

- **Режим работы:**  
  – **Периодический аудит:** запускается по расписанию (например, раз в сутки) с помощью встроенного планировщика (`APScheduler` или cron).  
  – **Ручной запуск:** через REST API (POST `/audit`), интегрированный с C4.3 Command Console, что позволяет выполнять аудит по требованию.  

- **Действия при обнаружении проблем:**  
  – **Критические нарушения** (отсутствие traceability, циклы в навыках):  
    * Блокировка патча через вызов API BR7 (установка статуса `BLOCKED`).  
    * Для навыков с циклами – обновление статуса в BR17 через C17.5 (опционально).  
    * Отправка алерта в BR18 (C18.3 Alert Manager) с уровнем `high`.  
  – **Некритические проблемы** (противоречия, сироты, метаданные):  
    * Запись в локальный журнал и отправка лога в BR18.  
    * При необходимости создание задачи на исправление через BR1 (C1.2) или через BR19.  
  – Все результаты сохраняются в локальном файле `01_ЦЕХ/01_ЖУРНАЛЫ/semantic_audit.log` (JSON Lines) и дублируются в BR18.

- **Логирование:**  
  – Каждый выявленный инцидент или завершённый цикл аудита формирует событие для BR18. Пример формата:  
    ```json
    {
      "timestamp": "2026-03-18T12:00:00Z",
      "service": "C6.2",
      "event_type": "audit_issue",
      "details": {
        "issue_type": "traceability_missing",
        "entity_id": "P1.2.3",
        "description": "Патч не имеет связи с Вики-Вселенной",
        "severity": "high",
        "action_taken": "blocked"
      }
    }
    ```

**3. ВХОДЫ И ВЫХОДЫ (INTERFACES)**  

- **REST API (внутри Docker-сети):**  
  – `POST /audit` – запуск полного аудита (все проверки). Тело запроса может содержать опциональные параметры (например, типы проверок).  
    Ответ: `202 Accepted` с ID задачи аудита.  
  – `GET /audit/{id}` – получение статуса и результатов конкретного запуска.  
  – `GET /audit/last` – получение последнего отчёта.  
  – `GET /config` – просмотр текущей конфигурации (пороги, расписание).  
  – `PUT /config` – изменение конфигурации (только для администратора).  

**4. ИНТЕГРАЦИИ**  

- **BR2 (Memory):**  
  – **C2.2 Indexer** – получение списка документов и метаданных.  
  – **C2.3 Semantic Search** – семантическое сравнение документов.  
- **BR17 (Skills):**  
  – **C17.3 Skill Graph** – анализ графа зависимостей навыков.  
- **BR1/BR7 (Tasks):**  
  – Реестр задач и граф патчей – для проверки traceability и блокировки.  
- **BR18 (Monitoring):**  
  – **C18.1 Log Aggregator** – отправка логов.  
  – **C18.3 Alert Manager** – отправка алертов.  
- **BR4 (Interface):**  
  – **C4.3 Command Console** – приём команд ручного запуска через API.  

**5. СТЕК ТЕХНОЛОГИЙ**  

- Python + FastAPI (микросервис).  
- Планировщик: `APScheduler` или cron.  
- HTTP-клиент (`httpx`) для вызовов API BR2, BR17, BR1/BR7, BR18.  
- (Опционально) вызов LLM для анализа противоречий (можно добавить позже).  
- Локальное хранение отчётов: файл JSON Lines.  
- Docker (контейнер без специальных привилегий).
