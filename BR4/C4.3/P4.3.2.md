
### 📄 СПЕЦИФИКАЦИЯ ПАТЧА P4.3.2 (LEVEL 5)

**ID:** P4.3.2  
**Контейнер:** C4.3 (Command Console)  
**Название:** Парсер команд и маршрутизация

**Зависимости:** P4.3.1

---

#### 1. ЗАМЫСЕЛ ПАТЧА  
Заменить заглушку на реальную логику обработки команд. Сервер должен анализировать введённую команду, определять целевую ветку (BR7, BR1, BR17, BR20, BR18, BR0) и соответствующий API, вызывать его и возвращать результат. Также добавляется поддержка команд `take`, `complete`, `delegate`, `status`, `logs`, `restart` и др.

---

#### 2. ТЕХНИЧЕСКИЕ ПАРАМЕТРЫ  

- **Алгоритм парсинга:**  
  - Простейший парсер на основе регулярных выражений или разделения строки.  
  - Примеры:  
    - `take <task_id>` → команда для BR7 (handover).  
    - `logs <service>` → запрос к BR18.  
    - `restart <service>` → вызов Docker API через BR0.  
- **Маршрутизация:** для каждой команды определён API целевого сервиса (URL из переменных окружения).  
- **Выполнение:** синхронный HTTP-запрос к соответствующему API, возврат результата.  
- **Обработка ошибок:** при недоступности сервиса или неверной команде возвращать понятное сообщение.  

---

#### 3. РЕАЛИЗАЦИЯ (L6 — КОД) – ОПИСАНИЕ  

- В эндпоинте `/api/command` реализовать функцию-диспетчер, которая вызывает нужный обработчик.  
- Создать отдельные функции-обработчики для каждой группы команд (например, `handle_task_command`, `handle_logs_command`).  
- Для команд, требующих прав (например, `restart`), пока проверка не реализована (будет в P4.3.5).  

---

#### 4. КРИТЕРИЙ ПРИЕМКИ (DoD)  

- Команда `take P1.2.3` приводит к вызову handover (если BR7 доступен).  
- Команда `logs br1` возвращает последние логи.  
- При неверной команде возвращается сообщение об ошибке.  
- Все действия логируются в локальный файл.
